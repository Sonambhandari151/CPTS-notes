# Attacking Applications Connecting to Services

## Core Idea
Applications that connect to backend services (databases, APIs, etc.) often embed **connection strings containing credentials** inside their compiled binaries. If these aren't protected, reverse-engineering the binary can leak plaintext credentials — useful for lateral movement or privilege escalation.

> [!tip] Why this matters
> Even when an app has no direct web-facing vulnerability, the binary itself may be leaking database/service credentials that are reused elsewhere on the network.

## Case 1 — ELF Executable (`octopus_checker`)

**Behavior when run:**
```bash
./octopus_checker

Program had started..
Attempting Connection
Connecting ...

01000:1:0:[unixODBC][Driver Manager]Can't open lib 'ODBC Driver 17 for SQL Server' : file not found
connected
```
The binary attempts a SQL connection — likely via a connection string containing credentials.

### Tooling: GDB + PEDA
**PEDA** (Python Exploit Development Assistance) extends GDB with easier memory/register inspection — useful for stepping through binaries and reading live variable values.

**Step 1 — Load and disassemble:**
```bash
gdb ./octopus_checker
```
```asm
gdb-peda$ set disassembly-flavor intel
gdb-peda$ disas main
```
Disassembly reveals scattered string references (parts of a SQL connection string) — not stored contiguously, and reversed due to endianness (the byte order used by the CPU architecture).

**Step 2 — Find the connection call:**
```asm
call   0x5555555551b0 <SQLDriverConnect@plt>
```
`SQLDriverConnect` is the ODBC API call that actually opens the DB connection — the full connection string must be assembled in memory just before this call.

**Step 3 — Breakpoint + run:**
```asm
gdb-peda$ b *0x5555555551b0
gdb-peda$ run
```
At the breakpoint, inspect the register holding the string pointer:
```
RDX: 0x7fffffffda70 ("DRIVER={ODBC Driver 17 for SQL Server};SERVER=localhost,1401;UID=username;PWD=password;")
```

> [!success] Outcome
> Full connection string recovered in plaintext, including `UID` and `PWD` — usable directly against the DB, or for **password reuse checks** against other services/users on the network.

## Case 2 — .NET DLL (`MultimasterAPI.dll`)

**Step 1 — Inspect metadata:**
```powershell
Get-FileMetaData .\MultimasterAPI.dll
```
Reveals it's a **.NET Framework 4.6.1** assembly, with references like an internal API route (`api/getColleagues`) and a local endpoint (`http://localhost:8081`).

**Step 2 — Decompile with dnSpy**
**dnSpy** is a debugger + .NET assembly editor that can read, edit, and step through decompiled C#/VB source directly from a compiled DLL.

Navigating to `MultimasterAPI.Controllers → ColleagueController` reveals a **hardcoded database connection string containing the password**, directly in the decompiled source.

> [!tip] Beyond direct DB access
> As with the ELF case, credentials pulled from a DLL are also worth testing via **password spraying** against other exposed services (SSH, RDP, other web logins, etc.) — reused creds are common in real environments.

## Tooling Summary
| Tool                    | Purpose                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------ |
| GDB + PEDA              | Live debugging of compiled ELF binaries — read registers/memory at runtime                             |
| `disas`                 | Disassemble a function to locate string references and API calls                                       |
| Breakpoints (`b *addr`) | Pause execution right before a sensitive call (e.g. `SQLDriverConnect`) to read arguments in registers |
| `Get-FileMetaData`      | Quick metadata triage of a .NET DLL (framework version, routes, endpoints)                             |
| dnSpy                   | Full decompilation/debugging of .NET assemblies — read source-level logic directly                     |

## Quick Recap
| Stage         | Technique                                        | Result                                                |
| ------------- | ------------------------------------------------ | ----------------------------------------------------- |
| Binary triage | Run the binary, observe connection attempts      | Confirms it talks to a backend service                |
| ELF analysis  | GDB + PEDA, breakpoint before `SQLDriverConnect` | Recovers full SQL connection string incl. credentials |
| DLL analysis  | `Get-FileMetaData` + dnSpy decompilation         | Recovers hardcoded DB password from source            |
| Follow-up     | Test recovered creds directly + password spray   | DB access and/or lateral movement across services     |
