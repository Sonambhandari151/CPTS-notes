# Other Notable Applications

## Core Takeaway
This module covers nine specific applications, but the real goal is **methodology** that generalises to *any* unfamiliar application encountered during an assessment — from fingerprinting and discovery to abusing built-in functionality and known public exploits.

> [!tip] Mindset
> A big part of pentesting is adapting to the unknown. Don't get discouraged if initial scans show nothing directly exploitable — dig through the noise. Weak/default creds on a forgotten Tomcat instance, or an exposed Git repo leaking an SSH key, are exactly the kind of things automated scanners miss but manual review catches.

Sections like osTicket and GitLab weren't just about those specific apps — they demonstrate how **support ticketing systems** and **Git repositories** in general tend to leak useful information elsewhere in an engagement.

## Methodology Checklist for Unknown Applications
1. **Fingerprint** — version, framework, underlying server (headers, error pages, default files/paths).
2. **Check for default/weak credentials** — a huge number of these apps ship with well-known admin defaults.
3. **Look for built-in "legitimate" functionality that can be abused** — file/service upload (WAR/AAR-style), API endpoints, plugin/config management — often more reliable than a public exploit.
4. **Check for known CVEs** matching the fingerprinted version.
5. **Don't stop at the front door** — ticketing systems, wikis, and intranets often leak credentials/secrets useful *elsewhere* in the network, even without a direct exploit.
6. **Filter out scanner noise manually** — automated tools (e.g. EyeWitness on large engagements) can produce hundreds of pages; manual review is what finds the outliers scanners miss.
