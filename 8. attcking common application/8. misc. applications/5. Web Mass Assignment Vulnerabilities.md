# Web Mass Assignment Vulnerabilities

## What It Is
**Mass assignment** is a framework convenience feature that lets developers dump an entire set of user-submitted form fields directly into an object/database record in one step, instead of assigning each field manually.

The vulnerability appears when this happens **without a whitelist** restricting which fields the user is actually allowed to set. An attacker can then add extra parameters to a request and modify fields they were never meant to control — including sensitive ones like `admin`, `role`, or `confirmed`.

> [!warning] Core idea
> If the backend blindly maps "whatever the client sent" onto a database record, the client effectively controls more of that record than the developer intended.

## Example — Ruby on Rails

**Intended model:**
```ruby
class User < ActiveRecord::Base
  attr_accessible :username, :email
end
```
Only `username` and `email` are *supposed* to be mass-assignable.

**Attacker-supplied payload:**
```javascript
{ "user" => { "username" => "hacker", "email" => "hacker@example.com", "admin" => true } }
```
Even though `admin` isn't declared as accessible, if the whitelist isn't enforced properly, the attacker can still set it — creating an admin account via a normal registration POST request.

## Worked Example — Asset Manager App

**Scenario:** After registering, login shows *"Account is pending approval"* — a human admin must approve new accounts.

**Reviewing `app.py`:**
```python
for i,j,k in cur.execute('select * from users where username=? and password=?',(username,password)):
  if k:
    session['user']=i
    return redirect("/home",code=302)
  else:
    return render_template('login.html',value='Account is pending for approval')
```
Login only succeeds if column `k` (the approval flag) is truthy.

**Reviewing the registration logic:**
```python
try:
  if request.form['confirmed']:
    cond=True
except:
  cond=False
with sqlite3.connect("database.db") as con:
  cur = con.cursor()
  cur.execute('select * from users where username=?',(username,))
  if cur.fetchone():
    return render_template('index.html',value='User exists!!')
  else:
    cur.execute('insert into users values(?,?,?)',(username,password,cond))
    con.commit()
    return render_template('index.html',value='Success!!')
```
If a `confirmed` parameter is present **at all** in the registration request (any truthy value), `cond` becomes `True` — and that value is inserted straight into the approval column.

### Exploitation Steps
1. Intercept the `/register` POST request in Burp Suite.
2. Add an extra parameter that isn't part of the normal form:
   ```
   username=new&password=test&confirmed=test
   ```
3. Submit registration → account is created **pre-approved**.
4. Log in immediately with `new:test` — no admin approval needed.

> [!success] Outcome
> By injecting a parameter the form never exposed, the approval workflow is bypassed entirely.

## Prevention

Always **explicitly whitelist** which attributes can be mass-assigned — never trust the full parameter set blindly.

**Rails "strong parameters" example:**
```ruby
class UsersController < ApplicationController
  def create
    @user = User.new(user_params)
    if @user.save
      redirect_to @user
    else
      render 'new'
    end
  end

  private

  def user_params
    params.require(:user).permit(:username, :email)
  end
end
```
`user_params` returns a hash containing **only** `username` and `email` — anything else sent by the client (e.g. `admin`, `confirmed`) is silently dropped before it ever reaches the database layer.

## Quick Recap
| Stage   | Technique                                           | Result                                                   |
| ------- | --------------------------------------------------- | -------------------------------------------------------- |
| Recon   | Review app source / registration flow               | Identify unprotected fields (`confirmed`, `admin`, etc.) |
| Exploit | Add extra params via Burp (e.g. `confirmed=test`)   | Bypass approval / privilege checks                       |
| Fix     | Explicit whitelisting (`permit`, `attr_accessible`) | Only intended fields are ever mass-assignable            |
