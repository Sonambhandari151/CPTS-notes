# LDAP

## What Is LDAP?
LDAP (**Lightweight Directory Access Protocol**) is a protocol for accessing and managing **directory information** — a hierarchical data store holding info about network resources (users, groups, computers, printers, etc.).

## Strengths
| Functionality       | Description                                                       |
| ------------------- | ----------------------------------------------------------------- |
| Efficient           | Fast queries via a lean query language and non-normalised storage |
| Global naming model | Supports multiple independent directories with unique entries     |
| Extensible          | Custom attributes/schemas for local/future needs                  |
| Compatibility       | Runs over TCP/IP and SSL, platform-independent                    |
| Authentication      | Enables single sign-on across multiple resources                  |

## Weaknesses
| Functionality | Description                                            |
| ------------- | ------------------------------------------------------ |
| Compliance    | Servers must be LDAP-compliant, limiting vendor choice |
| Complexity    | Hard to configure/secure correctly                     |
| Encryption    | **No encryption by default** — needs LDAPS or StartTLS |
| Injection     | Vulnerable to LDAP injection without input validation  |

## Common Use Cases
- **Authentication** — single login across multiple apps/systems
- **Authorisation** — permissions/access control for network resources
- **Directory Services** — search/retrieve/modify data for large user/device bases (based on X.500 standard)
- **Synchronisation** — replicate directory changes across systems

## LDAP vs Active Directory
| LDAP                                               | Active Directory (AD)                                 |
| -------------------------------------------------- | ----------------------------------------------------- |
| A protocol defining client-server directory access | A directory server using LDAP as one of its protocols |
| Open, cross-platform                               | Proprietary, Windows-only; needs DNS + Kerberos       |
| Flexible/extensible schema                         | Predefined schema extending X.500; modify with care   |
| Supports simple bind, SASL, etc.                   | Primarily Kerberos; also NTLM, LDAPS                  |

> [!note] Key distinction
> LDAP is **not** a directory service itself — it's the protocol used to talk to one. AD is an actual directory service that happens to use LDAP.

## How LDAP Requests Work
Client-server model, messages encoded in **ASN.1**, transmitted over TCP/IP.

**Request components:**
1. `Session connection`: The client connects to the server via an LDAP port (usually 389 or 636).
2. `Request type`: The client specifies the operation it wants to perform, such as `bind`, `search`, etc.
3. `Request parameters`: The client provides additional information for the request, such as the `distinguished name` (DN) of the entry to be accessed or modified, the scope and filter of the search query, the attributes and values to be added or changed, etc.
4. `Request ID`: The client assigns a unique identifier for each request to match it with the corresponding response from the server.

**Response components:**
1. `Response type`: The server indicates the operation that was performed in response to the request.
2. `Result code`: The server indicates whether or not the operation was successful and why.
3. `Matched DN:` If applicable, the server returns the DN of the closest existing entry that matches the request.
4. `Referral`: The server returns a URL of another server that may have more information about the request, if applicable.
5. `Response data`: The server returns any additional data related to the response, such as the attributes and values of an entry that was searched or modified

### ldapsearch Example
```bash
ldapsearch -H ldap://ldap.example.com:389 \
  -D "cn=admin,dc=example,dc=com" -w secret123 \
  -b "ou=people,dc=example,dc=com" "(mail=john.doe@example.com)"
```
Breakdown:
- Connect to the server `ldap.example.com` on port `389`.
- Bind (authenticate) as `cn=admin,dc=example,dc=com` with password `secret123`.
- Search under the base DN `ou=people,dc=example,dc=com`.
- Use the filter `(mail=john.doe@example.com)` to find entries that have this email address.
Example response:
```ldap
dn: uid=jdoe,ou=people,dc=example,dc=com
objectClass: inetOrgPerson
cn: John Doe
sn: Doe
uid: jdoe
mail: john.doe@example.com

result: 0 Success
```

## LDAP Injection

Attackers inject special LDAP characters into input fields to alter query logic — conceptually similar to SQL injection.

| Input                        | Effect                                      |
| ---------------------------- | ------------------------------------------- |
| `*`                          | Wildcard — matches any number of characters |
| `( )`                        | Groups expressions                          |
| `\|`                         | Logical OR                                  |
| `&`                          | Logical AND                                 |
| `(cn=*)` / `(objectClass=*)` | Conditions that always evaluate true        |
|                              |                                             |

### Example Vulnerable Query
```php
(&(objectClass=user)(sAMAccountName=$username)(userPassword=$password))
```

**Bypass via username field:**
```php
$username = "*";
$password = "dummy";
// matches ANY user account with password "dummy"
```

**Bypass via password field:**
```php
$username = "dummy";
$password = "*";
// matches the "dummy" account with ANY password
```

> [!danger] Impact
> LDAP injection can lead to unauthorised access, privilege escalation, and full application/server compromise — plus data tampering or deletion in the directory itself.

### Prevention
- Validate and sanitize all user input before use in LDAP queries
- Strip LDAP-specific special characters (`*`, `(`, `)`, `&`, `|`)
- Use parameterised queries so input is always treated as data, never as query logic

## Practical Walkthrough

### Step 1 — Enumeration
```bash
nmap -p- -sC -sV --open --min-rate=1000 10.129.204.229

PORT    STATE SERVICE VERSION
80/tcp  open  http    Apache httpd 2.4.41 (Ubuntu)
|_http-title: Login
389/tcp open  ldap    OpenLDAP 2.2.X - 2.3.X
```
Port 389 (LDAP) + a login page on port 80 → strong hint the web app authenticates via LDAP.

### Step 2 — Exploiting the Injection
Since OpenLDAP is present, it's reasonable to assume the login form on port 80 authenticates against it.

**Test:** enter `*` as both username and password.

> [!success] Result
> Wildcard input in both fields bypasses authentication entirely — the LDAP query matches any entry, granting unauthorised access.
