# Attacking thick client applications — simplified notes

## Quick theory (just the essentials)

**Thick client** = app installed locally that does its own processing (unlike a web app, which relies on the browser + server). Built in Java, C++, .NET, etc.

**Two-tier vs three-tier:**

```
Two-tier:    Client ────────────► Database
Three-tier:  Client ──HTTP──► App server ──► Database
```

- Two-tier = client talks straight to the DB. Riskier — no gatekeeper.
- Three-tier = client talks to a server first. Safer, but the server itself is now a normal web app, so it can have SQLi, path traversal, etc.

**Why thick clients are less secure:** the whole binary sits on the user's machine, so anyone with local access can reverse-engineer it — hardcoded passwords, logic, validation, all exposed.

**Common vulnerabilities:** hardcoded credentials, insecure local storage, DLL hijacking, buffer overflows, SQL injection, verbose error messages leaking internals.

**Testing approach — 3 angles:**

| Angle        | What you're doing                                             | Tools                                   |
| ------------ | ------------------------------------------------------------- | --------------------------------------- |
| Client-side  | Reverse-engineer the binary (static) + watch it run (dynamic) | Ghidra, IDA, dnSpy, JADX, x64dbg, Frida |
| Network-side | Capture traffic between client and server                     | Wireshark, Burp Suite, tcpdump          |
| Server-side  | Same as normal web app testing (OWASP Top 10)                 | —                                       |

Info-gathering tools worth knowing: **CFF Explorer** (inspect exe structure), **Detect It Easy** (identify what built the binary), **Process Monitor / ProcMon** (watch file/registry/process activity live), **Strings** (pull readable text out of a binary).

## Walkthrough: recovering hardcoded credentials

**Setup:** you already have SMB access to a `NETLOGON` share and find `Restart-OracleService.exe` sitting in it.

### 1. Run it — nothing happens

```cmd
C:\Apps>.\Restart-OracleService.exe
C:\Apps>
```

No output. Either it failed silently or it's doing something you can't see. Time to watch it, not just run it.

### 2. Watch it with ProcMon

ProcMon logs every file/registry/process action live — the fastest way to see "what does this actually do" without reverse engineering the whole thing.

It shows the exe creating a temp file in:
```
C:\Users\Matt\AppData\Local\Temp
```

### 3. Stop the temp file from self-deleting

The file gets deleted right after creation (you'll see why in step 4). Fix: deny delete permission on the Temp folder so the file survives.

**How:** right-click `Temp` folder → Properties → Security → Advanced → your user → Disable inheritance → convert to explicit permissions → Edit → Show advanced permissions → **uncheck** "Delete subfolders and files" and "Delete" → OK → Apply → OK → OK.

This blocks only the delete action — everything else runs normally.

### 4. Re-run it and grab the dropped file

```cmd
C:\Apps>dir C:\Users\cybervaca\AppData\Local\Temp\2

6F39.bat
6F39.tmp
```

(Filename is random each run.)

### 5. Read the batch file

```batch
if %username% == matt goto correcto
if %username% == frankytech goto correcto
if %username% == ev4si0n goto correcto
goto error

:correcto
echo TVqQAAMAAAAEAAAA... > c:\programdata\oracle.txt
echo AAAAAAAAAAgAAAAA... >> c:\programdata\oracle.txt
<SNIP - many more echo lines>

echo $salida = $null; $fichero = (Get-Content C:\ProgramData\oracle.txt); foreach ($linea in $fichero) {$salida += $linea}; $salida = $salida.Replace(" ",""); [System.IO.File]::WriteAllBytes("c:\programdata\restart-service.exe", [System.Convert]::FromBase64String($salida)) > c:\programdata\monta.ps1
powershell.exe -exec bypass -file c:\programdata\monta.ps1
del c:\programdata\monta.ps1
del c:\programdata\oracle.txt
c:\programdata\restart-service.exe
del c:\programdata\restart-service.exe
```

**What it does:**
1. Checks if your username is on a hardcoded allowlist (weak "access control")
2. Writes a base64 blob line-by-line into `oracle.txt`
3. Builds a PowerShell script (`monta.ps1`) that decodes it into `restart-service.exe`
4. Runs everything, then **deletes all 3 files** — hence step 3's ACL trick

### 6. Strip the `del` lines and re-run

Just remove the three `del` commands (and don't let it run/delete the final exe). Now everything it builds stays in `c:\programdata\` for you to inspect calmly.

### 7. Rebuild the final exe manually

```powershell
C:\> cat C:\programdata\monta.ps1
```
```powershell
$salida = $null; $fichero = (Get-Content C:\ProgramData\oracle.txt); foreach ($linea in $fichero) {$salida += $linea}; $salida = $salida.Replace(" ",""); [System.IO.File]::WriteAllBytes("c:\programdata\restart-service.exe", [System.Convert]::FromBase64String($salida))
```

In plain terms: read `oracle.txt`, join all lines, strip spaces, base64-decode, save as `restart-service.exe`.

```powershell
C:\> ls C:\programdata\
monta.ps1              273 bytes
oracle.txt          601066 bytes
restart-service.exe  432273 bytes
```

### 8. Run it and see what it does

```powershell
C:\> .\restart-service.exe
```
Prints a banner ("Restart Oracle created by HelpDesk, 2010"). Running under ProcMon again shows lots of registry lookups — but nothing that clearly shows credentials. Static/registry inspection is dead-ended → time to check what's happening **in memory** while it runs.

### 9. Set up x64dbg to skip the noise

x64dbg → Options → Preferences → uncheck everything except **Exit Breakpoint**.

**Why:** normally the debugger pauses many times as DLLs load. Keeping only the exit breakpoint lets the program run almost to completion, so whatever it computed along the way is still sitting in memory when you pause.

### 10. Inspect memory for hidden data

![[Pasted image 20260707112143.png]]

Open `restart-service.exe` in x64dbg → right-click in CPU view → **Follow in Memory Map**.

One region stands out: size `0x3000`, type `MAP`, protection `-RW--`.

**Why this one:** `MAP` type usually means a memory-mapped file — data the program treats like memory instead of writing it to disk as a separate file. That makes it a strong hiding spot for a hidden payload.

Double-click it → see `MZ` in the ASCII view → that's the signature of a Windows executable. So there's a second exe hidden in memory.

### 11. Dump it to disk

Right-click the memory region → **Dump Memory to File**. Now you have the hidden data as a normal file you can analyze with regular tools.

### 12. Confirm what it is

```powershell
C:\> strings64.exe .\restart-service_00000000001E0000.bin
```
```
.NETFramework,Version=v4.0,Profile=Client
.NET Framework 4 Client Profile
```
Confirms it's a .NET executable, loaded straight from memory instead of disk (to dodge easy static analysis).

### 13. Deobfuscate it

```cmd
de4dot v3.1.41592.3405
Detected Unknown Obfuscator
Cleaning ...
Saving ...-cleaned.bin
```

.NET obfuscators scramble class/method/variable names into garbage. de4dot undoes as much of that as possible so the decompiled code is actually readable.

### 14. Decompile and read the source

Drag the cleaned `.bin` into **dnSpy**. The recovered source shows this is a custom `runas.exe`-style tool that restarts the Oracle service using **hardcoded credentials** built right into the code (wrapped in `SecureString` at runtime — that protects the value in memory, but doesn't hide it from someone reading the decompiled source).

## The pattern to remember

| Problem                                    | Fix                                                |
| ------------------------------------------ | -------------------------------------------------- |
| Program shows nothing                      | Watch it with ProcMon instead of guessing          |
| It deletes its own evidence                | Deny delete permission on the folder first         |
| Secrets aren't on disk or in the registry  | Check memory with a debugger while it runs         |
| Found data looks like a file inside memory | Dump it, run `strings`, decompile it               |
| Decompiled code is scrambled               | Deobfuscate first (de4dot), then decompile (dnSpy) |

Big picture: if you have local execution rights, nothing the program does is truly hidden — not its file writes, not its memory, not its own code.
