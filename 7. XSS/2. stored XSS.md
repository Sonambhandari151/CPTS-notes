## Stored (Persistent) XSS

### Overview

- **Persistence:** The malicious script is saved directly into the web application's **back-end database**.
    
- **Impact:** High. Any user who visits the page where the data is retrieved (e.g., a comments section or a profile) will execute the payload in their browser.
    
- **Removal:** Difficult. Since the payload is in the database, simply clearing the browser cache or closing the session won't stop the attack; the entry must be manually deleted from the server.
    

---

### Detection & Testing

To identify if a field is vulnerable, you input a script and check if the browser executes it instead of just displaying it as text.

#### 1. Standard Testing Payload

HTML

```
<script>alert(window.origin)</script>
```

- **Why `window.origin`?** It displays the URL where the script is executing. This helps verify if the vulnerability is on the main site or isolated inside an `<iframe>`.
    

#### 2. Alternative Payloads

If a browser blocks `alert()`, use these to confirm XSS:

- **Print Dialog:** `<script>print()</script>` (Triggers the browser's print window).
    
- **Plaintext Break:** `<plaintext>` (Stops the browser from rendering any further HTML, displaying the rest of the page's source code as raw text).
    

---

### Verification Workflow

1. **Inject:** Enter the payload into the target input field (e.g., a To-Do list or comment box).
    
2. **Execute:** Observe if the script runs (e.g., an alert box appears).
    
3. **Inspect Source:** Press `CTRL+U` to verify the script is sitting in the HTML:
    
    `<ul><script>alert(window.origin)</script></ul>`
    
4. **Confirm Persistence:** Refresh the page. If the script executes again automatically, the XSS is **Stored**.
    

---

### Identifying the Target

> **Note:** Modern apps often use IFrames to isolate input forms. Using `alert(window.origin)` is essential here because the origin shown in the alert will tell you exactly which domain or sub-service is actually vulnerable.
