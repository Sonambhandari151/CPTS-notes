## 🔹 Open Vulnerability Assessment Language (OVAL)

**What it is:**

- An international **standard** used to check system state, vulnerabilities, and compliance.
    
- Supported by the U.S. Department of Homeland Security.
    
- Used by NIST’s **SCAP (Security Content Automation Protocol)** for automating vulnerability management and compliance checks.
    

**Goal:** Make vulnerability checks **standardized, repeatable, and shareable** in XML format.

**Process (3 steps):**

1. Identify system configurations for testing.
    
2. Evaluate current system state.
    
3. Report results.
    

**Possible states:**

- Vulnerable
    
- Non-compliant
    
- Installed Asset
    
- Patched
    

**Why useful:**

- Can **detect problems without exploiting them** (safe scanning).
    
- Helps decide what needs patching.
    

**OVAL Definitions (XML-based):**

1. **Vulnerability Definitions** → checks for known vulnerabilities.
    
2. **Compliance Definitions** → checks if system matches policies.
    
3. **Inventory Definitions** → checks if specific software is installed.
    
4. **Patch Definitions** → checks if patches are applied.
    

**Unique ID Format:**

- Looks like `oval:org.mitre.oval:obj:1116`
    
- Format = `oval:OrganizationDomain:IDType:IDValue`
    
- Types: `def` (definition), `obj` (object), `ste` (state), `var` (variable).
    

**Tools:**

- Scanners like **Nessus** can use OVAL for compliance templates.

## 🔹 Common Vulnerabilities and Exposures (CVE)

**What it is:**

- A **public catalog of security vulnerabilities** (sponsored by DHS).
    
- Each issue gets a **unique CVE ID** assigned by a CVE Numbering Authority (CNA).
    
- Provides: description, references, and standardization.
    

**Why important:**

- Makes it easy for IT/security teams to identify, track, and patch vulnerabilities.
    
- Used worldwide by researchers, vendors, and tools.
    

---

## 🔹 How CVE IDs Are Assigned (Process)

**Requirements for CVE:**

- Must be independently fixable.
    
- Must affect only one codebase.
    
- Must be acknowledged & documented by vendor.
    

**Stages:**

1. **Identify need for CVE** – Is it a vulnerability? Check if it already exists.
    
2. **Contact Vendor** – Report issue directly (responsible disclosure).
    
3. **Check CNA** – If vendor is a CNA, contact them; if not, contact 3rd-party coordinator.
    
4. **Request via Web Form** – If above fails, request CVE from CVE Team.
    
5. **Confirmation** – Researcher gets an email confirming request.
    
6. **Receive CVE ID** – Assigned privately at first.
    
7. **Public Disclosure** – Announced once vendors/parties are ready.
    
8. **Announcement** – Researcher ensures each CVE represents different vulnerabilities.
    
9. **Add Info to CVE Team** – Researcher provides details for NVD (National Vulnerability Database).
    

---

## 🔹 Responsible Disclosure

- **Definition:** Researcher reports issue to vendor first before public disclosure.
    
- **Why important:** Ensures patch is ready → prevents attackers from abusing “0-day” vulnerabilities.
    
- **Bad disclosure:** Public disclosure without notice → attackers exploit before fix.
    

---

## 🔹 Examples of CVEs

1. **CVE-2020-5902**
    
    - Vulnerability: BIG-IP Traffic Management UI (TMUI).
        
    - Type: Unauthenticated Remote Code Execution (RCE).
        
    - Impact: Complete system takeover.
        
2. **CVE-2021-34527 (PrintNightmare)**
    
    - Vulnerability: Windows Print Spooler service.
        
    - Type: Authenticated Remote Code Execution (RCE).
        
    - Impact: Full control of system/domain controllers.
        
    - Dangerous: Allows attackers to control networks.
        

---

## 🔹 Summary

- **OVAL** → Standard language to detect vulnerabilities/configurations (safe, XML-based, used by scanners like Nessus).
    
- **CVE** → Public catalog of vulnerabilities with unique IDs (helps track & fix).
    
- **Responsible Disclosure** → Ethical way to report vulnerabilities to vendors before making public.
    
- **Examples** → CVE-2020-5902 (BIG-IP RCE), CVE-2021-34527 (PrintNightmare).
