# Situational Awareness

Orienting yourself in space and time on a newly-landed system — before jumping into privesc — lets you make informed, proactive decisions instead of reactive ones. Look for other reachable hosts, protections needing bypass, or tools that simply won't work against this target.

---

## Network Information

> [!info] Why this matters for privesc
> A **dual-homed** host (belongs to two+ networks, usually via multiple NICs) might open lateral movement into a previously unreachable network segment. Even when it doesn't directly help escalate privileges locally, network info can reveal a different path forward, or intel useful for lateral movement after escalation succeeds.

Check:
- [Routing tables](https://en.wikipedia.org/wiki/Routing_table) — local + surrounding network visibility
- Local domain info if AD-joined, including DC IPs
- [ARP cache](https://docs.microsoft.com/en-us/windows-server/administration/windows-commands/arp) per interface — recently-contacted hosts, potentially indicating where admins RDP/WinRM in from

## Enumerating Protections

Modern environments almost always run some AV/EDR, actively monitoring/alerting/blocking. These directly threaten enumeration and exploitation tooling — especially public PoCs. Knowing exactly what's in place informs which methods will actually work, and how to modify/craft payloads before compiling.

### Application Whitelisting — AppLocker

Many orgs control what applications/file types users can run — often blocking non-admins from `cmd.exe`, `powershell.exe`, or other unneeded binaries. Microsoft's solution: **[AppLocker](https://docs.microsoft.com/en-us/windows/security/threat-protection/windows-defender-application-control/applocker/applocker-overview)**. We can use the [GetAppLockerPolicy](https://docs.microsoft.com/en-us/powershell/module/applocker/get-applockerpolicy?view=windowsserver2019-ps) cmdlet to enumerate the local, effective (enforced), and domain AppLocker policies.

> [!warning] Real-world detection is common
> Clients frequently have protections detecting the tools introduced in the previous section (Seatbelt, winPEAS, etc.). Some EDR products flag or block usage of even normal-looking binaries like `net.exe` or `tasklist` — an accountant's machine suddenly running specific CLI tools can trigger immediate alerts. Early protection enumeration saves time on non-evasive engagements and can make or break an evasive one.

#### Test AppLocker Policy
### Test Whether a Specific Binary Is Blocked

```powershell
PS C:\htb> Get-AppLockerPolicy -Local | Test-AppLockerPolicy -path C:\Windows\System32\cmd.exe -User Everyone

FilePath                    PolicyDecision MatchingRule
--------                    -------------- ------------
C:\Windows\System32\cmd.exe         Denied c:\windows\system32\cmd.exe
```

Directly confirms `cmd.exe` is blocked for the `Everyone` group — use `Test-AppLockerPolicy` against any specific binary/path to check before attempting to run it.

## Key Takeaways

- [ ] `ipconfig /all` reveals dual-homed hosts — a second network segment potentially reachable for lateral movement
- [ ] `arp -a` shows recently-contacted hosts per interface — hints at admin RDP/WinRM patterns
- [ ] `route print` confirms which network segments are actually routable from this host
- [ ] `Get-MpComputerStatus` — check `RealTimeProtectionEnabled` before assuming AV will/won't interfere
- [ ] `Get-AppLockerPolicy -Effective` shows enforced rules; `Test-AppLockerPolicy -path <binary> -User <group>` confirms if a specific binary is blocked before you try running it
- [ ] Real-world engagements almost always have some AV/EDR — enumerate first to avoid wasted/detected attempts, especially critical on evasive engagements
