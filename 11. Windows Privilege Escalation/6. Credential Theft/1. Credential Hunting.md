# Section 21: Credential Hunting


---

## Application Configuration Files

### Overview

Against best practices, applications often store passwords in **cleartext** configuration files. If we gain command execution in an unprivileged user context, we may find credentials.


### Searching for Credentials in Configuration Files

#### Using findstr Utility

The [findstr utility](https://ss64.com/nt/findstr.html) can search for sensitive information across multiple file types:

```powershell
PS C:\htb> findstr /SIM /C:"password" *.txt *.ini *.cfg *.config *.xml
```

**findstr Flags:**
- `/S` = Search subdirectories
- `/I` = Case-insensitive search
- `/M` = Print only filenames
- `/C:"password"` = Search string

#### Common Configuration File Locations

Applications commonly store sensitive data in configuration files with these extensions:
- `.txt` - Text files
- `.ini` - Initialization files
- `.cfg` - Configuration files
- `.config` - .NET configuration files
- `.xml` - XML configuration files

### IIS Configuration Files

#### web.config

Sensitive IIS information such as credentials may be stored in `web.config` files.

**Default IIS Location:**
```
C:\inetpub\wwwroot\web.config
```

> [!warning] Multiple Versions
> There may be multiple versions of `web.config` in different locations, which should be searched for recursively using findstr with the `/S` flag.

#### Common IIS Locations to Check

- `C:\inetpub\wwwroot\web.config`
- `C:\inetpub\wwwroot\*\web.config`
- Application-specific directories
- Backup/archive directories

## Dictionary Files

### Chrome Dictionary Files

#### Concept

Sensitive information such as passwords may be entered in:
- Email clients
- Browser-based applications
- Web forms

When typed, the browser underlines any words it doesn't recognize. Users often add these words to their dictionary to avoid the distracting red underline, **thereby storing the password in the dictionary file**.

#### Chrome Custom Dictionary Location

```
C:\Users\<username>\AppData\Local\Google\Chrome\User Data\Default\Custom Dictionary.txt
```

#### Searching Chrome Dictionary

```powershell
PS C:\htb> gc 'C:\Users\htb-student\AppData\Local\Google\Chrome\User Data\Default\Custom Dictionary.txt' | Select-String password

Password1234!
```


#### Other Browser Dictionary Locations

Similar techniques can be applied to:
- **Firefox**: Profile-specific dictionaries
- **Edge**: User data directory dictionaries
- **Safari**: Dictionary files in user library
- **Other applications**: Email clients, text editors, IDE spell-checkers

## Unattended Installation Files

### Overview

Unattended installation files define:
- Auto-logon settings
- Additional accounts to be created
- Installation parameters
- Credentials for automated tasks

Passwords in unattend files are stored in **plaintext** or **base64 encoded** format.

### Common Unattended Installation Files

- `unattend.xml`
- `autounattend.xml`
- `sysprep.xml`
- Installation answer files

### Typical Locations

These files should be automatically deleted after installation, but may be found in:
- `C:\Windows\Panther\`
- `C:\Windows\System32\sysprep\`
- Installation media/USB drives
- Backup/archive directories
- Admin shared folders
- Version control systems (accidental commits)

### unattend.xml Example

```xml
<?xml version="1.0" encoding="utf-8"?>
<unattend xmlns="urn:schemas-microsoft-com:unattend">
    <settings pass="specialize">
        <component name="Microsoft-Windows-Shell-Setup" processorArchitecture="amd64" publicKeyToken="31bf3856ad364e35" language="neutral" versionScope="nonSxS" xmlns:wcm="http://schemas.microsoft.com/WMIConfig/2002/State" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
            <AutoLogon>
                <Password>
                    <Value>local_4dmin_p@ss</Value>
                    <PlainText>true</PlainText>
                </Password>
                <Enabled>true</Enabled>
                <LogonCount>2</LogonCount>
                <Username>Administrator</Username>
            </AutoLogon>
            <ComputerName>*</ComputerName>
        </component>
    </settings>
</unattend>
```


> [!danger] Common Mistake
> Sysadmins often create copies of unattend.xml files in various locations during image development
> These copies may remain on the system after deployment, making them discoverable

### Searching for Unattended Installation Files

```powershell
# Search in common locations
PS C:\htb> Get-ChildItem -Path C:\Windows\Panther\ -Recurse -Filter "*unattend*"
PS C:\htb> Get-ChildItem -Path C:\Windows\System32\sysprep\ -Recurse -Filter "*unattend*"

# Recursive search across entire system
PS C:\htb> Get-ChildItem -Path C:\ -Recurse -Filter "*unattend*" -ErrorAction SilentlyContinue
```

## PowerShell History File

### PowerShell Version & History Saving

#### History File Location

```
C:\Users\<username>\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt
```

### Confirming History File Save Path

```powershell
PS C:\htb> (Get-PSReadLineOption).HistorySavePath
```

## PowerShell Credentials

### Overview

PowerShell credentials are often used for:
- Scripting and automation tasks
- Scheduled tasks
- Recurring administrative operations
- Service accounts

### Credential Protection: DPAPI

PowerShell credentials are protected using **DPAPI** ([Data Protection API](https://en.wikipedia.org/wiki/Data_Protection_API))

#### DPAPI Characteristics

- Credentials typically **can only be decrypted** by:
  - The **same user** who created them
  - On the **same computer** they were created on
- Encryption key is derived from user's login credentials
- Provides per-user, per-computer encryption

### Credential Storage Methods

#### Method 1: Export-Clixml with Get-Credential

```powershell
# Create encrypted credential export
Get-Credential | Export-Clixml -Path 'C:\scripts\pass.xml'
```

This creates an XML file containing DPAPI-encrypted credentials.

#### Method 2: Script Example - Connect-VC.ps1

Consider the following script a sysadmin has created:

```powershell
# Connect-VC.ps1
# Get-Credential | Export-Clixml -Path 'C:\scripts\pass.xml'
$encryptedPassword = Import-Clixml -Path 'C:\scripts\pass.xml'
$decryptedPassword = $encryptedPassword.GetNetworkCredential().Password
Connect-VIServer -Server 'VC-01' -User 'bob_adm' -Password $decryptedPassword
```

> [!note] Script Analysis
> 1. Credentials are imported from XML file
> 2. DPAPI automatically decrypts (if correct user/computer)
> 3. Password is extracted using GetNetworkCredential()
> 4. Credentials are used to connect to vCenter

### Decrypting PowerShell Credentials

#### Decryption Process

If we have **gained command execution** in the context of the user who created the credentials, we can recover the cleartext credentials from the XML file:

```powershell
PS C:\htb> $credential = Import-Clixml -Path 'C:\scripts\pass.xml'

PS C:\htb> $credential.GetNetworkCredential().username
bob

PS C:\htb> $credential.GetNetworkCredential().password
Str0ng3ncryptedP@ss!
```

#### Step-by-Step Decryption

**Step 1: Import Encrypted Credentials**

```powershell
$credential = Import-Clixml -Path 'C:\scripts\pass.xml'
```

> [!note] Automatic Decryption
> When you Import-Clixml in the context of the user who encrypted it,
> PowerShell automatically decrypts using DPAPI

**Step 2: Extract Username**

```powershell
$credential.GetNetworkCredential().username
```

Returns: `bob`

**Step 3: Extract Password**

```powershell
$credential.GetNetworkCredential().password
```

Returns: `Str0ng3ncryptedP@ss!`



### Step 1: Identify Credential Sources

| Source                     | Location                                                | Method                     |
| -------------------------- | ------------------------------------------------------- | -------------------------- |
| **Configuration Files**    | App directories, C:\Windows\                            | findstr, grep, cat         |
| **Dictionary Files**       | User AppData                                            | Get-Content, Select-String |
| **Unattended Files**       | C:\Windows\Panther, C:\Windows\System32\sysprep         | Get-ChildItem, cat         |
| **PowerShell History**     | AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine | Get-Content, gc            |
| **PowerShell Credentials** | Various script directories                              | Import-Clixml              |

### Step 2: Search and Extract

```powershell
# Search for common credential files
findstr /SIM /C:"password" *.txt *.ini *.cfg *.config *.xml

# Search entire file system
Get-ChildItem -Path C:\ -Recurse -Filter "*.xml" -ErrorAction SilentlyContinue
Get-ChildItem -Path C:\ -Recurse -Filter "*password*" -ErrorAction SilentlyContinue
Get-ChildItem -Path C:\ -Recurse -Filter "*unattend*" -ErrorAction SilentlyContinue
```

### Step 3: Extract Sensitive Data

```powershell
# Read configuration files
Get-Content -Path "C:\path\to\config.xml"

# Read PowerShell history
(Get-PSReadLineOption).HistorySavePath | Get-Content

# Decrypt PowerShell credentials
Import-Clixml -Path "C:\path\to\credential.xml" | GetNetworkCredential()
```

### Step 4: Verify and Test Credentials

```powershell
# Test credentials with net use
net use \\server\share password /user:domain\username

# Test credentials with WinRM
$credential = New-Object System.Management.Automation.PSCredential("domain\username", (ConvertTo-SecureString "password" -AsPlainText -Force))
```
