# Attacking Domain Trusts - Cross-Forest Trust Abuse - from Linux

## Cross-Forest Kerberoasting

Same cross-forest Kerberoasting concept, performed with `GetUserSPNs.py` — need credentials for a user(INLANEFREIGHT.LOCAL) that can authenticate into the target domain, plus the `-target-domain` flag.

### Enumerate SPN Accounts
wley:transporter@4
```shellsession
s0nam@htb[/htb]$ GetUserSPNs.py -target-domain FREIGHTLOGISTICS.LOCAL INLANEFREIGHT.LOCAL/wley
```

Rerunning the command with the `-request` flag added gives us the TGS ticket.
Add `-outputfile <name>` to write straight to a file for Hashcat. Crack with mode **`13100`**, same as any standard Kerberoast.
## cracking password
```
hashcat -m 13100 sapsso_tgs /usr/share/wordlists/rockyou.txt
```
You can target a **single user** with `-request-user`


> [!tip] Chase password re-use further
> If this cracks and hands over `FREIGHTLOGISTICS.LOCAL`, worth checking:
> - Does this exact account also exist in your **current** domain? Test for password re-use — a quick win if privesc has otherwise stalled there.
> - Even with the current domain already controlled, flag password re-use across similarly-named accounts as a **report finding** regardless.
> - Consider a single, careful password spray using the cracked password — if the same admin team manages both domains, it may work for other service accounts too. Iterative testing, no stone unturned.

## Hunting Foreign Group Membership with BloodHound.py

Same concept as the Windows section — a user/admin from one domain sitting inside a group in another, most commonly via **Domain Local Groups** (the only group type allowing foreign-forest principals). From Linux, [BloodHound.py](https://github.com/fox-it/BloodHound.py) can collect across multiple domains for this.

> [!info] DNS setup may be required first
> `bloodhound-python` needs a DNS **hostname** for the target DC, not just an IP. If the attack host isn't already configured to use the internal domain's DNS (some client-provisioned VMs are, some aren't), edit `/etc/resolv.conf`.

### Point resolv.conf at INLANEFREIGHT.LOCAL

```shellsession
s0nam@htb[/htb]$ cat /etc/resolv.conf

# Dynamic resolv.conf(5) file for glibc resolver(3) generated by resolvconf(8)
#     DO NOT EDIT THIS FILE BY HAND -- YOUR CHANGES WILL BE OVERWRITTEN
# 127.0.0.53 is the systemd-resolved stub resolver.
# run "resolvectl status" to see details about the actual nameservers.
#nameserver 1.1.1.1
#nameserver 8.8.8.8
domain INLANEFREIGHT.LOCAL
nameserver 172.16.5.5
```

> [!tip] Note the different credential format
> `-u forend@inlanefreight.local` — using the UPN format here since `forend` authenticates against `FREIGHTLOGISTICS.LOCAL` using their **home domain's** credentials across the trust.

### Find Foreign Membership in BloodHound

Upload both datasets (each JSON, or the zipped sets) into the GUI. Under **Analysis**, run **Users with Foreign Domain Group Membership**, source domain = `INLANEFREIGHT.LOCAL`. Confirms the same finding as the Windows section: `INLANEFREIGHT.LOCAL`'s built-in Administrator is a member of `FREIGHTLOGISTICS.LOCAL`'s built-in Administrators group.

## Closing Thoughts on Trusts

Recap of what domain trusts enable for an attacker:
- Taking over a trusted domain and finding password re-use across privileged accounts ("end-around" access to the primary domain)
- Domain Admin in a **child** domain almost always means the **parent** domain can be compromised via the ExtraSids attack
- Kerberoasting and foreign group membership abuse work the same way across **forest** trusts as they do parent-child

---

## Key Takeaways

- [ ] `GetUserSPNs.py -target-domain <domain> <home-domain>/<user> -request [-outputfile <name>]` for cross-forest Kerberoasting from Linux
- [ ] Hashcat mode `13100` — same as any RC4 Kerberoast
- [ ] Successful cross-domain cracks are worth testing for password re-use back in the home domain too, and worth a careful single-password spray if the same admin team runs both domains
- [ ] `bloodhound-python` needs DNS hostname resolution for the target DC — edit `/etc/resolv.conf` per-domain if not already configured
- [ ] Collect against each domain separately (different `-d`, `-dc`, and sometimes credential-format via UPN), then upload combined into BloodHound
- [ ] "Users with Foreign Domain Group Membership" pre-built query surfaces cross-forest privilege leaks directly
