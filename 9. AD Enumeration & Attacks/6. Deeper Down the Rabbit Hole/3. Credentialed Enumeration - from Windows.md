# Credentialed Enumeration - from Windows

Windows-side tools for the same goal: misconfigurations and permission issues enabling lateral/vertical movement, domain trust mapping (inside and outside the forest), and pillaging shares for sensitive data.

> [!tip] Not everything is offensive
> Some findings here (e.g. unrestricted BloodHound collection, odd account attributes) are purely informational — still worth including in a report as medium-risk findings or an appendix, even if they don't directly advance an attack path.

## Shares

Overly permissive shares can accidentally expose sensitive data (medical, legal, HR, config files, SSH keys, hardcoded passwords). Even standard user access to IT/infra shares can lead to serious disclosure. Worth flagging for HIPAA/PCI-type compliance concerns too. PowerView can hunt shares manually — but this is tedious and error-prone at scale, which is where **Snaffler** comes in.

---

## Snaffler

Automates hunting for credentials/sensitive data across domain shares: gets a host list, enumerates shares/readable directories, iterates readable content, and flags files of interest. Source: [SnaffCon/Snaffler](https://github.com/SnaffCon/Snaffler). Requires running from a domain-joined host or domain-user context.

### Execution

```bash
Snaffler.exe -s -d inlanefreight.local -o snaffler.log -v data
```

| Flag | Meaning |
|---|---|
| `-s` | print results to console |
| `-d` | domain to search within |
| `-o` | write results to a logfile |
| `-v data` | verbosity level — `data` shows only results, easier to review than full verbosity |

> [!tip] Output to file, review later
> Snaffler produces a lot of data — best to let it run to a logfile and review afterward. Raw output can also be handed to clients as supplemental evidence to help them prioritize which shares to lock down first.

### Exploring the Data

Search `domain:` in the top-left search bar → select `INLANEFREIGHT.LOCAL`. This lab environment: 550+ hosts, trusts with two other domains.

**Useful pre-built queries in the Analysis tab:**

- **Find Computers with Unsupported Operating Systems** — surfaces legacy OS hosts (e.g. Windows 7, Server 2008) potentially vulnerable to old RCEs like [MS08-067](https://support.microsoft.com/en-us/topic/ms08-067-vulnerability-in-server-service-could-allow-remote-code-execution-ac7878fc-be69-7143-472d-2507a179cd15).
  > [!warning] Validate before acting
  > Some records may be stale/powered-off hosts still lingering in AD. Confirm a host is actually "live" before recommending action. Report this as either a high-risk **Legacy Operating Systems** finding, or a best-practice note about cleaning up stale AD records — depending on what you find.

- **Find Computers where Domain Users are Local Admin** — flags hosts where an entire broad group (e.g. `Domain Users`) has local admin rights, often from convenience/oversight rather than deliberate design. If found, **any** account you control can typically access those hosts and potentially pull credentials from memory.

> [!tip] Deeper study
> For a dedicated walkthrough, see the [Active Directory BloodHound](https://academy.hackthebox.com/course/preview/active-directory-bloodhound) module.  [custom Cypher queries](https://hausec.com/2019/09/09/bloodhound-cypher-cheatsheet/) go in the Raw Query box at the bottom of the screen.

> [!warning] Document your footprint
> Log every file transferred to/from hosts and where it landed on disk — needed for deconfliction with the client if something looks suspicious. Depending on scope, clean up anything placed in the environment at the end of the engagement.

## Key Takeaways

- [ ] `Get-ADDomain`, `Get-ADUser -Filter {ServicePrincipalName -ne "$null"}`, `Get-ADTrust -Filter *`, `Get-ADGroup`/`Get-ADGroupMember` — all built-in, no extra tooling needed, more likely to blend in
- [ ] PowerView: `Get-DomainUser`, `Get-DomainGroupMember -Recurse` (nested membership!), `Get-DomainTrustMapping`, `Test-AdminAccess`, `Get-DomainUser -SPN` for Kerberoastable accounts
- [ ] SharpView = .NET PowerView port, useful when PowerShell itself is restricted/monitored
- [ ] Snaffler automates share-hunting for credential-shaped files at scale — far more efficient than manual PowerView share digging
- [ ] SharpHound `-c All --zipfilename <name>` → upload to BloodHound GUI (`neo4j` / `HTB_@cademy_stdnt!` default creds)
- [ ] Validate "unsupported OS" BloodHound findings are actually live before reporting them as high-risk
- [ ] "Domain Users = local admin" findings mean literally any controlled account can access those hosts
- [ ] Always log file transfers to/from hosts for deconfliction and cleanup purposes
