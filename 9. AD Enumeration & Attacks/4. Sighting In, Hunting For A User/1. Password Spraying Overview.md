# Password Spraying Overview

Password spraying can gain access to systems and provide a foothold on a target network. The attack: try **one common password** against a **long list of usernames/emails** on an exposed service. Those usernames typically come from OSINT recon or initial domain enumeration.

> [!tip] Pentesting isn't linear
> A real assessment iterates across multiple techniques at once. While a poisoning attack (Responder/Inveigh) runs in the background, you can simultaneously work on building a password spray target list — using time efficiently matters since assessments are time-boxed.

---

## Story Time — Real-World Examples

Both scenarios below are from **non-evasive grey-box** assessments: internal network access via a Linux VM, plus a list of in-scope IP ranges — nothing else provided.

### Scenario 1 — Standard Username List + Kerbrute

No SMB NULL session or LDAP anonymous bind was available to pull a user list directly. Instead:

1. Used **Kerbrute** to enumerate valid domain users (technique covered in a later section)
2. Built the target list by combining the `jsmith.txt` list from the [statistically-likely-usernames](https://github.com/insidetrust/statistically-likely-usernames) GitHub repo with usernames scraped from LinkedIn
3. Password sprayed the combined list with the common password `Welcome1`
4. Got **two hits** on low-privileged accounts — enough to run **BloodHound** and eventually find an attack path to full domain compromise

### Scenario 2 — Predictable Username Format Discovered via PDF Metadata

Standard username lists and LinkedIn scraping produced no results. Pivoted to Google, searching for PDFs published by the organization:

- Checked document properties (metadata) of several PDFs
- Found the internal username format in the **Author field**: `F9L8`-style — 4-character random GUIDs using capital letters and digits (A-Z, 0-9)

> [!warning] Metadata leaks matter
> Strong example of why scrubbing document metadata before publishing online is important — the author field alone exposed the entire internal username scheme.

Since the format was fully known, a short script could brute-force generate every possible combination:

```bash
#!/bin/bash

for x in {{A..Z},{0..9}}{{A..Z},{0..9}}{{A..Z},{0..9}}{{A..Z},{0..9}}
    do echo $x;
done
```

This generates **1,679,616** possible 4-character username combinations (36⁴).

**Result:** fed this full list into Kerbrute to enumerate every single valid account in the domain. Normally a list like `jsmith.txt` only identifies **40–60%** of valid accounts — here, the predictable GUID format plus the leaked metadata allowed enumeration of essentially **100%** of accounts, massively improving the odds of a successful spray. From valid passwords obtained this way, a complex attack chain involving **Resource-Based Constrained Delegation (RBCD)** and the **Shadow Credentials** attack ultimately led to full domain compromise.

## Password Spraying Considerations

> [!danger] Careless spraying causes real harm
> Locking out hundreds of production accounts is a serious, realistic risk if this isn't done carefully.

### Spraying vs. Brute Forcing

| Attack Type        | Approach                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| **Brute force**    | Many passwords tried against **one** account                                                         |
| **Password spray** | **One** common password tried across **many** accounts, with a delay before trying the next password |

### Visualizing a Spray

| Attack  | Username                      | Password     |
| ------- | ----------------------------- | ------------ |
| 1       | bob.smith@inlanefreight.local | `Welcome1`   |
| 1       | john.doe@inlanefreight.local  | `Welcome1`   |
| 1       | jane.doe@inlanefreight.local  | `Welcome1`   |
| *DELAY* |                               |              |
| 2       | bob.smith@inlanefreight.local | `Passw0rd`   |
| 2       | john.doe@inlanefreight.local  | `Passw0rd`   |
| 2       | jane.doe@inlanefreight.local  | `Passw0rd`   |
| *DELAY* |                               |              |
| 3       | bob.smith@inlanefreight.local | `Winter2022` |
| 3       | john.doe@inlanefreight.local  | `Winter2022` |
| 3       | jane.doe@inlanefreight.local  | `Winter2022` |

Fewer login attempts per username than brute forcing → much lower lockout risk, but **not zero risk**. A delay between rounds is essential.

### Account Lockout Policy

- Internal spraying (for lateral movement) carries the same lockout considerations — but with internal access, it's often possible to pull the actual domain password policy, which significantly reduces risk (covered practically in the next section)
- Common real-world policy: **5 bad attempts** before lockout, **30-minute** auto-unlock
- Some orgs configure longer lockout windows or require **manual admin unlock**

> [!tip] Practical guidance
> - **Best**: obtain the actual password policy before spraying (internal access often allows this)
> - **If unknown**: wait a few hours between spray attempts — long enough for most lockout thresholds to reset
> - **If all else fails**: a single "hail mary" spray attempt with one weak/common password, only after other foothold options are exhausted
> - **Client-facing option**: simply ask the client to clarify their password policy up front

## Key Takeaways

- [ ] Password spraying = one common password across many usernames, not many passwords against one account
- [ ] Username lists come from OSINT (LinkedIn, PDFs/metadata), Kerbrute enumeration, or combinations of both
- [ ] **Scrub document metadata** before publishing — author fields have leaked entire internal username schemes in the wild
- [ ] Always throttle attempts with a delay between password rounds to avoid lockouts
- [ ] Getting the real password lockout policy first (internal access) is much safer than guessing
- [ ] Typical policy: 5 bad attempts / 30-min auto-unlock — but this varies by org
- [ ] Password spraying often provides just enough low-privilege access to kick off BloodHound-driven attack path discovery
