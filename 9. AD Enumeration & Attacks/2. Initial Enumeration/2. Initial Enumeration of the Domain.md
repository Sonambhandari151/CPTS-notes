# Initial Enumeration of the Domain

> [!info] Scenario
> External recon is done. We're now placed **inside** the client's network on an attack host, starting the internal AD-focused pentest against `Inlanefreight`. No credentials yet.

---

## Setting Up — How Internal Access Is Usually Granted

| Setup | What it means |
|---|---|
| Pentest VM inside their network | SSH in over VPN via a jump host |
| Physical box plugged into an ethernet port | Calls back to us over VPN, SSH in |
| Physical presence on-site | Laptop plugged directly into their network |
| Cloud VM (Azure/AWS) inside their network | SSH via public key, our IP whitelisted |
| Plain VPN into their network | Limiting — some attacks (LLMNR/NBT-NS poisoning) won't work |
| Corporate laptop connected to client VPN | — |
| Managed Windows workstation on-site | Sometimes locked down, sometimes full internet + local admin + AV in monitor mode |
| VDI (Citrix, etc.) | Same idea as managed workstation, accessed remotely |

**Test style options client picks from:**
- **Grey box** — given partial info (e.g. IP/CIDR ranges)
- **Black box** — nothing given, discover everything blindly
- **Evasive / Non-evasive / Hybrid evasive** — start quiet and escalate to see detection threshold, or just go loud from the start
- **Starting point** — no credentials, or starting as a standard domain user

### Inlanefreight's Chosen Approach
- Custom pentest VM inside their network → SSH via jump host
- A Windows attack host also provided for tool staging
- Start **unauthenticated**, but a standard domain user account (`htb-student`) is available to log into the Windows attack host
- **Grey box**: given network range `172.16.5.0/23`, nothing else
- **Non-evasive** testing
- No credentials or network map provided up front

> [!tip] Why start with zero credentials?
> Mirrors what a real attacker could achieve via phishing, physical access, rogue wireless touching the AD environment, or a rogue employee. Good results here often lead the client to hand over creds/host access to speed up the rest of the engagement.

---

## Tasks For This Phase

1. Enumerate the internal network — hosts, critical services, foothold avenues
2. Use active **and** passive techniques to identify users, hosts, vulnerabilities
3. **Document everything** — save scan/tool output to files as you go. Critical for later phases and the final report.

### Key Data Points to Track

| Data Point | Description |
|---|---|
| `AD Users` | Valid user accounts to target for password spraying |
| `AD Joined Computers` | Domain Controllers, file/SQL/web/Exchange/database servers |
| `Key Services` | Kerberos, NetBIOS, LDAP, DNS |
| `Vulnerable Hosts and Services` | Anything that could be an easy foothold |

---

## Methodology (TTPs)

AD has a huge amount of data — approach it in stages or you'll miss things:

1. **Passive identification** of hosts on the network (just listen)
2. **Active validation** — confirm what's alive, then dig into services/names/vulns per host
3. **Probe** interesting hosts for data
4. **Regroup** — review findings, aim for a foothold (creds, or a shell on a domain-joined host) to move into credentialed enumeration

---

## Stage 1: Passive Host Identification

The idea: before sending any traffic yourself, just **listen**. Hosts constantly broadcast ARP requests, MDNS queries, and other Layer 2 traffic — you can learn IPs and hostnames for free.

### Wireshark

 Spawn the target, connect to the Linux attack host using `xfreerdp` and fire up Wireshark to begin capturing traffic.
```shellsession
xfreerdp3 /v:10.129.51.21 /u:htb-student /p:HTB_@cademy_stdnt!
```
**Connect and start capturing:**
```shellsession
┌─[htb-student@ea-attack01]─[~]
└──╼ $sudo -E wireshark

11:28:20.487     Main Warn QStandardPaths: runtime directory '/run/user/1001' is not owned by UID 0, but a directory permissions 0700 owned by UID 1001 GID 1002
<SNIP>
```

![[Pasted image 20260721110852.png]]
**What we observed:**
- **ARP requests/replies** — VMware-sourced hosts broadcasting, querying IPs in the `172.16.5.x` range → revealed hosts `172.16.5.5`, `172.16.5.25`, `172.16.5.50`, `172.16.5.100`, `172.16.5.125`

![[Pasted image 20260721111012.png]]
- **MDNS query** from `172.16.5.125` to `224.0.0.251` for `AAAA ACADEMY-EA-WEB01.local` → revealed host `ACADEMY-EA-WEB01`

On a non-GUI host, use  [tcpdump](https://linux.die.net/man/8/tcpdump), [net-creds](https://github.com/DanMcInerney/net-creds), and [NetMiner](https://www.netminer.com/en/product/netminer.php), etc., instead — same purpose.

```shellsession
s0nam@htb[/htb]$ sudo tcpdump -i ens224
```

You can also capture with `tcpdump` and save to a `.pcap`, then transfer it to another host and open in Wireshark elsewhere.


> [!tip] Save every capture
> Review PCAPs later for hints you missed, and they're great supporting evidence in the final report. Windows equivalent: `pktmon.exe` (built into Windows 10+).

### Responder — Analyze Mode

[Responder](https://github.com/lgandx/Responder) is built to listen, analyze, and poison LLMNR/NBT-NS/MDNS traffic. Right now we only use its passive **Analyze mode** — no poisoned packets are sent (active poisoning is covered later in the module).

```bash
sudo responder -I ens224 -A
```

Reveals additional unique hosts not seen in the Wireshark capture. Add these to the growing target list.

```shellsession
       15.366 sec (elapsed real time)
```

| Flag | Meaning |
|---|---|
| `-a` | show only targets that are alive |
| `-s` | print stats at the end of the scan |
| `-g` | generate the target list from the given CIDR |
| `-q` | quiet — no per-target line output, just the summary |

**Why fping over plain `ping`:** fping issues ICMP against a whole list of hosts in round-robin fashion instead of waiting on each host sequentially — much faster at scale.

**Result:** 9 live hosts (including our own attack host) out of 510 addresses checked.

> [!note] ICMP alone isn't complete
> Some hosts block ping but still run services. Open ports found in later scanning may reveal more hosts than ICMP alone did. Lab results will vary in size from this example — still worth reproducing and logging every live host found.

## Stage 3: Active Service Enumeration (Nmap)

Enumerate the confirmed hosts in depth: what services are running, which are Domain Controllers/critical servers, which look vulnerable. Focus especially on AD-adjacent protocols: **DNS, SMB, LDAP, Kerberos**.

```bash
sudo nmap -v -A -iL hosts.txt -oN /home/htb-student/Documents/host-enum
```

| Flag | Meaning |
|---|---|
| `-v` | verbose |
| `-A` | aggressive — OS detection, version detection, script scanning, traceroute together; quickly enumerates well-known ports (web, domain services, etc.) |
| `-iL hosts.txt` | read targets from file (IPs found via Responder/fping — overlapping hostnames were simplified to just IPs here) |
| `-oN <path>` | save normal-format output |

> [!tip] Best practice: use `-oA` instead of `-oN`
> Saves output in all formats (normal, XML, grepable) at once for reporting and feeding into other tools.

## Stage 4: Finding Valid Usernames (Kerbrute)

We still need an actual foothold: clear-text creds, an NTLM hash, a SYSTEM shell on a domain-joined host, or a shell as a domain user. Obtaining even a low-privilege valid user opens up major opportunities.

[Kerbrute](https://github.com/ropnop/kerbrute) exploits Kerberos pre-authentication: attempting pre-auth for a username reveals whether that username exists, and failed Kerberos pre-auth typically **doesn't trigger the same logs/alerts** as a failed Windows logon — making it a relatively stealthy option.

> [!warning] Still risks lockouts
> A failed Kerberos pre-auth attempt still counts as a failed login for that account and **can lock it out**. Be mindful of the client's account lockout policy before running large wordlists.

Wordlists commonly used: `jsmith.txt` / `jsmith2.txt` from the [Insidetrust statistically-likely-usernames](https://github.com/insidetrust/statistically-likely-usernames) repo — contains many username permutation lists useful for unauthenticated enumeration.

## Alternative Foothold Path: SYSTEM-Level Access

`NT AUTHORITY\SYSTEM` is a built-in Windows account with the highest privilege level in the OS, used to run most Windows services (and often third-party services too by default). On a **domain-joined host**, SYSTEM can enumerate AD by impersonating the computer account (computer accounts are AD objects just like user accounts) — this makes SYSTEM access nearly equivalent to having a domain user account.

**Ways to gain SYSTEM-level access:**
- Remote Windows exploits — **MS08-067**, **EternalBlue**, **BlueKeep**
- Abusing a service running as SYSTEM, or abusing `SeImpersonate` privileges with tools like  [Juicy Potato](https://github.com/ohpe/juicy-potato) (works on older Windows OS, not always possible on Server 2019)
- Local privilege escalation flaws (e.g. the Windows 10 Task Scheduler 0-day)
-  Gaining admin access on a domain-joined host with a local account and using Psexec to launch a SYSTEM cmd window.

**What SYSTEM-level access on a domain-joined host enables:**
- Enumerate the domain with built-in tools or offensive tools like **BloodHound** and **PowerView**
- Perform **Kerberoasting / ASREPRoasting** attacks within the domain
- Run tools like **Inveigh** to capture Net-NTLMv2 hashes or perform SMB relay attacks
- Token impersonation to hijack a privileged domain user account
- Carry out **ACL attacks**

## A Word of Caution

> [!warning] Match tooling/noise to engagement style
> - **Non-evasive** test, client staff aware → noise generally doesn't matter
> - **Evasive / adversarial assessment / red team** engagement → mimicking a real attacker means stealth matters. Throwing Nmap at an entire network isn't quiet, and many common pentest tools will trigger alarms for an educated, prepared SOC/blue team.
>
> Always clarify the goal and constraints of the assessment with the client **in writing** before it begins.

## Key Takeaways

- [ ] Start passive (Wireshark/tcpdump, Responder analyze mode) before sending any active traffic
- [ ] `fping -asgq <range>` for a fast live-host sweep across a large CIDR
- [ ] `nmap -A -iL hosts.txt -oA <path>` for deep service enumeration; watch for clustered Kerberos/LDAP/DNS/SMB ports = Domain Controller
- [ ] Old OS hosts (2008 R2, Windows 7/8) = potential quick wins via EternalBlue/MS08-067 — get written approval before exploiting
- [ ] `kerbrute userenum -d <domain> --dc <IP> <wordlist> -o <outfile>` = fast, relatively stealthy AD username enumeration — mind lockout policy
- [ ] SYSTEM access on any domain-joined host ≈ having a domain user account for AD enumeration purposes
- [ ] Always confirm noise level and exploitation approval with the client, in writing
- [ ] Goal of this whole phase: land a valid username/credential or a SYSTEM shell to unlock credentialed enumeration next
