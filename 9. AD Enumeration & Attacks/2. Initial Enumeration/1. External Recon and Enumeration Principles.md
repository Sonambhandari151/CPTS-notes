# External Recon and Enumeration Principles

> [!info] Why External Recon?
> Performed **before** any active pentest work. Helps to:
> - Validate scoping document info from client
> - Ensure actions stay in scope (remote work)
> - Find publicly accessible info affecting test outcome (e.g. leaked creds)

Goal: get the **lay of the land** — identify info leaks/breach data. Can be as simple as a username format from a website, or as deep as scanning GitHub for leaked credentials.

---

## What Are We Looking For?

| Data Point           | Description                                                                                                             |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `IP Space`           | ASN, netblocks, cloud presence/hosting providers, DNS records                                                           |
| `Domain Information` | Domain admin, subdomains, public-facing services (mail, DNS, web, VPN), visible defenses (SIEM, AV, IPS/IDS)            |
| `Schema Format`      | Org email accounts, AD usernames, password policies → build username lists for spraying/stuffing/brute force            |
| `Data Disclosures`   | Public files (.pdf, .ppt, .docx, .xlsx) revealing intranet sites, user metadata, shares, leaked creds in repos/metadata |
| `Breach Data`        | Publicly released usernames/passwords useful for initial foothold                                                       |

---

## Where Are We Looking?

| Resource                         | Examples                                                                                                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ASN / IP registrars`            | [IANA](https://www.iana.org/), [ARIN](https://www.arin.net/) (Americas), [RIPE](https://www.ripe.net/) (Europe), [BGP Toolkit](https://bgp.he.net/)                                  |
| `Domain Registrars & DNS`        | [Domaintools](https://www.domaintools.com/), [PTRArchive](http://ptrarchive.com/), [ICANN Lookup](https://lookup.icann.org/lookup), manual DNS queries (e.g. against `8.8.8.8`)      |
| `Social Media`                   | LinkedIn, Twitter, Facebook, regional platforms, news articles                                                                                                                       |
| `Public-Facing Company Websites` | News, embedded docs, "About Us" / "Contact Us" pages                                                                                                                                 |
| `Cloud & Dev Storage Spaces`     | [GitHub](https://github.com/), [Grayhat Warfare](https://grayhatwarfare.com/) (S3/Azure Blob), [Google Hacking Database (Dorks)](https://www.exploit-db.com/google-hacking-database) |
| `Breach Data Sources`            | [HaveIBeenPwned](https://haveibeenpwned.com/), [Dehashed](https://www.dehashed.com/) (cleartext creds/hashes → test against Citrix, RDS, OWA, O365, VPN, VMware Horizon, etc.)       |

### Finding Address Spaces

[BGP Toolkit (Hurricane Electric)](http://he.net/) — search a domain/IP to find assigned address blocks and ASN.

> [!warning] Scope Awareness
> Smaller orgs often host infra on shared third-party space (Cloudflare, AWS, Azure, GCP). Test agreement is with the **client only**, not the hosting provider or other tenants. Confirm self-hosted vs. third-party infra during scoping.
>
> - [AWS pentest guidelines](https://aws.amazon.com/security/penetration-testing/) — some services don't require prior approval
> - Oracle requires a [Cloud Security Testing Notification](https://docs.oracle.com/en-us/iaas/Content/Security/Concepts/security_testing-policy_notification.htm)
> - When in doubt → escalate before attacking any external-facing service

---

### DNS

Validates scope, finds undisclosed reachable hosts.

- [Domaintools Whois](https://whois.domaintools.com/)
- [ViewDNS.info](https://viewdns.info/) — reverse IP/whois lookup, IP history, DNS report, reverse MX/NS lookup, DNSSEC testing, firewall/censorship tests

May reveal out-of-scope hosts (bring to client to confirm) or in-scope subdomains not listed in the SOW.

---

### Public Data

**Job Postings** (LinkedIn, Indeed, Glassdoor) can reveal:
- Tech stack maturity (e.g. SharePoint 2013 + 2016 → possible in-place upgrade → legacy vulns)
- Security program details, backup/DR practices

**Company Websites**: contact emails, phone numbers, org charts, published documents — often link to intranet/internal infrastructure.

**Leaked Dev Data**: credentials hardcoded and pushed to public repos.

Tools:
- [Trufflehog](https://github.com/trufflesecurity/truffleHog) — scans repos for secrets
- [Grayhat Warfare](https://buckets.grayhatwarfare.com/) — exposed cloud storage buckets

## Overarching Enumeration Principles

- Enumeration is **iterative** — repeated throughout the pentest
- Order: `passive` (wide → narrow) first, then move into `active` enumeration once passive is exhausted
- Primary sources: scoping document + your own passive/active findings

## Example Enumeration Process — `inlanefreight.com`

### 1. ASN / IP & Domain Data (BGP.he.net)

- IP Address: `134.209.24.248`
- Mail Server: `mail1.inlanefreight.com`
- Nameservers: `NS1.inlanefreight.com`, `NS2.inlanefreight.com`
![[Pasted image 20260719180821.png]]

> Small org → no dedicated ASN, as expected.

### 2. Validate with ViewDNS (Reverse IP)

Confirms IP matches; also surfaced a second domain sharing the IP (`lycjg.us`).
![[Pasted image 20260719180839.png]]

### 3. Validate Nameservers via `nslookup`

```shellsession
s0nam@htb[/htb]$ nslookup ns1.inlanefreight.com
Server:     192.168.186.1
Address:    192.168.186.1#53

Non-authoritative answer:
Name:   ns1.inlanefreight.com
Address: 178.128.39.165

nslookup ns2.inlanefreight.com
Server:     192.168.86.1
Address:    192.168.86.1#53

Non-authoritative answer:
Name:   ns2.inlanefreight.com
Address: 206.189.119.186
```

→ Two new IPs to validate against scope before any active testing (passive browsing OK; scanning requires in-scope confirmation).

### 4. Social Media

Fictitious company for the module — in a real engagement, check LinkedIn/Twitter/Instagram/Facebook here.

### 5. Google Dork — Files

```
filetype:pdf inurl:inlanefreight.com
```

→ Found: "corporate goals and strategy" PDF. Always save a local copy + note source URL.

### 6. Google Dork — Email Addresses

```
intext:"@inlanefreight.com" inurl:inlanefreight.com
```

→ [Contact page](https://www.inlanefreight.com/index.php/contact/) revealed staff emails across global offices.

![[Pasted image 20260719181051.png]]

**Naming convention discovered:** `first.last`

### 7. Username Harvesting

[linkedin2username](https://github.com/initstring/linkedin2username) — scrapes LinkedIn to generate username permutations (`flast`, `first.last`, `f.last`, etc.) for password spraying.

### 8. Credential Hunting — Dehashed

```shellsession
s0nam@htb[/htb]$ sudo python3 dehashed.py -q inlanefreight.local -p
id             :  5996447501
email          :  roger.grimes@inlanefreight.local
username       :  rgrimes
password       :  Ilovefishing!
name           :  Roger Grimes
database_name  :  ModBSolutions

id             :  7344467234
email          :  jane.yu@inlanefreight.local
username       :  jyu
password       :  Starlight1982_!
name           :  Jane Yu
database_name  :  MyFitnessPal
<SNIP>
```

> [!note] Script Source
> [dehashed.py (mrb3n813)](https://github.com/mrb3n813/Pentest-stuff/blob/master/dehashed.py) or alt: [Dehashed (sm00v)](https://github.com/sm00v/Dehashed) — API structure may have changed; review before use.

Most breach passwords won't work directly on AD, but occasional hits provide a foothold. Even failed hits are useful for building a targeted wordlist for internal password spraying.

---

## Key Takeaways

- [ ] Confirm scope (ASN/IP/subdomains) before any active interaction
- [ ] Google dorks (`filetype:`, `intext:`, `inurl:`) are fast wins for files/emails
- [ ] Establish org's username naming convention early
- [ ] Combine OSINT + breach data → build a targeted wordlist for internal password spraying
- [ ] The majority of internal AD enumeration/attacks only require **low-privilege domain credentials**
