# Kerberos "Double Hop" Problem

The "Double Hop" problem arises when using Kerberos authentication across **two or more hops**. Kerberos tickets aren't like passwords — they're signed data from the KDC stating what resources an account can access. Authenticating via Kerberos gets you a ticket for a **specific resource** (e.g. one machine). Authenticating via a password, by contrast, caches the NTLM hash in your session, which **can** be reused elsewhere.

---

## Background

Commonly hit when using **WinRM/PowerShell**, since its default auth mechanism only provides a ticket for the specific resource connected to. This breaks lateral movement or file-share access attempted from that remote shell — the account *has* the rights, but access still gets denied.

> [!info] Why PSExec-style access doesn't have this problem
> Initial auth over SMB or LDAP (e.g. via PSExec or exploiting an app) stores the user's **NTLM hash** in memory — reusable for subsequent resource access. WinRM's Kerberos-based auth **never caches the password**, so there's nothing to reuse.

### Visualizing the Attack Path

```
Attack Host (not domain-joined) --WinRM--> DEV01 (First Hop) --???--> DC01 (Second Hop)
```

Scenario: attack host is a Parrot box on the corporate network, not domain-joined. A domain user's creds are obtained, and that user is in `Remote Management Users` on DEV01. Goal: use **PowerView** from DEV01 to query the DC — the **second hop**.

**Root cause:** connecting to DEV01 via `evil-winrm` uses **network authentication** — credentials never land in memory. Loading PowerView and querying AD sends a request to the DC, but Kerberos has no TGT to attach — only the **TGS** for DEV01 was delivered, not the **TGT**. Without the TGT, the second-hop resource (the DC) can't validate the request, and access is denied.

> [!tip] Unconstrained delegation sidesteps this entirely
> If unconstrained delegation is enabled on the intermediate server, the user's **TGT** gets forwarded along with their TGS when they connect. The server can then cache that TGT and request further TGS tickets on the user's behalf for subsequent hops. Generally, landing on a host with unconstrained delegation means this problem is already moot — you've likely got bigger wins available.

## Workarounds

Covered in [this post](https://posts.slayerlabs.com/double-hop/). Two methods below: one for `evil-winrm` sessions, one for GUI-based Windows access.

---

## Workaround #1: PSCredential Object

### The Problem

```shellsession
*Evil-WinRM* PS C:\Users\backupadm\Documents> import-module .\PowerView.ps1
*Evil-WinRM* PS C:\Users\backupadm\Documents> get-domainuser -spn
Exception calling "FindAll" with "0" argument(s): "An operations error occurred. "
```

```shellsession
*Evil-WinRM* PS C:\Users\backupadm\Documents> klist

Current LogonId is 0:0x57f8a
Cached Tickets: (1)

#0>     Client: backupadm @ INLANEFREIGHT.LOCAL
        Server: academy-aen-ms0$ @
        KerbTicket Encryption Type: AES-256-CTS-HMAC-SHA1-96
        Ticket Flags 0xa10000 -> renewable pre_authent name_canonicalize
        Cache Flags: 0x4 -> S4U
        Kdc Called: DC01.INLANEFREIGHT.LOCAL
```

Only one cached ticket — for the **current server**, nothing for the DC.

### The Fix — Pass Credentials Explicitly

```shellsession
*Evil-WinRM* PS C:\Users\backupadm\Documents> $SecPassword = ConvertTo-SecureString '!qazXSW@' -AsPlainText -Force
*Evil-WinRM* PS C:\Users\backupadm\Documents> $Cred = New-Object System.Management.Automation.PSCredential('INLANEFREIGHT\backupadm', $SecPassword)
```

```shellsession
*Evil-WinRM* PS C:\Users\backupadm\Documents> get-domainuser -spn -credential $Cred | select samaccountname

samaccountname
--------------
azureconnect
backupjob
krbtgt
mssqlsvc
sqltest
sqlqa
sqldev
mssqladm
svc_sql
sqlprod
sapsso
sapvc
vmwarescvc
```

**Success** — because credentials were explicitly attached to the request. Omitting `-credential` reproduces the original error.

> [!tip] GUI/RDP access sidesteps this automatically
> If RDP'd into the same host directly (instead of WinRM), `klist` shows **all** necessary cached tickets, including for the DC — the password is genuinely stored in memory in that session, so it's sent along with every request.

## Workaround #2: Register PSSession Configuration

For scenarios where PSCredential objects aren't practical (some tools won't accept a `-Credential` parameter) — e.g. connecting from a domain-joined host or a Windows attack host using `Enter-PSSession`.

### Reproduce the Problem

```powershell
PS C:\htb> Enter-PSSession -ComputerName ACADEMY-AEN-DEV01.INLANEFREIGHT.LOCAL -Credential inlanefreight\backupadm
```

```powershell
[ACADEMY-AEN-DEV01.INLANEFREIGHT.LOCAL]: PS C:\Users\backupadm\Documents> klist

Current LogonId is 0:0x11e387
Cached Tickets: (1)

#0>     Client: backupadm @ INLANEFREIGHT.LOCAL
        Server: HTTP/ACADEMY-AEN-DEV01.INLANEFREIGHT.LOCAL @ INLANEFREIGHT.LOCAL
```

> [!info] Why only an HTTP ticket
> WinRM uses SOAP (XML over HTTP) — so the cached ticket is scoped to the HTTP service on the target, matching expectations.

```powershell
[ACADEMY-AEN-DEV01.INLANEFREIGHT.LOCAL]: PS C:\Users\backupadm\Documents> Import-Module .\PowerView.ps1
[ACADEMY-AEN-DEV01.INLANEFREIGHT.LOCAL]: PS C:\Users\backupadm\Documents> get-domainuser -spn | select samaccountname
Exception calling "FindAll" with "0" argument(s): "An operations error occurred. "
```

### The Fix — Register a New Session Configuration

```powershell
PS C:\htb> Register-PSSessionConfiguration -Name backupadmsess -RunAsCredential inlanefreight\backupadm

WARNING: When RunAs is enabled in a Windows PowerShell session configuration, the Windows security model cannot enforce a security boundary between different user sessions that are created by using this endpoint. Verify that the Windows PowerShell runspace configuration is restricted to only the necessary set of cmdlets and capabilities.
WARNING: Register-PSSessionConfiguration may need to restart the WinRM service if a configuration using this name has recently been unregistered, certain system data structures may still be cached. In that case, a restart of WinRM may be required. All WinRM sessions connected to Windows PowerShell session configurations, such as Microsoft.PowerShell and session configurations that are created with the Register-PSSessionConfiguration cmdlet, are disconnected.

   WSManConfig: Microsoft.WSMan.Management\WSMan::localhost\Plugin

Type            Keys                                Name
----            ----                                ----
Container       {Name=backupadmsess}                backupadmsess
```

Then restart WinRM (kicks you out of the current session):
```powershell
Restart-Service WinRM
```

Reconnect using the named configuration:
```powershell
PS C:\htb> Enter-PSSession -ComputerName DEV01 -Credential INLANEFREIGHT\backupadm -ConfigurationName backupadmsess
```

```powershell
[DEV01]: PS C:\Users\backupadm\Documents> klist

Current LogonId is 0:0x2239ba
Cached Tickets: (1)

#0>     Client: backupadm @ INLANEFREIGHT.LOCAL
        Server: krbtgt/INLANEFREIGHT.LOCAL @ INLANEFREIGHT.LOCAL
        Cache Flags: 0x1 -> PRIMARY
        Kdc Called: DC01
```

Now a **krbtgt** ticket is cached — problem solved:

```powershell
[DEV01]: PS C:\Users\Public> get-domainuser -spn | select samaccountname

samaccountname
--------------
azureconnect
backupjob
krbtgt
mssqlsvc
<SNIP>
```

> [!info] Why this works
> The local machine now **impersonates** the remote machine in the `backupadm` context — all requests get routed directly to the DC as that user, without needing a PSCredential object each time.

> [!warning] Limitations of this method
> - Doesn't work from an `evil-winrm` shell — no way to get the credentials popup for `RunAsCredential`
> - Passing `-RunAsCredential $Cred` after building a PSCredential object still fails — `RunAs` requires an **elevated** PowerShell terminal
> - Doesn't work from Linux (Parrot/Ubuntu) PowerShell due to Kerberos credential handling limitations
> - Works best when testing from a **Windows attack host** with creds, or after RDP'ing into a compromised host to use as a jump host

Other unlisted methods exist too: **CredSSP**, **port forwarding**, or injecting into a process running as the target user (a "sacrificial process").

---

## Wrap Up

The Double Hop problem shows up often when working with WinRM in AD — understanding it (and having these workarounds ready) avoids wasted time on assessments.

---

## Key Takeaways

- [ ] Kerberos tickets are scoped to a resource; passwords (NTLM hash) are cached and reusable across hops — this is the root cause of the problem
- [ ] WinRM's default auth caches no password → only a TGS for the immediate host, no TGT to forward
- [ ] `klist` reveals exactly which tickets are cached — diagnostic tool #1
- [ ] Workaround #1 (evil-winrm): build a `PSCredential` object and pass `-credential $Cred` explicitly on each command
- [ ] Workaround #2 (GUI/Windows attack host): `Register-PSSessionConfiguration -RunAsCredential <user>` + restart WinRM + reconnect with `-ConfigurationName`
- [ ] Unconstrained delegation on the intermediate host eliminates this problem entirely (but usually means bigger wins already exist)
- [ ] Workaround #2 doesn't work from evil-winrm or Linux PowerShell — GUI/Windows-native access required
