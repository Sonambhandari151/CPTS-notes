# DCSync

Following the ACL abuse chain, we now control `adunn`, who has DCSync privileges in `INLANEFREIGHT.LOCAL`. This section digs into the attack itself, from both Linux and Windows.

## What is DCSync and How Does It Work?

> [!info] Core mechanism
> DCSync steals the AD password database by abusing the built-in **Directory Replication Service Remote Protocol**, normally used by Domain Controllers to replicate domain data. It lets an attacker **mimic a Domain Controller** to retrieve user NTLM password hashes.

The attack hinges on requesting a DC to replicate passwords via the **`DS-Replication-Get-Changes-All`** extended right — an extended access control right in AD allowing replication of secret data.

> [!important] Requirement
> Control over an account with **Replicating Directory Changes** and **Replicating Directory Changes All** permissions. Domain/Enterprise Admins and default domain administrators have this by default.

> [!info] Flag meanings
> - `-just-dc` — extract NTLM hashes and Kerberos keys from the NTDS file
> - `-just-dc-ntlm` — NTLM hashes only
> - `-just-dc-user <USERNAME>` — only extract data for a specific user
> - `-pwd-last-set` — shows when each account's password was last changed
> - `-history` — dumps password history (useful for cracking / password-strength metrics)
> - `-user-status` — flags whether an account is disabled — useful for filtering disabled accounts out of client-facing cracking statistics

> [!tip] Client-facing reporting metrics
> Combine `-user-status` with cracked-hash data to report only against **active** accounts: number/% of passwords cracked, top 10 passwords, password length metrics, password reuse.

`-just-dc` types :
1. Containing `NTLM` hashes.
2. Containinf `Kerberos keys`
3. Contain `cleartext passwords` from NTDS for any  accounts set with [reversible encryption](https://docs.microsoft.com/en-us/windows/security/threat-protection/security-policy-settings/store-passwords-using-reversible-encryption) enabled.

## Reversible Encryption Accounts

> [!info] What "Store password using reversible encryption" actually means
> Passwords aren't stored in true cleartext — they're stored using **RC4 encryption**. The decryption key ([Syskey](https://docs.microsoft.com/en-us/windows-server/security/kerberos/system-key-utility-technical-overview)) lives in the registry and can be extracted by a Domain Admin or equivalent. Tools like `secretsdump.py` will decrypt these automatically while dumping NTDS (as Domain Admin, or via DCSync).
>
> This setting is occasionally used to support applications/protocols requiring the user's password directly for authentication. If disabled after being set, the user must **change their password** for it to switch to one-way encryption — any password set while the option was enabled stays reversibly encrypted until changed.

## Key Takeaways

- [ ] DCSync abuses the Directory Replication Service Remote Protocol to impersonate a DC and pull the AD password database
- [ ] Requires `DS-Replication-Get-Changes` + `DS-Replication-Get-Changes-All` (or `-In-Filtered-Set`) rights on the domain object — held by Domain/Enterprise Admins by default, but sometimes misconfigured onto standard users
- [ ] `Get-ObjectAcl "DC=...,DC=..." -ResolveGUIDs | ? {$_.ObjectAceType -match 'Replication-Get'}` confirms whether a given SID has these rights
- [ ] `secretsdump.py -outputfile <name> -just-dc <domain>/<user>@<dc-ip>` performs the DCSync and writes 3 files: `.ntds` (hashes), `.ntds.kerberos` (Kerberos keys), `.ntds.cleartext` (reversible-encryption passwords, if any)
- [ ] Useful `secretsdump.py` flags: `-just-dc-ntlm`, `-just-dc-user <name>`, `-pwd-last-set`, `-history`, `-user-status`
- [ ] Reversible encryption stores passwords via RC4 (decryptable via Syskey), not true cleartext — but functionally recoverable by a DA or via DCSync; enumerate with `Get-ADUser -Filter 'userAccountControl -band 128'` or PowerView's `ENCRYPTED_TEXT_PWD_ALLOWED` flag
- [ ] Mimikatz's `lsadump::dcsync /domain:<domain> /user:<target>` needs to run **as** the DCSync-privileged account — use `runas /netonly /user:<domain>\<user>` to get that context first
- [ ] If you have WriteDacl over a user, you can grant DCSync rights, run the attack, then remove the rights again to help cover tracks
