# Access Control List (ACL) Abuse Primer

Not all users/computers in AD can access all objects and files — this is controlled through **Access Control Lists (ACLs)**. A slight ACL misconfiguration can leak permissions to objects that don't need them, posing a serious threat to domain security.

---

## ACL Overview

> [!info] What's an ACL?
> A list defining **(a)** who has access to a given asset/resource and **(b)** the level of access provisioned. The individual settings within an ACL are called **Access Control Entries (ACEs)**. Each ACE maps back to a user, group, or process (a "security principal") and defines the rights granted to it. Every object has an ACL, and can have multiple ACEs since multiple principals may need access. ACLs can also be used for auditing.

### Two Types of ACLs

| Type                                         | Purpose                                                                                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **DACL** (Discretionary Access Control List) | Defines which security principals are granted or denied access to an object. Made up of ACEs that allow or deny access. I**permission tab** |
| **SACL** (System Access Control List)        | Lets administrators log access attempts made to secured objects. **Auditing tab**                                                           |


> [!warning] What happens with no DACL / an empty DACL
> - **No DACL exists** for an object → everyone who attempts access is granted **full rights**.
> - **DACL exists but has no ACE entries** → the system **denies access to all** users/groups/processes attempting to access it.


---

## Access Control Entries (ACEs)

Three main ACE types apply to all securable objects in AD:

| ACE                    | Description                                                                                                                                        |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Access denied ACE**  | Used within a DACL — explicitly denies a user/group access to an object                                                                            |
| **Access allowed ACE** | Used within a DACL — explicitly grants a user/group access to an object                                                                            |
| **System audit ACE**   | Used within a SACL — generates audit logs when a user/group attempts access, recording whether access was granted and what type of access occurred |

### Four Components of Every ACE

1. The security identifier (SID) of the user/group that has access to the object (or principal name graphically)
2. A flag denoting **ACE type** (access denied, allowed, or system audit)
3. Flags specifying whether child containers/objects can **inherit** the ACE entry from the parent object
4. An [access mask](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/7a53f60e-e730-4dfe-bbe9-b21b62eb790b?redirectedfrom=MSDN) — a 32-bit value defining the rights granted

## Why Are ACEs Important?

> [!info] Attacker value
> Attackers use ACE entries to further access or establish **persistence**. Many organizations are unaware of the ACEs applied to their objects, or the impact of misconfiguring them. ACL issues:
> - **Cannot** be detected by vulnerability scanners
> - Often go **unchecked for years**, especially in large/complex environments
> - Can be a great avenue for lateral/vertical movement once the "low hanging fruit" is gone in an assessment

### Example AD Object Permissions & Abuse Tools

| Permission            | Abused With                                         |
| --------------------- | --------------------------------------------------- |
| `ForceChangePassword` | `Set-DomainUserPassword`                            |
| `Add Members`         | `Add-DomainGroupMember`                             |
| `GenericAll`          | `Set-DomainUserPassword` or `Add-DomainGroupMember` |
| `GenericWrite`        | `Set-DomainObject`                                  |
| `WriteOwner`          | `Set-DomainObjectOwner`                             |
| `WriteDACL`           | `Add-DomainObjectACL`                               |
| `AllExtendedRights`   | `Set-DomainUserPassword` or `Add-DomainGroupMember` |
| `AddSelf`             | `Add-DomainGroupMember`                             |

This module covers enumerating and leveraging **four specific ACEs**:

- [ForceChangePassword](https://bloodhound.specterops.io/resources/edges/force-change-password#forcechangepassword) — reset a user's password without knowing the current one. *(Use cautiously — consult the client first before resetting passwords.)*
- [GenericWrite](https://bloodhound.specterops.io/resources/edges/generic-write#genericwrite) — write to any non-protected attribute on an object. Over a **user**: assign an SPN → Kerberoast (relies on the account having a weak password). Over a **group**: add yourself/another principal to it. Over a **computer**: perform Resource-Based Constrained Delegation (outside this module's scope).
- [AddSelf](https://bloodhound.specterops.io/resources/edges/add-self#addself) — shows security groups a user can add themselves to.
- [GenericAll](https://bloodhound.specterops.io/resources/edges/generic-all#genericall) — full control over the target object. Over a user/group: modify membership, force-change password, targeted Kerberoasting. Over a **computer** with [LAPS](https://www.microsoft.com/en-us/download/details.aspx?id=46899) in use: read the LAPS password → local admin on that machine.

> [!note] Stay adaptable
> You'll run into other interesting ACEs/privileges over time. Keep the same methodology (BloodHound, PowerView, built-in AD tools) adaptable for new ones. E.g., a user might have [ReadGMSAPassword](https://bloodhound.specterops.io/resources/edges/read-gmsa-password) rights over a gMSA — a tool like [GMSAPasswordReader](https://github.com/rvazarkar/GMSAPasswordReader) can then retrieve that password. Other extended rights worth knowing, like [Unexpire-Password](https://learn.microsoft.com/en-us/windows/win32/adschema/r-unexpire-password) or [Reanimate-Tombstones](https://learn.microsoft.com/en-us/windows/win32/adschema/r-reanimate-tombstones), using PowerView may require research to figure out how to exploit. Worth familiarizing yourself with all [BloodHound edges](https://bloodhound.specterops.io/resources/edges/overview) and AD [Extended Rights](https://learn.microsoft.com/en-us/windows/win32/adschema/extended-rights).

## ACL Attacks in the Wild

ACL attacks can be used for:
- Lateral movement
- Privilege escalation
- Persistence

### Common Attack Scenarios

| Attack | Description |
|---|---|
| **Abusing forgot password permissions** | Help Desk/IT users are often granted password-reset rights. Taking over such an account (or one in a group conferring this) may let you reset a more privileged account's password. |
| **Abusing group membership management** | Help Desk/staff commonly have rights to add/remove users from a group — always worth enumerating, since you may be able to add a controlled account into a privileged built-in group or one granting an interesting privilege. |
| **Excessive user rights** | Users/computers/groups often end up with excessive rights the client isn't aware of — e.g. after a software install (Exchange makes many ACL changes at install time), or a legacy/accidental config. Sometimes an account was given rights out of convenience to solve a nagging problem quickly. |

> [!danger] Some ACL attacks are destructive
> Changing a user's password or modifying AD objects can be disruptive. **If in doubt, run the attack by the client first** and get written approval. Carefully document attacks start-to-finish, revert changes, and include this in the report — clearly highlight what was changed so the client can verify proper reversion.

## Key Takeaways

- [ ] DACL = who's allowed/denied access; SACL = audit logging of access attempts
- [ ] No DACL = full access to everyone; DACL with no ACEs = access denied to everyone
- [ ] ACLs are evaluated top-to-bottom, stopping at the first access-denied match
- [ ] Every ACE has 4 parts: SID, ACE type, inheritance flags, and a 32-bit access mask
- [ ] This module focuses on 4 ACEs: `ForceChangePassword`, `GenericWrite`, `AddSelf`, `GenericAll`
- [ ] ACL misconfigurations aren't caught by vuln scanners and often go unnoticed for years — a strong avenue once other low-hanging fruit is gone
- [ ] Common real-world patterns: forgot-password rights abuse, group membership management abuse, excessive/unintended rights from software installs or legacy config
- [ ] Always get client sign-off before performing potentially destructive ACL attacks (e.g. password resets), and document + revert everything
