## Abusing ACLs — Executing the Attack Chain

> [!info] Recap
> We control `wley` (NTLMv2 hash captured via Responder, cracked offline with Hashcat due to a weak password). This access can kick off a chain ending in control of `adunn`, who can DCSync — giving full domain compromise (NTLM hashes for all users, escalation to Domain/Enterprise Admin, persistence).

**Attack chain plan:**
1. Use `wley` to force-change the password for `damundsen`
2. Authenticate as `damundsen`, leverage `GenericWrite` to add a controlled user to `Help Desk Level 1`
3. Leverage nested membership in `Information Technology` + `GenericAll` to take control of `adunn`

### Step 3 — Targeted Kerberoasting via GenericAll on adunn

> [!info] Scenario twist
> Say the client permits changing `damundsen`'s password, but `adunn` is an admin account that **cannot be interrupted**. Since we have `GenericAll` over `adunn`, we can instead perform a **targeted Kerberoasting attack** by modifying the account's [servicePrincipalName attribute](https://docs.microsoft.com/en-us/windows/win32/adschema/a-serviceprincipalname) to add a fake SPN, then Kerberoast it and crack the hash offline.

> [!important] Auth requirement
> Must be authenticated as a member of `Information Technology` for this to work. Adding `damundsen` to `Help Desk Level 1` gave us that inherited access via nested group membership.

**Create the fake SPN with [Set-DomainObject](https://powersploit.readthedocs.io/en/latest/Recon/Set-DomainObject/):**

> [!tip] Linux equivalent
> [targetedKerberoast](https://github.com/ShutdownRepo/targetedKerberoast) performs this same attack from Linux in one command — creates a temporary SPN, retrieves the hash, and deletes the SPN automatically.


#### Creating a Fake SPN

```powershell
PS C:\htb> Set-DomainObject -Credential $Cred2 -Identity adunn -SET @{serviceprincipalname='notahacker/LEGIT'} -Verbose

VERBOSE: [Get-Domain] Extracted domain 'INLANEFREIGHT' from -Credential
```

## Cleanup

> [!important] Order matters
> 1. Remove the fake SPN from `adunn`
> 2. Remove `damundsen` from `Help Desk Level 1`
> 3. Reset `damundsen`'s password to its original value (if known) or have the client reset/alert the user
>
> If you remove the group membership **first**, you lose the rights needed to remove the fake SPN — so SPN cleanup must come before group removal.

### Removing the Fake SPN

```powershell
PS C:\htb> Set-DomainObject -Credential $Cred2 -Identity adunn -Clear serviceprincipalname -Verbose

VERBOSE: [Get-Domain] Using alternate credentials for Get-Domain
VERBOSE: [Get-Domain] Extracted domain 'INLANEFREIGHT' from -Credential
VERBOSE: [Get-DomainSearcher] search base: LDAP://ACADEMY-EA-DC01.INLANEFREIGHT.LOCAL/DC=INLANEFREIGHT,DC=LOCAL
VERBOSE: [Get-DomainSearcher] Using alternate credentials for LDAP connection
VERBOSE: [Get-DomainObject] Get-DomainObject filter string: (&(|(|(samAccountName=adunn)(name=adunn)(displayname=adunn))))
VERBOSE: [Set-DomainObject] Clearing 'serviceprincipalname' for object 'adunn'
```

### Removing damundsen from the Group

```powershell
PS C:\htb> Remove-DomainGroupMember -Identity "Help Desk Level 1" -Members 'damundsen' -Credential $Cred2 -Verbose

VERBOSE: [Get-PrincipalContext] Using alternate credentials
VERBOSE: [Remove-DomainGroupMember] Removing member 'damundsen' from group 'Help Desk Level 1'
True
```

### Confirming Removal

```powershell
PS C:\htb> Get-DomainGroupMember -Identity "Help Desk Level 1" | Select MemberName |? {$_.MemberName -eq 'damundsen'} -Verbose
```

> [!note] Report everything regardless
> Even with cleanup performed, **every modification** made during the assessment should be documented in the final report — clients need to be informed of any changes for their own peace of mind and verification.

> [!tip] This was one example path
> Large domains can have many attack paths, some shorter, some more complex. Real-world engagements often mirror this exact type of chain. Sometimes an ACL attack chain is too time-consuming or destructive to execute fully — in that case, enumerate and present the client with enough evidence to understand and remediate the issue instead.

## Detection and Remediation

### 1. Auditing for and Removing Dangerous ACLs
Organizations should run regular AD audits and train staff to use tools like BloodHound to spot dangerous ACLs that can be removed.

### 2. Monitor Group Membership
Visibility into high-impact groups is essential — all such groups should be monitored to alert IT staff to changes that might indicate an ACL attack chain in progress.

### 3. Audit and Monitor for ACL Changes
Enable the [Advanced Security Audit Policy](https://docs.microsoft.com/en-us/archive/blogs/canitpro/step-by-step-enabling-advanced-security-audit-policy-via-ds-access), especially [Event ID 5136: A directory service object was modified](https://docs.microsoft.com/en-us/windows/security/threat-protection/auditing/event-5136) — indicates a domain object was modified, potentially an ACL attack.

## Key Takeaways

- [ ] Full attack chain: `wley` → force-change `damundsen`'s password → `damundsen` adds self to `Help Desk Level 1` (GenericWrite) → nested in `Information Technology` → `GenericAll` over `adunn` → DCSync rights = domain compromise
- [ ] `Set-DomainUserPassword -Credential <cred>` force-changes a password using ForceChangePassword rights
- [ ] `Add-DomainGroupMember` / `Remove-DomainGroupMember -Credential <cred>` manage group membership via GenericWrite
- [ ] `Set-DomainObject -SET @{serviceprincipalname='x/y'}` creates a fake SPN for targeted Kerberoasting via GenericAll; `-Clear serviceprincipalname` removes it
- [ ] Rubeus (`kerberoast /user:<name> /nowrap`) or `targetedKerberoast` (Linux) retrieves the roastable hash for offline cracking
- [ ] Cleanup order matters: remove fake SPN **before** removing group membership, or you lose the rights needed to clean up the SPN
- [ ] Document every change made during the attack chain in the final report, even after full cleanup
- [ ] Detection: Event ID 5136 + Advanced Security Audit Policy flags directory object modifications; decode the SDDL with `ConvertFrom-SddlString` to spot unexpected principals gaining rights (e.g. GenericWrite on the domain object itself)
