# Domain Trusts Primer

## Scenario

Large orgs acquiring companies over time often establish **trust relationships** with new domains rather than migrating all objects — faster integration, but can introduce weaknesses if not carefully reviewed. A subdomain with an exploitable flaw can become a route into the target domain. Trusts also form between companies (e.g. an MSP), a customer, or business units/regional divisions of the same company.

---

## Domain Trusts Overview

A [trust](https://social.technet.microsoft.com/wiki/contents/articles/50969.active-directory-forest-trust-attention-points.aspx) establishes forest-forest or domain-domain authentication, letting users access resources (or perform admin tasks) in another domain outside their own. Trusts link two domains' authentication systems and can be one-way or bidirectional.

### Trust Types

| Type                                                                          | Description                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Parent-child**                                                              | Two+ domains in the same forest. Two-way transitive trust — e.g. users in `corp.inlanefreight.local` can authenticate into `inlanefreight.local` and vice versa                                                                                                 |
| **Cross-link**                                                                | Trust between child domains to speed up authentication                                                                                                                                                                                                          |
| **External**                                                                  | Non-transitive trust between two separate domains in separate forests not already forest-joined. Uses [SID filtering](https://www.serverbrain.org/active-directory-2008/sid-history-and-sid-filtering.html) to filter auth requests not from the trusted domain |
| **Tree-root**                                                                 | Two-way transitive trust between a forest root domain and a new tree root domain — created automatically when setting up a new tree root                                                                                                                        |
| **Forest**                                                                    | Transitive trust between two forest root domains                                                                                                                                                                                                                |
| **[ESAE]**(https://docs.microsoft.com/en-us/security/compass/esae-retirement) | A bastion forest used to manage Active Directory                                                                                                                                                                                                                |

### Transitive vs. Non-Transitive

> [!info] Transitive
>  trust is extended to objects that the child domain trusts.. If `Domain A` trusts `Domain B`, and `Domain B` has a transitive trust with `Domain C`, then `Domain A` automatically trusts `Domain C`.

> [!info] Non-transitive
> Only the directly named child domain is trusted — doesn't extend further down the chain.

![[Pasted image 20260728230446.png]]

| Transitive | Non-Transitive |
|---|---|
| Shared, 1-to-many | Direct trust only |
| Shared with anyone in the forest | Not extended to next-level child domains |
| Forest, tree-root, parent-child, cross-link trusts | Typical for external/custom trust setups |

> [!tip] Analogy
> **Transitive** = giving your whole household permission to accept a package on your behalf. **Non-transitive** = strict orders that only the delivery service and you personally can handle/sign for the package — no one else in the house counts.

### One-Way vs. Bidirectional

- **One-way trust:** users in the **trusted** domain can access resources in the **trusting** domain — not the reverse
- **Bidirectional trust:** users on both sides can access each other's resources (e.g. `INLANEFREIGHT.LOCAL` ↔ `FREIGHTLOGISTICS.LOCAL`)

---

## Why Trusts Matter for Security

> [!warning] Real-world risk pattern
> Trusts set up purely for convenience often never get a security review. **Mergers & Acquisitions** frequently create bidirectional trusts with acquired companies — introducing risk if the acquired company's security posture is unknown/untested. An attacker targeting your org might instead attack the *acquired* company as the softer target, then pivot in through the trust.
>
> This is a real, repeatable pattern: Kerberoasting a domain **outside** the principal domain can surface a user with admin access **inside** the principal domain. Finding zero footholds in the primary domain but a flaw in a trusted domain — which then hands over a foothold or full admin in the primary domain — is a common "end-around" attack path in real engagements.

![[Pasted image 20260728231021.png]]

> [!tip] Report this clearly
> Larger orgs are frequently unaware a trust relationship even exists with certain domains. Flag every trust found during enumeration, regardless of whether it was exploited.

**Reading this:** `INLANEFREIGHT.LOCAL` has two trusts:
- **`LOGISTICS.INLANEFREIGHT.LOCAL`** — `IntraForest: True` → a **child domain**, meaning we're currently positioned at the forest root
- **`FREIGHTLOGISTICS.LOCAL`** — `ForestTransitive: True` → a **forest** (or external) trust

Both show `Direction: BiDirectional` — authentication flows both ways across both trusts.

> [!important] Bidirectional access is a prerequisite
> If we can't authenticate **across** a trust, we can't enumerate or attack across it. Confirming direction matters before planning any cross-trust attack.

## Key Takeaways

- [ ] Trust types: parent-child, cross-link, external, tree-root, forest, ESAE
- [ ] Transitive = extends through the chain (forest/tree-root/parent-child/cross-link); non-transitive = direct only (external/custom)
- [ ] One-way (trusted → trusting only) vs. bidirectional (both directions)
- [ ] M&A-driven trusts are a common overlooked risk — attacking the weaker acquired company can be an "end-around" into the primary domain
- [ ] `Get-ADTrust -Filter *` (built-in) / `Get-DomainTrust` / `Get-DomainTrustMapping` (PowerView) / `netdom query trust` (CMD) / BloodHound's "Map Domain Trusts" — five ways to enumerate the same info depending on tool availability
- [ ] Confirm trust **direction** before planning cross-trust attacks — one-way trusts limit which side can reach the other
- [ ] Always confirm discovered trusts are in-scope with the client before attacking across them
